# 第四十一课：项目六问法

> 本课的一句话结论：**面对任何 Self-hosted 项目，先用六个固定问题把它看透 —— 它解决什么问题、要什么硬件、跑在哪里、怎么联网、数据在哪、Docker 扮演什么角色 —— 再决定要不要动手，可以省下大量试错。**

## 1. 今天学习什么

今天只学 1 个东西：**项目六问法** —— 一套用来分析任意 Self-hosted 项目的提问框架。

六个问题是：

```text
① 它解决什么问题？        →  这个服务存在的意义
② 硬件需求是什么？        →  CPU / 内存 / 存储 / 特殊硬件
③ 运行在哪里？            →  裸机 / Docker / VM
④ 怎么联网访问？          →  局域网 / 端口 / 远程方式
⑤ 数据存在哪里？          →  配置 / 数据库 / 文件的位置
⑥ Docker 在其中起什么作用？→  是它本身、依赖它、还是无关
```

你今天要建立的核心结构是：

```text
看一个陌生项目
    ↓
先不要抄教程
    ↓
用六问过一遍  →  形成自己的判断
    ↓
再决定要不要部署、怎么部署
```

## 2. 为什么要学

前八周你学了很多零件：硬件、存储、网络、Linux、Docker、Compose。但从今天起，你要面对的是**一整个项目** —— 一个有 README、有部署步骤、有配置项的完整东西。

如果没有一套框架，大多数人会这样做：**打开教程，照着敲命令，能跑起来就完事。**

这样做的问题是：教程不会解释「为什么这样配」。一旦出问题，你不知道该从哪里查；一旦要换个环境，你不知道哪些步骤可以变、哪些不能。

不学这套框架，会遇到这些问题：

- 为什么跟着教程部署，换一台机器就装不上了？
- 为什么有些项目作者说「很简单」，你却觉得处处是坑？
- 为什么装完之后数据放错了地方，重装一次全丢了？
- 为什么明明是同一个服务，别人的配置和你的要求差那么多？
- 为什么你总是先折腾半天，最后才发现硬件根本跑不动？

**六问法的价值，是把「抄教程」变成「做判断」。** 你不再是复述别人的步骤，而是先理解这个项目是什么、要什么，再决定怎么落地。

## 3. 小白解释

### 3.1 六问像「看房清单」

想象你要租一套房子。如果只是走进去看一眼「还行」，你很可能漏掉关键问题：采光好不好、水压够不够、隔音怎么样、通勤多远。

**有经验的人会带一张清单**：位置、面积、采光、水电、噪音、租金。每套房子都按同一张清单过一遍，就不会被表面印象骗到。

项目六问法就是看 Self-hosted 项目的**看房清单**。不管这个项目是影音、照片还是广告拦截，你都用同样的六个问题去问它。

### 3.2 为什么是这六个，顺序有讲究

六个问题不是随意凑的，它们有先后逻辑：

```text
先问价值：  ① 解决什么问题           ← 值不值得装
再问资源：  ② 硬件需求               ← 装不装得起
然后定位：  ③ 运行在哪里             ← 用什么方式装
         ④ 怎么联网访问             ← 别人怎么用
         ⑤ 数据存在哪里             ← 东西放哪、会不会丢
最后关系：  ⑥ Docker 的作用           ← 它对容器的依赖有多深
```

**很多人顺序反了**：一上来就研究「怎么用 Docker 装」，结果装完才发现硬件不够，或者数据放错了地方。先问价值和资源，能帮你**在动手之前就排除掉不合适的项目**。

### 3.3 六问不是考试，是习惯

这六个问题不需要你背得一字不差。它更像一个**固定的思考习惯**：每次看到新项目，心里自动过一遍。

用久了你会发现，你甚至能在**读 README 的过程中**就填完大部分答案 —— 因为好的 README 本身就会回答这几件事，只是散落在不同段落里。六问法帮你把它们重新组织起来。

## 4. 技术解释

### 4.1 六问的每一问在问什么

**① 它解决什么问题**

问的是这个项目的**核心价值**。不是「它有什么功能」，而是「它替代了什么、帮你省了什么」。比如影音服务替代的是「手动翻文件夹找视频」。

**② 硬件需求是什么**

问的是**最低门槛和瓶颈**。这里要特别注意：很多项目写「内存最低 2GB」，但真正吃资源的是某个特定功能（比如转码、机器学习）。**要找到那个真正的瓶颈，而不是只看最低配置。**

**③ 运行在哪里**

问的是**部署形态**：裸机（直接装在系统上）、Docker（容器里）、还是 VM（虚拟机里）。这个答案决定了你后面所有配置步骤长什么样。

**④ 怎么联网访问**

问的是**入口**：局域网内怎么访问（地址和端口）、出门要不要访问、用什么方式（参考第五周的结论）。这一问直接关系到安全。

**⑤ 数据存在哪里**

问的是**持久化**：哪些数据是配置、哪些是数据库、哪些是用户文件。这一问决定了你**备份什么、挂载什么卷**。对 NAS 用户来说，这是最不能马虎的一问。

**⑥ Docker 在其中起什么作用**

问的是**依赖关系**：这个项目本身就是一个 Docker 镜像？还是必须配合 Docker 才能跑？还是和 Docker 无关、可以裸机装？这决定了你选哪条部署路线。

### 4.2 为什么这套框架通用

这六个问题之所以能套用在几乎所有 Self-hosted 项目上，是因为**任何一个要在你的机器上长期运行的服务，都必须回答这六件事**：

- 它得有用（①）
- 它得能跑起来（②③）
- 你得能用上它（④）
- 它的数据得能留住（⑤）
- 它的部署方式得选对（⑥）

框架通用，不代表答案相同。恰恰相反：**同一套问题，不同项目的答案差别巨大** —— 这正是它有价值的地方。本周后面几天你会看到，同样是六问，Pi-hole 和 Immich 的答案完全不同。

### 4.3 这套框架的边界

必须说清楚它**不能**做什么：

- 它**不告诉你**这个项目好不好用、稳不稳定 —— 那要靠社区口碑和版本历史。
- 它**不告诉你**具体的命令和配置项 —— 那是教程和 README 的事。
- 它**不替你判断**该不该装 —— 它只是把决策所需的信息摆齐，最后的取舍还是你来做。
- 它**不覆盖**运维和故障处理 —— 装起来只是开始，长期维护是另一回事。

**六问法是一个起点，不是万能钥匙。** 它帮你把混乱的信息整理成清晰的判断，但不代替你思考。

## 5. 类比

把 Self-hosted 项目想象成**一件要请进家里的家具**。

买家具之前，你会先问自己：

```text
这件家具是干嘛用的？        ← ① 解决什么问题
家里放得下吗？              ← ② 硬件需求
放哪个房间？                ← ③ 运行在哪里
怎么搬进来、进出方便吗？     ← ④ 怎么联网访问
坏了怎么修、怎么搬走？       ← ⑤ 数据存在哪里
需要专门配一套配件吗？       ← ⑥ Docker 的作用
```

**这个类比能解释什么？**

- 它解释了**为什么顺序重要**：先想「放得下吗」，再想「搬进来」—— 反过来就是白忙。
- 它解释了**为什么同一个框架能问所有项目**：家具千差万别，但「用途、空间、位置、进出、维护、配件」这套问题对每件都适用。
- 它还解释了框架的**边界**：清单能帮你不漏关键问题，但**家具好不好看、耐不耐用，清单不会告诉你** —— 那要你亲自判断。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：看到一个「功能很酷」的项目，要不要装？**

先用六问过一遍。如果第①问你就答不出「它替代了什么」，那说明你其实不需要它。**能清楚说出「它帮我省了什么」的项目，才值得进入下一步。**

**场景二：教程能跑通，但换台机器就不行**

大概率是你跳过了③和⑤。运行方式（裸机/Docker/VM）决定了步骤的形态；数据位置决定了迁移时什么要带走。**只抄步骤、不填六问，就会遇到这种「只在原作者机器上能跑」的问题。**

**场景三：装完用了几天，数据全没了**

这是⑤没问清楚。容器本身是可以随时删掉的，**真正的数据必须放在容器之外的持久位置**。删容器丢数据，几乎总是因为没分清「哪些数据在容器里、哪些在挂载的卷里」。

### 6.2 六问答案的差异表

同一个框架，答案会差很远。这是本项目后面几天要填的对照表的样子：

| 项目 | ① 问题 | ③ 运行位置 | ⑤ 数据位置 | ⑥ Docker 作用 |
|---|---|---|---|---|
| 影音服务 | 统一管理影音库 | Docker 或裸机 | 媒体文件 + 数据库 | 打包环境，媒体靠挂载 |
| 广告拦截 | 网络层拦截广告 | Docker 或裸机 | 查询记录 + 规则 | 打包环境 |
| 照片备份 | 自建相册替代云相册 | Docker（多容器） | 原件 + 数据库 + 缩略图 | 是它工作的前提 |
| 远程通道 | 安全访问内网 | 每台设备装客户端 | 密钥和登录状态 | 可选，不必须 |

**看这张表就能明白：六问法不给你统一答案，它给你统一的思考路径。** 答案的差异，恰恰是每个项目性格的体现。

## 7. 常见误区

### 误区一：先看部署教程，再了解项目用途

反了。**先问「它解决什么问题」，再问怎么装。** 直接看教程的人，容易在装完之后才发现自己根本用不上，或者需要的功能它没有。价值判断永远在最前面。

### 误区二：硬件需求就是 CPU 和内存

不完整。**真正的瓶颈常常是某个特定功能，而不是整机配置。** 比如影音服务的瓶颈可能是转码、照片服务的瓶颈可能是机器学习功能。只看「最低配置」，会漏掉那个真正决定成败的环节。

### 误区三：六问法是用来背的考试题

它不是。**六问法是一个思考习惯，不是知识点。** 你不需要一字不差地背出来，而是要在看到新项目时，自然而然地想到这六个方向。用多了它会变成直觉。

### 误区四：六问法能判断一个项目好不好

不能。**它只帮你把信息摆齐，不评价质量。** 一个项目六问都答得很漂亮，也可能长期不更新、bug 一堆。稳定性、活跃度、口碑，是六问之外的另一套判断，要靠社区和版本历史。

### 误区五：六个问题问完就能直接照做了

还不够。六问法处理的是「是什么、要什么」，**不处理「具体怎么做」**。填完六问，你得到的是判断；具体的命令、配置项、参数，仍然要回到 README 和教程里去落实。
