# 第三十八课：容器的生命周期

> 本课的一句话结论：**Compose 文件描述的是「应该是什么样」，而容器会经历创建、运行、停止、重建的循环 —— 升级的本质是「用新描述换掉旧容器」，而数据能不能活下来，取决于它有没有被放在 volumes 里。**

## 1. 今天学习什么

今天要理解 4 个环节：

1. **创建（Create）**：按文件描述把容器造出来。
2. **停止（Stop）**：容器被停下来，但通常不会被删除。
3. **日志（Logs）**：程序运行时说的话，都在日志里。
4. **升级（Upgrade）**：换一个版本，本质是「重建」。

今天的核心结构：

```text
         compose.yaml（描述「应该是什么样」）
                  │
                  │ 执行
                  ↓
   ┌──────────────────────────────┐
   │  创建 → 运行 → 停止 → 重建    │   ← 容器的一生
   └──────────────────────────────┘
                  │
                  ↓
        volumes 里的数据留了下来
        （容器是临时的，数据是长期的）
```

以及一条最重要的区分：

```text
容器（Container）  →  临时的，可以随时删掉重建
数据（Data）       →  长期的，放在 volumes 里才不会丢
```

## 2. 为什么要学

前两天你能读文件了。但文件读懂了，动手时仍然会遇到一连串疑问：**改完文件该怎么让它生效？停了服务数据还在吗？出问题了我该看哪里？升级会不会把数据搞没？**

不理解生命周期会遇到这些问题：

- 为什么我改了 compose.yaml，服务还是老样子？
- 为什么说「重启容器」和「重建容器」是两件不同的事？
- 为什么服务打不开时，第一件事是去看日志？
- 为什么升级前要先备份，而不能直接点「更新」？
- 为什么删掉容器之后，数据有时候还在，有时候却没了？

**这些问题全部指向同一件事**：容器是临时的，而你在它身上花的时间、放进它的数据，需要被放在容器之外的某个地方才安全。

## 3. 小白解释

### 3.1 容器像一次性的工作间

把容器想象成一个**临时搭建的工作间**：

```text
按图纸搭起来（创建）
里面开始干活（运行）
暂时收工（停止）
拆掉重搭一个新的（重建 / 升级）
```

关键在于：**这个工作间本身是临时的。** 拆掉它，墙和桌椅都没了 —— 但如果你把重要的东西存在**楼下的储物柜**里（volumes），那柜子还在。

```text
工作间（容器）  →  拆了可以重搭，不心疼
储物柜（数据）  →  只有它才装着真正重要的东西
```

**所以每次动手之前要问自己一句**：这个服务的哪些东西存在储物柜里？哪些只存在于工作间里？只存在工作间里的，重建时就没了。

### 3.2 「停止」和「删除」不是一回事

这两件事经常被混在一起，但它们完全不同：

```text
停止（Stop）  →  工作间锁上门，东西还在里面
删除（Remove）→  工作间拆掉，里面的东西一起没了
```

停止之后再启动，还是原来那个容器；删除之后再启动，是一个**全新的容器**。

**为什么要分清？** 因为「改了一个环境变量」这种改动，光靠停止再启动是不够的 —— 需要让容器按新描述重新生成。

### 3.3 日志：程序在说话

容器里的程序没法弹出对话框告诉你发生了什么。**它唯一能说话的地方，就是日志（Logs）。**

```text
启动成功  →  日志里会写「已启动，监听 xxx」
配置错了  →  日志里会写「缺少环境变量 xxx」
连不上数据库 → 日志里会写「连接被拒绝」
```

**所以「服务打不开」时的第一反应，不该是反复重启，而是先看日志。** 日志通常直接告诉你原因。

### 3.4 升级：换一个新的，而不是修补旧的

容器的世界里，**升级的方式是「重建」**：

```text
旧做法（软件）：在原有的程序上打补丁 → 越打越乱
容器做法：      按新的描述造一个新的，把旧的扔掉
```

这样做的好处是干净：新容器从镜像重新生成，不会残留旧的临时文件。

**但这也意味着**：任何没放进 volumes 的东西，都会在升级时消失。**升级前备份，就是这个道理。**

## 4. 技术解释

### 4.1 容器的几种状态

| 状态 | 含义 |
|---|---|
| Created | 已创建，但还没启动 |
| Running | 正在运行 |
| Exited / Stopped | 已停止，容器还在，可以再启动 |
| Removed | 已删除，容器不存在了 |

**注意 Exited 和 Removed 的区别**：前者是「停了，还在」，后者是「没了」。日常操作里，前者可以随时恢复，后者只能重建。

### 4.2 文件改动什么时候生效

这是最实用的一条：

| 你改了什么 | 需要做什么才生效 |
|---|---|
| 只改了环境变量、端口、镜像版本 | 需要**重建**容器 |
| 改了 volumes 的挂载路径 | 需要**重建**容器 |
| 只改了宿主机上挂载目录里的文件 | 通常不需要做什么，容器直接读到新内容 |
| 什么都没改，只是程序卡住了 | 重启容器即可 |

**规律是**：**凡是写在 Compose 文件里的内容，改了都要重新应用一次描述。** 只改文件、不执行，不会生效。

### 4.3 日志的读法

日志通常按时间顺序排列，**最后几行最重要**，因为最新的信息在最下面。

```text
开头  →  启动过程：加载了什么、用了什么配置
中间  →  运行过程：收到的请求、做的操作
结尾  →  最新的状态，或者出错的原因
```

**读日志的正确姿势**：

1. 先拉到**末尾**，看最后发生了什么。
2. 找到第一个「错误」或「失败」出现的位置 —— 那通常才是根因，后面的一堆报错往往是连带的。
3. **注意日志里可能包含敏感信息**（比如连接字符串、令牌）。分享日志求助前，先把这些内容去掉。

### 4.4 升级的正确顺序

```text
1. 确认新版本的说明        → 有没有「必须改配置」的提示
2. 备份数据目录            → volumes 对应的宿主机目录
3. 记录当前版本            → 出问题时能退回去
4. 修改文件里的版本号      → 从 :1.0 改成 :1.1
5. 重新应用描述            → 让容器按新版本重建
6. 看日志确认启动成功
7. 实际访问一次验证功能
```

**第 2 步不能跳过。** 容器的回滚很方便（改回版本号再重建），但**数据的回滚只能靠备份**。镜像可以换回来，被新版本升级过的数据结构未必能降级。

> **安全提醒**：升级前把数据目录复制一份到别的位置。这不是「小心过度」——数据损坏和误操作是自托管最常见的损失来源，而它们几乎都无法通过重装软件挽回。

## 5. 类比

把容器想象成**酒店房间，而你是长期住客**：

- **创建**是办理入住，按订单（Compose 文件）安排房间。
- **停止**是你退房离开，但房间还在，行李如果放在保险箱（volumes）里，下次来还能取。
- **删除**是房间被彻底清空翻新，放在房间里的东西全没了 —— 只有保险箱里的东西还在。
- **升级**是换到同一间新装修的房间：家具是新的（新镜像），但你的保险箱没动。
- **日志**是前台留下的记录本，写着这间房发生过什么、有没有出问题。

这个类比能解释什么：

- **为什么升级前要备份**：翻新过程中，保险箱里如果有东西被新装修队弄乱了（数据结构变更），你自己得有一份拷贝。
- **为什么「重启一下」有时没用**：你只是又住进了同一间房，订单并没有变。
- **为什么「数据没了」通常是自己造成的**：把重要东西放在了房间里，而不是保险箱里。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：改了端口，重启后没变化**

因为**重启不会重新读取 Compose 文件**。文件的改动需要在「重新应用」的动作里才会被读到，那通常意味着容器被重新创建。这两件事被很多界面放在不同的按钮上，值得每次动手前确认一遍。

**场景二：服务打不开，该先做什么**

先看日志，**不要先重启**。重启会把当前的错误现场清掉一部分，而你还没看到原因。日志里通常会直接写清楚是配置问题、端口冲突，还是连不上依赖。

**场景三：升级一个「有数据库」的服务**

这类服务最需要小心。**新旧版本的数据结构可能不一样**，新版本启动时可能会自动升级数据 —— 而这个升级往往**不可逆**。

```text
升级前   →  备份数据目录
出问题   →  改回旧版本号重建，并把备份的数据放回去
```

**如果没备份，改回旧版本也可能读不了已经被升级过的数据。** 这就是备份和回滚不是一回事。

### 6.2 常见操作与后果对照

| 操作 | 容器 | 数据（在 volumes 里） | 什么时候用 |
|---|---|---|---|
| 停止 | 保留 | 保留 | 临时不用了 |
| 重启 | 保留 | 保留 | 程序卡住 |
| 重建 | 换成新的 | 保留 | 改了文件里的配置 |
| 删除容器 | 消失 | 保留 | 清理，之后重新部署 |
| 删除 volumes | 消失 | **消失** | 确定不要这些数据了 |

**这张表里最需要盯住的是最后一行。** 删除 volumes 是少数几个「不可逆」的操作之一，做之前一定要确认清楚这个卷对应宿主机上的哪个目录、里面是什么。

### 6.3 一个可以复用的自查清单

```text
动手前：
  □ 我知道这个服务的数据存在哪个目录吗？
  □ 我最近备份过它吗？
  □ 我知道当前是哪个版本吗？

动手后：
  □ 日志最后几行有没有报错？
  □ 我实际访问过一次，确认能打开吗？
  □ 数据还在吗？
```

## 7. 常见误区

### 误区一：改完文件会自动生效

不会。**文件是描述，改动必须通过一次「重新应用」才会被读到**，而那通常意味着容器被重建。改完文件发现「没变化」，绝大多数情况是这个原因。

### 误区二：停止容器等于删除了它

不是。停止只是让它不再运行，容器本身还在，可以再启动。**删除才是真的没了。** 这两件事在不同的界面上往往挨得很近，操作前要看清按钮上的字。

### 误区三：数据丢了是因为 Docker 不稳定

大多数情况恰恰相反：**是因为数据从一开始就没放进 volumes。** 容器被重建时，只存在于容器内部的文件会随之消失，这是容器的正常设计，不是故障。判断方法很简单 —— 回看 Compose 文件里有没有覆盖到程序真正写入的那些目录。

### 误区四：升级就是换个版本号，没什么风险

风险主要来自**数据**，而不是程序。程序回滚容易（改回版本号重建），但新版本可能已经改动了数据的结构，**这个改动的回退只能靠升级前的备份**。所以「升级」这件事的准备工作，比操作本身重要得多。

### 误区五：出问题就重启，重启能解决大部分问题

重启只能解决「进程卡住」这一类问题。**它解决不了配置错误、端口冲突、路径写错、权限不足。** 而且每次重启都会让你丢失一部分现场信息。正确的第一反应是**看日志**，找到原因再决定动作。
