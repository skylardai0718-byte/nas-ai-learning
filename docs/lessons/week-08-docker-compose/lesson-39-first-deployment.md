# 第三十九课：一次局域网部署

> 本课的一句话结论：**部署不是「把文件贴上去点运行」，而是先用四个字段预测出访问地址和数据位置，再去验证预测对不对 —— 预测错了，说明你还没读懂那份文件。**

## 1. 今天学习什么

今天没有新术语，而是把前三天的内容用一遍：

1. **局域网部署（Local Deployment）**：只在家庭网络内部提供服务的部署方式。
2. **先预测、后验证（Predict then Verify）**：动手前先写下结论，再对照实际结果。
3. **示例数据原则**：练习只用虚构内容，不涉及任何真实凭据。

今天的核心结构：

```text
第 1 步  选一个安全的练习对象（无账号、无密码、无真实数据）
第 2 步  读它的 compose.yaml，写下四个预测
第 3 步  执行
第 4 步  用浏览器和文件管理器验证
第 5 步  对不上的地方，就是你没读懂的地方
```

以及你要填的那张预测表：

```text
用什么？   ____________________
从哪进？   ____________________
数据在哪？ ____________________
缺什么？   ____________________
```

## 2. 为什么要学

前三天你都在「读」。但读没读懂，只有动手那一刻才知道。

**很多人学 Compose 的方式是：抄一份文件、点运行、能打开就算成功。** 这样做的问题在于 —— 下次换一个项目，你还是不会。因为你验证的是「这次碰巧通了」，而不是「我读懂了」。

不理解这一课的意义会遇到这些问题：

- 为什么我照着教程做成功过一次，换一个项目又完全不会了？
- 为什么服务明明在运行，我却不知道它的数据存在哪？
- 为什么「能打开」不等于「部署对了」？
- 为什么练习时用一个真实的、带账号的服务，是不合适的？
- 为什么我说不清「我刚才到底做了什么」？

**本课的目标是让你能完整讲述一次部署**：用的是什么、从哪进、数据在哪、缺什么、结果如何。这比「跑通一次」重要得多。

## 3. 小白解释

### 3.1 为什么要先预测

想象你要去一个陌生的地方，先看一眼地图，说出「我应该往东走三个路口」，然后再走。

```text
先预测  →  走错了，你知道是哪里错了
后验证  →  走错了，你只知道「没到」
```

**先写下预测，会让「没成功」也变成有效的信息。** 你会知道是自己哪一步的理解出了问题，而不是只得到一个「打不开」。

### 3.2 选一个安全的练习对象

**不要拿真实在用的服务来练手。** 第一轮练习要满足三个条件：

```text
1. 不需要账号和密码
2. 不接触任何真实数据
3. 只在局域网内部，不对公网开放
```

**为什么强调这些？** 因为练习意味着会反复停止、重建、甚至删掉重来。拿真实服务练，一次误操作可能就丢掉数据；拿带密码的服务练，很容易把凭据写进笔记。

**本课用的示例是一个纯静态的欢迎页服务** —— 它只显示一个本地目录里的内容，没有登录、没有数据库、没有密码。

### 3.3 「部署完了」的五个问题

一次部署做得完整不完整，用这五个问题检验：

```text
1. 它是什么？          （用什么镜像）
2. 我从哪访问它？      （地址:端口）
3. 它的数据在哪？      （宿主机的哪个目录）
4. 我要填什么？        （有没有必填变量）
5. 我怎么知道它正常？  （日志写了什么、页面能不能打开）
```

**五题都答得上来，才叫部署完了。** 只回答得出第 2 题，那只是「碰巧打开了」。

## 4. 技术解释

### 4.1 练习用的目录结构

先建一个专门的项目目录，把所有东西放在一起：

```text
~/hello-web/
├── compose.yaml        ← 这份文件描述怎么跑
└── site/               ← 这是数据目录，会被挂进容器
    └── index.html      ← 一个纯文本的欢迎页，内容是示例文字
```

**为什么文件和数据放在同一个目录里？** 因为这样备份和迁移时是一个整体 —— 复制这个目录，就等于复制了整个服务。这是自托管里值得养成的习惯。

`site/index.html` 里只放示例文字，比如一句「这是一个练习页面，仅用于局域网内部测试」。**不要放任何真实内容。**

### 4.2 练习用的 compose.yaml

```yaml
services:
  hello:
    image: example/hello-web:1.0
    ports:
      - "8081:80"
    volumes:
      - ./site:/usr/share/web/static:ro
    environment:
      - SITE_TITLE=Practice Only
    restart: unless-stopped
```

（`example/hello-web:1.0` 是教学用的虚构镜像名。）

逐段说明：

| 字段 | 内容 | 说明 |
|---|---|---|
| `image` | `example/hello-web:1.0` | 一个只提供静态文件的程序，版本 1.0 |
| `ports` | `"8081:80"` | 从局域网的 8081 端口进入 |
| `volumes` | `./site:/usr/share/web/static:ro` | 把本地的 `site/` 目录挂进去，`:ro` 表示**只读** |
| `environment` | `SITE_TITLE=Practice Only` | 一个无害的设置，仅为演示 |
| `restart` | `unless-stopped` | 除非手动停掉，否则退出后自动重启 |

关于 `:ro`：它是 **read-only（只读）** 的缩写。意思是容器只能读这个目录，不能往里写。**练习阶段用只读挂载更安全** —— 即使程序行为异常，也动不了你的文件。

### 4.3 动手前，先写下预测

**这一步不要跳到第 4.4 节。** 先闭卷在纸上写下你的四个答案：

```text
1. 用什么？      ____________________
2. 从哪进？      ____________________
3. 数据在哪？    ____________________
4. 缺什么？      ____________________
```

对照检查你写的应该是：

```text
1. 用一个静态网页服务，版本 1.0
2. 局域网地址:8081（比如 192.168.1.10:8081）
3. 数据在 ~/hello-web/site/（相对 compose.yaml 所在目录）
4. 没有必填的敏感变量；SITE_TITLE 只是一个普通设置
```

**注意第 3 题**：数据目录是 `./site`，也就是**相对于这份 Compose 文件所在的目录**。如果你把文件放在 `~/hello-web/`，那就是 `~/hello-web/site/`。

### 4.4 执行与验证

按顺序做这几件事：

```text
1. 确认目录结构正确      两个条目：compose.yaml 和 site/
2. 执行这份 Compose 文件 （通过系统提供的入口，不在这里展开具体命令）
3. 观察它是否被创建出来
4. 打开日志，看最后几行
5. 在浏览器访问 设备地址:8081
6. 回到文件管理器，确认 site/ 目录还在，内容没被改动
7. 修改 index.html 的内容，刷新浏览器，看是否立刻变化
```

**第 7 步是最有说服力的一步**：

```text
改了宿主机上的文件 → 刷新页面就看到新内容
= 证明「这个目录确实被挂进了容器」
```

如果改完没变化，说明挂载路径可能不对 —— 那正是你要找出来的东西。

### 4.5 对不上怎么办

预测和实际不符时，按这个顺序排查：

| 现象 | 先看哪里 |
|---|---|
| 页面打不开 | `ports` 写的是什么？浏览器地址里的端口和它一致吗？ |
| 页面打开但内容不对 | `volumes` 的路径对不对？容器里的目标路径写错了吗？ |
| 改了文件没变化 | 挂载的是不是这个目录？是不是写成了只读？ |
| 容器反复重启 | 看日志最后几行，通常直接写了原因 |

**「预测错了」不是失败，而是这次练习最有价值的部分** —— 它精确地指出了你哪个概念还没对。

## 5. 类比

把这次部署想象成**在家里办一场只请邻居的小型展览**：

- **`site/` 目录是你的展品库**：展品放在你自己家的柜子里，随时能换。
- **`volumes` 是「把展品柜搬到展厅现场」**：观众看的是你的人，不是复制品 —— 你换了展品，现场立刻变。
- **`:ro` 是「只展不卖、不许动手」**：观众只能看，不能改你的东西。
- **`ports` 是展厅的门牌号**：`8081` 是你选的，邻居知道敲这一扇门。
- **局域网部署是「只开放给本小区」**：门牌号只有小区内的人找得到，外面的人不知道有这么个门。
- **先预测是把路线写在纸上**：走之前先说出「应该在东边第三栋」，到了之后才知道自己认不认路。

这个类比能解释什么：

- **为什么改宿主机文件、页面就变**：观众看的始终是你的柜子，不是复印件。
- **为什么练习不放真实内容**：这是对邻居开放的展览，不是自家保险柜。
- **为什么先预测**：只有先说出预期，走错时才分得清是路的问题还是自己看错地图。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：页面能打开，但我不知道数据在哪**

这说明你只验证了「从哪进」，没验证「数据在哪」。**补做一件事**：去宿主机上找到那个目录，改一个文件，看页面是否变化。能变化，就证明你找到了正确的位置。

**场景二：教程说用 8080，我用了 8081，可以吗**

可以，但你要明白自己改了什么。**改 `ports` 左边那个数字，只影响「你从哪个门进」，不影响容器内部。** 换端口的原因通常是原端口已被别的服务占用。改完之后，你访问时必须用新端口 —— 这一点经常被忘掉。

**场景三：练习时该不该让它开机自动启动**

练习阶段建议先不要。`restart: unless-stopped` 会让它一直跟着系统跑，占着端口。等这个服务你确定要长期保留、并且已经想清楚数据备份方案之后，再打开这个设置。

### 6.2 一次部署的记录表

把这次练习的结果填进表里，**这就是你第一份可复述的部署记录**：

| 项目 | 你的答案 |
|---|---|
| 服务是什么 | 一个只在局域网使用的静态欢迎页 |
| 访问地址 | 设备局域网地址:8081 |
| 数据位置 | 项目目录下的 `site/` 子目录 |
| 必填变量 | 无敏感变量；`SITE_TITLE` 为普通设置 |
| 是否对公网开放 | 否，只在局域网内 |
| 数据是否在 volumes 里 | 是，且为只读挂载 |
| 如何验证正常 | 日志无报错 + 浏览器能打开 + 改文件后页面随之变化 |

**注意「是否对公网开放」这一栏要写「否」并说得出理由**：这个服务没有做端口转发，也没有接入任何对外的通道，所以只有同一个局域网内的设备能访问它。

### 6.3 为什么第一轮练习要对公网保持关闭

```text
练习服务通常：没有强认证、用默认设置、随时会被删掉重建
     ↓
如果暴露到公网：
  任何人都能访问，而且你并不打算认真维护它
     ↓
结论：练习服务一律只放在局域网内
```

**这不是「以后再说」的事，而是「第一次就做对」的事。** 很多人的第一个服务就是直接暴露出去的，之后再想收回来，往往要花更多功夫。

## 7. 常见误区

### 误区一：能打开就算部署成功

不够。**「能打开」只验证了 `ports`。** 数据在哪、有没有必填项没填、容器重建后数据还在不在，这些都还没验证。用第 3.3 节的五个问题过一遍，才算完整。

### 误区二：先执行，出问题再看文件

顺序反了。**先执行会让你失去判断力** —— 页面打开了，你不知道为什么；打不开，你也不知道该查哪。先预测再执行，两种情况都能给你信息。

### 误区三：练习用真实数据更有意义

对自己真实在用的数据练手，风险极高。**练习会反复停止、重建、删除**，而真实数据的丢失往往是不可逆的。第一轮用示例内容，学会了再迁移真实内容 —— 迁移时的步骤是一样的。

### 误区四：`./site` 是容器里的路径

不是。**冒号左边永远是宿主机上的路径，右边才是容器内部的路径。** `./site` 指的是「这份 Compose 文件旁边的 site 目录」，是你自己机器上的位置。写反了，数据就会挂到别的地方去。

### 误区五：反正是练习，密码随便写一个就行

问题不在于密码强度，而在于**习惯**。练习时随手写一个真实密码，很容易在截图、笔记、求助时被一起带出去。**从一开始就用 `CHANGE_ME` 这样的占位符**，让「写占位符」成为肌肉记忆。
