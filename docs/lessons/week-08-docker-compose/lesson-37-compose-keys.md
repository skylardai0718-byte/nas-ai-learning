# 第三十七课：读懂 Compose 的四个关键字段

> 本课的一句话结论：**一份 Compose 文件里，`image` 决定用什么、`ports` 决定从哪进、`volumes` 决定数据在哪、`environment` 决定怎么配置 —— 读懂这四个字段，就读懂了一个项目的大部分。**

## 1. 今天学习什么

今天要掌握 4 个字段：

1. **image（镜像）**：这个服务用哪个现成的程序包启动。
2. **ports（端口）**：从外面通过哪个地址和端口访问它。
3. **volumes（卷 / 目录挂载）**：它的数据实际存在宿主机的哪里。
4. **environment（环境变量）**：启动时传给它的设置，比如必填的密码占位符。

今天的核心结构：

```text
一个 Service
├── image        →  用什么         （哪个程序）
├── ports        →  从哪进         （访问入口）
├── volumes      →  数据在哪       （会不会丢）
└── environment  →  怎么配置       （要填什么）
```

以及一个判断顺序：

```text
先看 image  → 这是什么东西
再看 ports  → 我从哪打开它
再看 volumes → 我的数据安不安全
最后看 environment → 我还缺什么没填
```

## 2. 为什么要学

昨天你知道了 Compose 文件是一份清单。但清单上的字你还没认全 —— 尤其是从网上抄来的项目，几十行字段堆在一起，很容易看完之后仍然不知道：**这东西到底怎么打开，数据会不会丢。**

不理解这四个字段会遇到这些问题：

- 为什么 README 里写了一堆说明，我却找不到访问地址？
- 为什么照着教程部署完，数据一重启就没了？
- 为什么文件里有 `volumes:`，但我根本不知道文件到底存在哪？
- 为什么服务启动报错，说某个变量没设置？
- 为什么同一个服务在别人的教程里端口是 8080，在我这里却是 3000？

**这四个字段是「读懂别人的文件」这件事的主体。** 今天之后，你拿到任何一份 Compose 文件，都应该能在五分钟内回答出「从哪进、数据在哪、缺什么」。

## 3. 小白解释

### 3.1 image：用什么

`image` 回答的是「这个服务用什么程序」。

```yaml
image: example/notes:1.0
```

它的写法和 Week 7 学过的镜像完全一样：

```text
仓库名 / 项目名 : 标签
example / notes : 1.0
```

- 冒号后面是**标签（tag）**，也就是版本。不写标签时会默认用 `latest`，但那意味着「每次拉取可能都不一样」，不利于稳定。
- **image 只是「用什么」，它不告诉你这个程序该怎么配。** 配置在 `environment` 里。

### 3.2 ports：从哪进

`ports` 回答的是「我从哪个地址打开它」。

```yaml
ports:
  - "8080:80"
```

这一行的读法是固定的，**冒号左边是外面，右边是里面**：

```text
"8080:80"
   ↑     ↑
 宿主机  容器
 (你访问) (程序自己)
```

于是访问方式就是：`设备地址:8080`。

**这是最容易读反的一处。** 记住一句话：**左边是你敲的，右边是程序自己的。**

### 3.3 volumes：数据在哪

`volumes` 回答的是「数据实际放在哪」。

```yaml
volumes:
  - ./data:/app/data
```

同样是「左边外面、右边里面」：

```text
./data  :  /app/data
   ↑           ↑
宿主机上的    容器内部的
一个目录      一个目录
```

它的意义是：**容器被删除、重建、升级时，`./data` 这个目录还在，数据不会跟着消失。**

`./` 表示「相对于这份 Compose 文件所在的目录」。所以文件放在 `~/notes-app/`，数据就会出现在 `~/notes-app/data/`。

> **这条特别重要**：`volumes` 是数据安全的界线。没有它，容器一删，数据一起没。

### 3.4 environment：怎么配置

`environment` 回答的是「启动时要告诉它什么」。

```yaml
environment:
  - APP_MODE=simple
  - DB_PASSWORD=CHANGE_ME
```

它是**键=值**的列表。程序启动时会读这些值，用来决定自己的行为。

**很多项目的环境变量是必填的** —— 比如数据库密码、访问令牌、初始管理员账号。不填，容器可能直接启动失败，或者用了一个不安全的默认值。

> **安全提醒**：凡是密码、令牌、密钥，在示例和笔记里一律写成 `CHANGE_ME` 这样的占位符。**真实凭据不要写进 Compose 文件** —— 这类文件最常被误传到公开仓库，一旦泄露，等于把你家的钥匙挂在网上。

## 4. 技术解释

### 4.1 一份带中文旁注的完整示例

下面这份文件是教学示例，镜像名是虚构的。先整体读一遍，再看后面的逐段旁注。

```yaml
# compose.yaml —— 一个「局域网内部使用」的笔记服务示例
services:
  notes:
    image: example/notes:1.0
    ports:
      - "8080:80"
    volumes:
      - ./data:/app/data
      - ./uploads:/app/uploads
    environment:
      - APP_MODE=simple
      - ADMIN_PASSWORD=CHANGE_ME
    restart: unless-stopped
```

下面逐段说明它在描述什么：

```text
# compose.yaml —— 一个「局域网内部使用」的笔记服务示例
  这是注释，YAML 会忽略。注释是给人看的，不影响运行。
  好的项目会在注释里写清用途，读到这类注释是好事。

services:
  顶层字段。它下面列出的每一项，都是这个项目里的一个容器。

  notes:
    服务名。这里是「笔记服务」。
    这个名字由作者自定，只在文件内部用于互相引用。

    image: example/notes:1.0
    用什么：这个项目的笔记程序，版本 1.0。
    读法：仓库/项目:标签。

    ports:
      - "8080:80"
    从哪进：外面 8080 → 容器内部 80。
    所以你访问的是「设备地址:8080」。

    volumes:
      - ./data:/app/data
      - ./uploads:/app/uploads
    数据在哪：宿主机当前目录下的 data/ 和 uploads/，
    分别挂进容器的 /app/data 和 /app/uploads。
    容器重建了，这两个目录依然在。

    environment:
      - APP_MODE=simple
      - ADMIN_PASSWORD=CHANGE_ME
    怎么配置：两项目设置。第二项是密码占位符，
    真实使用时必须替换成你自己的强密码，且不要提交到公开仓库。

    restart: unless-stopped
    附加设置：除非被手动停掉，否则容器退出后自动重启。
    常见于「想让它一直开着」的服务。
```

**读到这里，你应该能回答出四件事：**

```text
用什么？   example/notes:1.0
从哪进？   设备地址:8080
数据在哪？ ./data 和 ./uploads（相对 compose.yaml 所在目录）
缺什么？   ADMIN_PASSWORD 需要替换成真实值
```

**这四句话，就是「读懂一份 Compose 文件」的最小成果。**

### 4.2 拿到一个项目的 README，怎么找出这四样

Compose 文件常常不是孤零零给的，项目根目录一般还有一份 `README.md`。**更省力的读法是先看 README，再去文件里核对。** 按这个顺序找：

| 你要找的 | README 里通常写在哪 | 关键词 |
|---|---|---|
| 镜像 | 安装 / 部署章节 | `image:`、`docker pull`、Images |
| 端口 | 安装章节，或「访问」说明 | `port`、`访问`、`open`、`localhost:` |
| 数据目录 | 安装章节的挂载说明，或「备份」章节 | `volume`、`mount`、`data`、`backup` |
| 必填变量 | 「配置」或「环境变量」章节 | `environment`、`.env`、`required`、`Variables` |

**三条实用判断**：

```text
1. README 的「快速开始」里出现的变量，通常就是必填的 —— 因为不填就跑不起来。
2. 「备份」章节提到的目录，就是真正装着数据的那个 volume。
3. 如果 README 让你复制一份 .env.example，那说明这个项目把配置放在外部文件里，
   Compose 文件里看到的往往是 ${变量名} 这种引用，而不是写死的值。
```

**另一种情况**：README 里只给了 `docker run` 命令，没有 Compose 文件。这时你可以自己把它翻译过来 —— 每个 `-p` 变成 `ports` 一行，每个 `-v` 变成 `volumes` 一行，每个 `-e` 变成 `environment` 一行。**第 40 课会专门练这件事。**

### 4.3 `${变量名}` 是什么意思

有些 Compose 文件里会看到这样的写法：

```yaml
environment:
  - DB_PASSWORD=${DB_PASSWORD}
```

这不是笔误。它的意思是「这个值从外部读」，通常来自同目录下的 `.env` 文件。

**这是一种更安全的做法**：Compose 文件本身可以公开，真实的值藏在 `.env` 里，而 `.env` 不提交到仓库。

**但要记住它的边界**：`.env` 只是把密码换了个地方放，**并没有加密**。它仍然需要你自己保证不泄露、不进公开仓库、不被备份到不安全的地方。

### 4.4 关于 `latest` 与固定版本

`image: example/notes` 不写标签时，等价于 `example/notes:latest`。

它的风险是：**你不知道下次拉取到的还是不是同一个东西。** 今天跑得好好的，明天重建可能就变了行为。

固定版本（如 `:1.0`）的好处是「可重复」—— 同一个描述，跑出来的东西是一样的。代价是升级需要你手动改版本号。

**两种做法没有绝对对错，但你必须知道自己在选哪一种**，以及它有没有把「版本变化」这件事告诉你。

## 5. 类比

把一份 Service 想象成**给一个租客准备的房间**：

- **image 是「租客是谁」**：来的是哪一位，带着什么本事。
- **ports 是「房门开在哪」**：从哪条走廊、哪个门牌号能找到他。
- **volumes 是「他的储物柜」**：行李放在楼里的柜子里，而不是放在他身上 —— 换人了，柜子里的东西还在。
- **environment 是「给他的入住须知」**：告诉他该怎么做事，比如「密码是这个」「用简单模式」。

这个类比能解释什么：

- **为什么删掉容器数据还在**：行李在储物柜（宿主机目录）里，不在租客身上。
- **为什么改了环境变量要重建**：入住须知是入住时交给他的，改须知就得重新办一次入住。
- **为什么端口很容易搞反**：`"8080:80"` 是「外面的门牌」在前、「房间里的门牌」在后。
- **为什么没有 volumes 就危险**：租客一走，他身上的东西就一起带走了。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：README 说要访问 `localhost:8080`，但你在 NAS 上**

`localhost` 指的是「运行这个程序的那台机器自己」。如果程序跑在 NAS 上，那 `localhost` 指的是 NAS，**不是你的电脑**。你要用的是 NAS 的局域网地址，比如 `192.168.1.10:8080`。

**这是一个非常常见的误解**：教程作者假设你在同一台机器上操作，而你在另一台设备上访问。

**场景二：文件里 ports 写的是 `"8080:80"`，我该访问哪个**

访问 **8080**，也就是冒号左边那个。右边是容器内部的端口，你在外面用不到 —— 除非你把左边也写成 80。

```text
"8080:80"  →  访问 设备地址:8080
"9000:80"  →  访问 设备地址:9000
"80:80"    →  访问 设备地址（默认就是 80，可不写）
```

**场景三：只有一个 `./data:/app/data`，够不够**

要看这个项目会往哪些目录写东西。有些项目除了主数据目录，还会往配置目录、缓存目录、上传目录写。**判断方法**：查 README 的「备份」章节 —— 它让你备份哪些目录，那些就是需要挂载的目录。只挂一个而漏了另一个，升级时可能丢掉一部分。

### 6.2 四个字段的排查对照表

| 字段 | 它决定什么 | 出问题时你会看到 |
|---|---|---|
| `image` | 用什么程序 | 拉取失败、镜像找不到、版本行为不符预期 |
| `ports` | 从哪访问 | 打不开、地址写错、和别的服务端口冲突 |
| `volumes` | 数据在哪 | 重启后数据消失、找不到文件、权限报错 |
| `environment` | 怎么配置 | 启动报错说变量缺失、用了不安全的默认值 |

**这张表的用法**：遇到问题先定位它属于哪一类，再看对应字段，比漫无目的地翻文件快得多。

### 6.3 一个值得养成的阅读顺序

```text
第 1 步  看 image          → 知道这是什么
第 2 步  看 ports          → 写下「我将访问 设备地址:____」
第 3 步  看 volumes        → 写下「我的数据会存在 ____」
第 4 步  看 environment    → 列出「我还缺 ____ 没填」
第 5 步  才开始动手执行
```

**前四步都是在纸上完成的。** 这是第 39 课要训练的「先预测、后验证」—— 如果先执行再看结果，你只是碰巧跑通了一次，下次换个项目还是不会读。

## 7. 常见误区

### 误区一：`"8080:80"` 应该反过来读

读反是最常见的错误。规则是固定的：**冒号左边是宿主机（你访问用的），右边是容器内部（程序自己的）。** 如果读反，你会去访问一个根本没开的端口，然后以为服务坏了。记住「左边是你敲的」。

### 误区二：有了 volumes 就万事大吉

`volumes` 只保证「容器重建时数据还在」，它**不保证数据不会丢**。硬盘坏了、误删了目录、勒索软件加密了文件，`volumes` 都挡不住。数据安全还需要**另外的备份**，而且备份要放在不同的地方 —— 这是 Week 3 就学过的原则。

### 误区三：`latest` 就是「最新的，所以最好」

`latest` 只是一个标签名，不一定代表最新，也**不保证稳定**。它的真正问题是「不可重复」：同一条描述，不同时间拉取可能得到不同的东西。想要可控，就固定版本号。

### 误区四：`.env` 文件是加密的，所以密码放里面就安全了

不加密。`.env` 只是纯文本文件，把密码从 Compose 文件里挪到了另一个地方。**它的价值在于「方便不把密码提交到仓库」，而不是「保护密码」。** 文件权限、备份策略、谁能读到这台机器，仍然是你要自己负责的事。

### 误区五：环境变量没填也能跑，说明不重要

不一定。有些程序在缺变量时会**退化到一个默认值**，比如默认管理员密码、默认密钥、默认开放所有权限。它不报错，但那个默认值往往早就在文档里公开了。**「能跑起来」不等于「配置正确」** —— 遇到必填项，一律替换成你自己的值。
