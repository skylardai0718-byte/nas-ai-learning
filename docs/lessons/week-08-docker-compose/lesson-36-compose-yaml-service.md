# 第三十六课：Compose、YAML 与 Service

> 本课的一句话结论：**Compose 文件是把一长串 docker run 参数写成一份有结构的清单；YAML 是这份清单的书写格式，Service 是清单里的一个条目 —— 一个条目描述一个容器。**

## 1. 今天学习什么

今天要掌握 3 个概念：

1. **Docker Compose（容器编排工具）**：把容器的配置写成一份文件，而不是敲一长串命令。
2. **YAML（一种配置书写格式）**：这份文件的书写规则，靠缩进表达层级。
3. **Service（服务）**：Compose 文件里的一个条目，描述「一个容器该怎么运行」。

你今天要建立的核心结构是：

```text
compose.yaml
└── services:              ← 顶层，列出这个项目要跑的所有容器
    ├── notes:             ← 一个 Service（描述一个容器）
    │   ├── image          ← 用哪个镜像
    │   ├── ports          ← 从哪个门进去
    │   └── volumes        ← 数据放在哪
    └── database:          ← 另一个 Service（描述另一个容器）
```

以及一句话的分工：

```text
Compose  →  一份清单（写下来，可重复使用）
YAML     →  清单的排版规则（怎么写字）
Service  →  清单里的一行「一个容器」
```

## 2. 为什么要学

上周你学了 Docker，也见过那种很长的命令：一堆参数用反斜杠接着，敲错一个字就得重来。

**Compose 要解决的问题就是：命令太长了，写在纸上抄不下来，也讲不清楚。**

不理解 Compose 会遇到这些问题：

- 为什么别人的教程给的不是一条命令，而是一个 `compose.yaml` 文件？
- 为什么这个文件里通篇没有出现「运行」两个字，服务却真的跑起来了？
- 为什么它看起来只是配置，却有人说它其实是「命令的另一种写法」？
- 为什么 YAML 里多一个空格、少一个空格，结果就完全不同？
- 为什么一个文件里可以同时定义好几个容器，它们又是怎么被区分开的？

**这也是本周后面四天的基础。** 今天的三个词是词汇表，接下来三天分别讲「字段怎么读」「容器怎么管」「怎么真的跑一次」。

## 3. 小白解释

### 3.1 从一条长命令到一份清单

假设你要启动一个容器，用命令大概是这样的（示意，不是让你现在敲）：

```text
docker run -d \
  --name notes \
  -p 8080:80 \
  -v ./data:/app/data \
  -e APP_MODE=simple \
  example/notes:1.0
```

这条命令里有五件事：叫什么名字、从哪个门进、数据放哪里、有什么设置、用哪个镜像。

问题在于：**这条命令只活在命令历史里。** 关掉窗口、换一台机器、半年后再看，你很难说清当时到底配了什么。而且它只能启动一个容器。

Compose 的做法是：**把这些参数一条条写进一个文件。**

```yaml
services:
  notes:
    image: example/notes:1.0
    ports:
      - "8080:80"
    volumes:
      - ./data:/app/data
    environment:
      - APP_MODE=simple
```

同一件事，从「一行行的命令」变成了「一份看得见、存得住、能给别人看的清单」。

> 注意：这里的 `example/notes:1.0` 是教学用的虚构镜像名。真实的 Compose 文件里会写项目自己的镜像名。

### 3.2 YAML：靠缩进表达层级

`compose.yaml` 这种文件用的格式叫 **YAML**。

YAML 的规则很少，但有一条最重要：**用缩进表示「谁属于谁」。**

```text
services:            ← 顶层
  notes:             ← 缩进两格，说明它属于 services
    image: ...       ← 再缩进两格，说明它属于 notes
```

换句话说：

```text
缩进多  →  层级更深，是上面的「子项」
缩进同  →  是同一层的兄弟
```

**YAML 不看你写了几行，只看你缩进了多少。** 这就是为什么它对空格敏感 —— 空格在这里不是装饰，是语法本身。

### 3.3 Service：一个容器的一张说明书

在 Compose 文件里，`services:` 下面列出的每一项，就是一个 **Service**。

一个 Service 不是什么抽象的东西 —— **它就是「一个容器该怎么运行」的完整说明。**

```text
一个 Service  =  一个容器的说明书
  用哪个镜像？
  从哪个端口进？
  数据放哪？
  有哪些设置？
```

如果这个项目需要两个容器（比如一个网页、一个数据库），那就在 `services:` 下面写两个条目。**Compose 用 Service 的名字来区分它们**，而不是用容器 ID。

## 4. 技术解释

### 4.1 Compose 做了什么、没做什么

Docker Compose 是一个工具，它读取 `compose.yaml`，然后根据里面的描述去创建、启动、停止容器。

它做的事：

- 把文件里的描述翻译成对 Docker 的操作（本质上还是那套 `docker run` / `docker stop`）。
- 管理一个项目里的多个容器，让它们可以一起启动、一起停止。
- 记住这个项目包含哪些容器，方便你统一操作。

它**不**做的事（这一点常被误会）：

- 它**不会**自己变出镜像。文件里写 `image: xxx`，这个镜像仍然需要能拉取到或本地已有。
- 它**不会**替你检查配置是否合理。端口写错、路径写错，它不会拦你。
- 它**不会**在你保存文件的那一刻自动生效。文件只是描述，需要有指令去执行它。

**记住这条**：`compose.yaml` 是一份说明，不是一个运行中的程序。

### 4.2 YAML 的几条硬规则

读别人的 YAML 文件，只需要注意这几条：

| 规则 | 说明 |
|---|---|
| 缩进用空格 | 通常两格。**不能用 Tab**，混用会直接报错 |
| `键: 值` | 冒号后面要有一个空格，如 `image: example/notes:1.0` |
| `- ` 开列表 | 短横线加空格表示列表项，如 `- "8080:80"` |
| `#` 是注释 | 这一行后面的内容会被忽略 |
| 大小写敏感 | `Image` 和 `image` 是两个不同的东西 |
| 引号可省略 | 但像 `"8080:80"` 这种带冒号的，通常加上更安全 |

你会发现，读 YAML 其实不需要「读懂语法」，只需要**看缩进判断层级**。第 37 课会正式带你逐段读一份完整文件。

### 4.3 services 的结构

一份最小的 Compose 文件，骨架长这样：

```yaml
services:
  服务名:
    字段: 值
```

- `services:` 是顶层字段，**它下面列出这个项目所有的容器**。
- `服务名` 是你自己起的名字（比如 `notes`、`db`），用于在文件内部互相引用。
- `字段` 才是真正描述「怎么运行」的部分。

一个文件里可以有多个服务：

```yaml
services:
  web:
    image: example/web:1.0
  cache:
    image: example/cache:2.1
```

**它们会被当作同一个项目下的一组成员**，可以一起启动、一起停止。这正是 Compose 比单条命令更方便的地方。

### 4.4 文件名与版本

Compose 文件的常见名字有 `compose.yaml`、`compose.yml`、`docker-compose.yml`。

早年 Compose 文件必须写一行 `version: "3"` 表示格式版本。**现在这个字段已经不再需要，写了反而会提示过时。** 旧教程里看到它，知道那是历史遗留即可，不必照抄。

**你不需要记住哪个名字才对** —— 真正需要知道的是：这个文件放在项目目录里，里面的内容决定这个项目跑什么。

## 5. 类比

把 Compose 想象成一份**装修施工单**：

- **Compose 文件本身，是那张施工单**：写清楚了要装什么、怎么装。
- **YAML 是这张单子的排版规则**：哪个项目属于哪个房间，靠缩进对齐来体现。写串行了，工头就理解错。
- **Service 是单子上的一个施工项**：比如「厨房」是一大项，下面写着用什么材料（镜像）、水从哪进（端口）、柜子放哪（数据目录）。
- **施工单不等于房子**：单子写得再漂亮，房子也不会自己盖起来 —— 得有人拿着单子去施工（执行指令）。

这个类比能解释什么：

- **为什么一份文件能管多个容器**：一份施工单当然可以同时包含厨房、卫生间、客厅的活。
- **为什么缩进错了会出问题**：把厨房的项写到客厅下面，工头就会做错。
- **为什么「文件写好了」不等于「服务跑起来了」**：施工单只是纸，施工是另一件事。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：教程给的是 compose.yaml，不是命令，怎么办**

这说明作者希望你用 Compose 的方式部署。你需要做的是：把文件内容保存成 `compose.yaml`，放进一个专门的项目目录（比如 `~/notes-app/`），再通过 NAS 上提供的 Compose 界面或管理工具去执行它。

**注意**：Compose 文件通常和它的数据目录放在一起，这样备份和迁移时是一个整体。

**场景二：文件里有两个服务，但它们看起来完全独立**

这是正常的。多个 Service 可以各自独立，也可以互相依赖（比如网页需要连数据库）。它们被写在同一个文件里，只说明**它们属于同一个项目**，不代表它们必须一样。

**场景三：改完文件，服务没变**

因为文件只是描述，改动不会自动生效。**文件修改后需要重新执行一次「应用」的动作**（不同 NAS 系统的说法不同），服务才会按新描述重建。这条在第 38 课会展开。

### 6.2 Compose 文件和命令的对照

| 你在文件里看到的 | 它对应的意义 |
|---|---|
| `services:` | 这个项目要跑哪些容器 |
| `服务名` | 这个容器的名字，文件内部用它互相引用 |
| `image` | 用哪个镜像启动 |
| `ports` | 从外面哪个门能进去 |
| `volumes` | 数据存在宿主机哪里 |
| `environment` | 启动时传给容器的设置 |

**读文件时，先在脑子里把这六个位置对上号**，剩下的细节就好读了。

### 6.3 一个需要养成的习惯

拿到任何一份 Compose 文件，先做三件事：

```text
1. 数一数 services 下面有几个条目   → 知道这个项目有几个容器
2. 看每个条目的 image              → 知道它们分别是什么
3. 看 ports 和 volumes             → 知道从哪进、数据在哪
```

**这三步不需要理解全部字段，就能读懂一个项目的大概。** 第 37 课会更系统地做这件事。

## 7. 常见误区

### 误区一：Compose 是另一套东西，和 docker 命令没关系

不是。Compose 本质上是在**替你生成和执行 docker 命令**。文件里写的 `ports`、`volumes`，和命令里的 `-p`、`-v` 是一一对应的。学会 Compose 不会让你之前的 Docker 知识作废，反而是同一套概念换了个写法。

### 误区二：只要写进文件，服务就会跑起来

反了。**文件是描述，不是运行状态。** 保存 `compose.yaml` 不会让任何容器启动，你需要一个明确的「执行」动作。把文件当成一份还没送出去的施工单。

### 误区三：一个 Service 等于一个镜像

不完全是。**Service 是「一个容器该怎么运行」的说明，镜像是其中的一个字段。** 同一个镜像可以被两个不同的 Service 使用，配置不同，跑出来的就是两个不同的容器。

### 误区四：YAML 的缩进只是为了让文件好看

不是。**缩进在 YAML 里就是语法。** 少缩一格，某个字段可能就从「属于这个服务」变成「属于 services 顶层」，含义完全不同，甚至直接报错。它不像写文章那样可以随意调整排版。

### 误区五：学会写 Compose 就等于会部署了

还差得远。**Compose 只描述「容器怎么跑」，它不管：** 这个服务该不该暴露到公网、数据有没有备份、升级时会不会丢数据、密码放在哪里才安全。这些是部署真正要判断的事，也是本周后几天要讨论的内容。
