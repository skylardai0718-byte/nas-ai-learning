# 第四十课：Compose 综合题

> 本课的一句话结论：**Compose 的能力最终体现在「补齐」而不是「背诵」上 —— 给你一份缺字段的模板和一段说明，你能把 image、ports、volumes、environment 填对，就算真正读懂了这一周。**

## 1. 今天学习什么

今天没有新概念。要做的是把这一周的四件事合起来用：

1. **结构**：认出 `services:` 下面的条目和层级。
2. **字段**：读出 `image`、`ports`、`volumes`、`environment` 各自说明什么。
3. **生命周期**：知道改了字段之后要怎么才能生效、数据会不会留下。
4. **判断**：能说出这份文件「没有告诉你什么」，以及它有没有安全上的疏忽。

今天的核心结构：

```text
给你三样东西
├── 一份不完整的 compose.yaml 模板（缺字段）
├── 一段 README 摘录（描述需求）
└── 你的任务：补齐四个字段，并说明理由

读出四件事
├── image       用哪个
├── ports       从哪进
├── volumes     数据在哪
└── environment 缺什么
```

以及综合题的固定动作：

```text
第 1 步  读需求，划出关键词
第 2 步  先填，再对照
第 3 步  逐条说出「为什么填这个」
第 4 步  指出「这份文件没告诉你什么」
```

## 2. 为什么要学

前四天分别是「认词」「读字段」「看变化」「做一次」。今天要把它们合成一件事：**在没有现成答案的情况下，补齐一份文件。**

**因为真实场景里，你拿到的往往不是完整的文件。** 更多时候是一份模板、一段 README、或者别人聊天时贴的半截配置。

不理解综合应用会遇到这些问题：

- 为什么同样一个服务，教程里的写法和我看到的不太一样？
- 为什么 README 只说了「访问 8080」，却没告诉我数据该挂哪？
- 为什么我需要自己判断「哪些字段可以照抄、哪些必须改」？
- 为什么有些文件看起来能跑，但把风险留给了你？
- 为什么说「补齐字段」比「背诵字段」更能说明你读懂了？

**这也是本周的收尾**：读 Compose 文件的终点，不是记住所有字段名，而是能对着需求把该有的字段补出来，并说清理由。

## 3. 小白解释

### 3.1 「补齐」是一种什么能力

做填空题和做选择题的差别：

```text
选择题  →  别人已经想好了，你只是挑一个
填空题  →  你得自己知道要填什么，以及为什么填它
```

**Compose 综合题是填空题**：给你一段描述，你来决定 `image` 写什么、`ports` 怎么写、`volumes` 挂在哪、`environment` 缺什么。

这就是「读懂」和「眼熟」的分界线。

### 3.2 先读需求，划出关键词

这是最重要的一步。**Compose 的字段，几乎都能在需求描述里找到对应的句子。**

```text
「用某个版本的服务」        →  image
「通过 8xxx 端口访问」      →  ports
「数据要保存下来」          →  volumes
「需要设置一个初始密码」    →  environment
```

**如果你读完一段需求，说不清它对应哪个字段，说明这个字段你还没真正理解。** 这一步不需要动手，只要拿笔画线。

### 3.3 补齐之后一定要做的一件事

在任何一份真实的 Compose 文件上，都要问这一句：

> **这份文件没有告诉你什么？**

因为 Compose 文件只描述「容器怎么跑」，它**不会**回答：

```text
这个服务该不该暴露到公网？
数据谁来备份？备份放在哪？
密码存在这里安全吗？
升级的时候会不会丢数据？
```

**能主动说出这些空缺，是本周真正的能力。** 只会读字段的人，看到文件就以为信息完整了。

## 4. 技术解释

### 4.1 练习：从需求补齐字段

下面是模板和需求。**先自己填，再看后面的参考答案。**

**需求描述**（README 摘录）：

```text
这是一个内部使用的书签服务，只在家庭局域网里使用。
- 使用 example/bookmarks 这个程序，版本 2.3
- 通过 8090 端口访问
- 数据必须保存下来，放在项目目录下的 data/ 里，容器内的位置是 /app/data
- 有一个必填的设置：访问口令，变量名是 ACCESS_TOKEN
```

**模板**（`compose.yaml`）：

```yaml
services:
  bookmarks:
    image:            # ← 填这里
    ports:            # ← 填这里
    volumes:          # ← 填这里
    environment:      # ← 填这里
```

**参考答案**：

```yaml
services:
  bookmarks:
    image: example/bookmarks:2.3
    ports:
      - "8090:8090"
    volumes:
      - ./data:/app/data
    environment:
      - ACCESS_TOKEN=CHANGE_ME
```

**逐条说明为什么这样填**：

| 字段 | 填了什么 | 依据 |
|---|---|---|
| `image` | `example/bookmarks:2.3` | 需求写明了程序名和版本；**版本要固定，不省标签** |
| `ports` | `"8090:8090"` | 需求说「通过 8090 访问」，所以冒号左边是 8090 |
| `volumes` | `./data:/app/data` | 左边是宿主机路径（项目目录下），右边是容器内路径（需求给出） |
| `environment` | `ACCESS_TOKEN=CHANGE_ME` | 必填项不能空着，但**值用占位符，不写真值** |

**关于 `ports` 值得多解释一句**：需求只说「通过 8090 访问」，没说容器内部是哪个端口。参考答案里写成了 `"8090:8090"`，这是一个常见做法 —— 内外一致，读起来省事。但**这个假设是有风险的**：如果程序内部监听的其实是 80，那右边的 8090 就写错了。

**正确的做法是**：这类不确定的地方，要去查这个程序的文档，或者先按最可能的值试一次，再看日志确认。**「猜一个看起来合理的值」和「知道自己在猜」，是两回事。**

### 4.2 练习：从 docker run 翻译成 Compose

有些项目的 README 只给命令，不给 Compose 文件。翻译规则是固定的：

```text
--name notes        →  服务名（services 下面那一行的键）
-p 8080:80          →  ports 里的一行
-v ./data:/app/data →  volumes 里的一行
-e APP_MODE=simple  →  environment 里的一行
镜像名放最后         →  image
```

原命令：

```text
docker run -d \
  --name notes \
  -p 8080:80 \
  -v ./data:/app/data \
  -e APP_MODE=simple \
  example/notes:1.0
```

翻译结果：

```yaml
services:
  notes:
    image: example/notes:1.0
    ports:
      - "8080:80"
    volumes:
      - ./data:/app/data
    environment:
      - APP_MODE=simple
```

**注意 `-d`（后台运行）没有出现在结果里** —— 因为 Compose 默认就是让服务在后台运行，不需要额外指定。**这类「命令里有、文件里没有」的项，正是翻译时容易困惑的地方**：它不是漏了，而是 Compose 已经默认这么做了。

### 4.3 练习：找出这份文件的问题

下面这份文件有三处问题。**先自己找，再看答案。**

```yaml
services:
  myapp:
    image: example/myapp
    ports:
      - "8080:80"
    volumes:
      - ./data:/app/data
    environment:
      - DB_PASSWORD=hunter2
    restart: unless-stopped
```

**问题一：镜像没有固定版本。** `example/myapp` 没有写标签，等于 `latest`。这意味着不同时间拉取可能得到不同的东西 —— 同一条描述，跑出来的结果不可重复。

**问题二：真实密码写在了文件里。** `DB_PASSWORD=hunter2` 是一个具体的值，不是占位符。这类文件一旦被提交到公开仓库或贴进求助帖，密码就等于公开了。**应该写成 `DB_PASSWORD=CHANGE_ME`，把真实值放到不提交的 `.env` 里。**

**问题三：这份文件没有说明服务是否对公网开放。** 这一点不算文件本身的错误 —— Compose 文件本来就不负责这件事。但**如果你的部署把这个端口转发到了公网，那就完全是另一回事了**。任何一份文件到手，都要自己回答这个问题，而不是等它告诉你。

## 5. 类比

把这一周想象成**学会看一份装修施工单，并且能自己补上缺的那几项**：

- **Day 1 是认识「这是张施工单」** —— 知道它是描述，不是房子本身。
- **Day 2 是认字** —— 材料（image）、门（ports）、储物间（volumes）、须知（environment）。
- **Day 3 是知道施工过程** —— 拆了重装时，储物间的东西还在。
- **Day 4 是自己照着单子做一遍**，并先说出「东西应该放哪」，再去看。
- **Day 5 是别人给你一张缺项的单子，你来补齐** —— 这才是真正会看单子的标志。

这个类比能解释什么：

- **为什么补齐比背诵重要**：会背材料名称的人，不等于能照着需求开出一张完整的单子。
- **为什么「单子没写」不等于「不用管」**：施工单不会写「这栋楼该不该对外开放」，但这件事必须有人决定。
- **为什么猜要标出来**：单子上有一项你没把握，写「待确认」比随便填一个数字安全得多。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：模板里的字段我不确定，能不能先随便填**

不行。**不确定的字段应该先查文档或去项目讨论区找，而不是填一个看起来像的值。** 端口填错会导致打不开，路径填错会导致数据写到了你找不到的地方 —— 后者更麻烦，因为你可能几个月后才发现。

**场景二：README 的说明和 Compose 文件不一致**

以 Compose 文件为准，但要**核对清楚为什么不一致**。常见原因是：README 没跟上新版本、或者作者用了别人的配置片段。**遇到不一致时，把它当成一个需要解决的问题，而不是随便挑一个**。

**场景三：拿到一份文件，怎么判断它有没有安全上的疏忽**

按这个顺序看：

```text
1. environment 里有没有写死的真实密码/令牌？
2. image 有没有固定版本？
3. volumes 挂载的目录，权限是不是过宽？
4. 这个服务有没有必要对公网开放？
```

**第 4 条是 Compose 文件回答不了的**，只能由你根据部署环境来判断。

### 6.2 本周的字段速查表

| 字段 | 回答的问题 | 填错会怎样 | 文件里通常不会告诉你 |
|---|---|---|---|
| `image` | 用什么 | 拉不到、行为不符预期 | 版本会不会变化、是否值得信任 |
| `ports` | 从哪进 | 打不开、端口冲突 | 这个服务该不该对公网开放 |
| `volumes` | 数据在哪 | 数据丢失或找不到 | 谁来备份、多久备份一次 |
| `environment` | 缺什么 | 启动失败或用了不安全默认值 | 真实凭据该放在哪 |

**最后一列是这一周最想让你记住的。** 前四列是读文件的能力，最后一列是判断部署是否可靠的能力。

### 6.3 完成本周的复述

试着不看笔记，口头讲两分钟，把这个流程走一遍：

```text
① 我拿到一份 Compose 文件，我先看 services 下面有几个条目
② 对每个条目，我读 image 知道它是什么
③ 我读 ports，说出访问地址是「设备地址:端口」
④ 我读 volumes，说出数据存在宿主机上的哪个目录
⑤ 我读 environment，列出还缺哪些必填项
⑥ 我指出这份文件没有告诉我的事：备份、公网暴露、凭据存放
⑦ 我知道改了字段之后需要重新应用才会生效，且数据要放在 volumes 里
```

**能顺畅讲完这七句，本周就算通过。**

## 7. 常见误区

### 误区一：模板填空只是记字段名

不是。**填空考的是「从需求推出字段」的判断力。** 字段名只是词汇，真正要练的是：看到「数据要保存下来」就知道该写 `volumes`，并且知道左右两边分别是什么。

### 误区二：不确定的字段先随便填一个，跑起来再说

「跑起来了」会掩盖「填错了」。端口填错会立刻暴露，但**路径填错往往很久之后才暴露** —— 直到你要备份或迁移时，才发现数据根本不在你以为的地方。不确定就标出来去查。

### 误区三：Compose 文件没写密码，就说明这个部署是安全的

不是。**文件里没有密码，只说明密码不在这个文件里。** 它可能在 `.env`、可能在别的地方，也可能这个服务本身就没有认证。**「没写」和「安全」是两件事。**

### 误区四：字段填齐了，部署就完整了

字段齐了只说明「容器能按描述跑起来」。**备份、升级策略、是否对公网开放、凭据怎么保管**，这些都不在这份文件里，但少了任何一项，部署都算不上可靠。

### 误区五：学会 Compose 就等于学会部署

Compose 是「描述一个容器」的工具，覆盖的是部署里最机械的那部分。**需要判断的部分 —— 该不该做、风险在哪、出问题怎么恢复 —— 它一点都帮不上忙。** 这一周学的其实不是怎么填字段，而是怎么问出文件没回答的那些问题。
