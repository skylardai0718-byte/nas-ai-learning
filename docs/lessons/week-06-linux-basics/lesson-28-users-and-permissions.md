# 第二十八课：用户、root 与权限

> 本课的一句话结论：**Linux 从设计上就假设一台机器上有多个用户，所以每个人只得到自己该有的权限；root 是例外 —— 它几乎没有限制，也因此几乎没有保护，正确做法是平时用普通用户、需要时用 sudo 临时借一次权限。**

## 1. 今天学习什么

今天要掌握 4 个概念和 3 条命令：

1. **用户（User）**：一个身份，带着一套权限。
2. **root**：超级用户，几乎不受限制。
3. **sudo**：临时以更高权限执行一条命令，而不是切换身份。
4. **权限（Permission）**：谁可以对哪个文件做什么。
5. 三条自查命令：**`pwd`**、**`ls`**、**`cd`**。

你今天要建立的核心结构是：

```text
User（我是谁）
  └── Permission（我能对什么做什么）
        └── root（超级用户：什么都能做）
              └── sudo（临时借用一次 root 权限）
```

以及操作前的固定三问：

```text
pwd  →  我在哪？
ls   →  这里有什么？
cd   →  我要去哪里？
```

## 2. 为什么要学

这是本周最实用的一课。前面两天讲的是「那是什么系统」「怎么进去」，今天讲的是「**进去之后，你是谁，你能做什么**」。

绝大多数新手在 NAS 上犯的错误，都出在这一步。不学这个，你会遇到：

- 为什么有些命令报 `Permission denied`，明明命令本身是对的？
- 为什么教程里有的命令前面要加 `sudo`，有的不加？
- 为什么说「不要一直用 root」—— 既然 root 什么都能做，那不是更方便吗？
- 为什么我登录进去之后，连自己建的文件都不能改？
- 为什么 `sudo` 加了之后还是不行？

**关键的一条判断是：** 遇到权限报错时，第一反应不该是「加 sudo 试试」，而该是「**我在哪、我是谁、我要动的东西属于谁**」。这个顺序搞反了，`sudo` 不但解决不了问题，还会把你带进更危险的地方。

## 3. 小白解释

### 3.1 为什么一台机器要有「用户」

想象一栋合租的房子。厨房是共用的，但每个人的房间有自己的钥匙。

```text
共用的部分  →  大家都能进（系统公共文件）
你的房间    →  只有你能进（你的个人文件）
房东        →  哪里都能进（root）
```

**Linux 从第一天就是这么设计的。** 它不是「先有一台个人电脑，后来加了多用户功能」，而是**天生就是一台可以被很多人同时使用的机器**。哪怕这台机器只有你一个人用，这个结构也还在 —— 因为系统自己也需要一些「专用身份」来运行不同的服务。

**为什么要有这个结构？** 最直接的答案：**防止一个人（或一个程序）出错时，影响到其他人和整个系统。** 如果没有这层隔离，任何一个程序出问题都可能让整台机器完蛋。

### 3.2 root 是什么

root 是那个「房东」。它可以：

```text
读、改、删任何人的文件
安装和卸载系统级软件
改网络设置、改系统配置
启动和停止任何服务
```

**听起来很爽，这就是问题所在。**

root 的危险不是因为它坏，而是因为**它没有安全网**：

```text
普通用户想删系统文件
  →  系统拦住：「你没有这个权限」
  →  你发现问题了，停手

root 想删系统文件
  →  系统照做
  →  没有提示、没有确认、无法撤销
```

**一次手误就够了。** 在普通用户下，系统的拒绝本身就是一道护栏；用了 root，这道护栏被你自己拆掉了。

### 3.3 sudo 是什么

新手常以为 sudo 是「变成 root」。更准确的描述是：

```text
sudo  →  对「这一条命令」，临时以更高权限执行
       执行完就结束，你还是原来的你
```

区别在这里：

```text
一直用 root 登录        →  从头到尾都是满权限，每一次敲键盘都在放大风险
普通用户 + 需要时 sudo  →  权限只在这条命令上放大一次
```

**这个区别不是形式主义。** 它把「什么时候需要权限」变成一个需要你有意识做出的动作 —— 而不是默认状态。

但 sudo 有个必须讲清的边界：

```text
sudo 做的事：把权限放大
sudo 不做的事：判断这件事该不该做
```

**它不会帮你检查路径对不对、文件名有没有打错。** 加了 sudo，一条写错的删除命令破坏力只会更大，而不会更小。

### 3.4 权限：谁可以对什么做什么

权限回答的是三个问题：

```text
谁？   →  文件的主人、同组的人、其他人
做什么？→  读、写、执行
```

最常见的三种情形：

```text
你能读能写  →  你自己的文件
你能读不能写 →  系统提供的公共文件（你不该改它们）
你什么都做不了 →  别人的私人文件（或者系统保护的文件）
```

**当你遇到 `Permission denied` 时，就是这三条里的一条被触发了。** 接下来的任务不是「强行突破」，而是**判断是哪一条、为什么**。

### 3.5 三条自查命令

这三条命令简单到容易被忽略，但它们是终端操作里最重要的习惯：

```text
pwd   →  print working directory：我现在在哪个目录
ls    →  list：这个目录里有什么
cd    →  change directory：切换到另一个目录
```

**为什么它们这么重要？** 因为终端里最危险的事情是「你以为你在一个地方，实际上你在另一个地方」。

```text
你以为：在练习目录里，删掉一个测试文件
实际上：在别的位置，删掉了一个真文件
```

`pwd` 和 `ls` 就是用来消除这个误会的。**在敲任何会改动东西的命令之前，先跑一遍这两条** —— 这个习惯能避免绝大多数事故。

## 4. 技术解释

### 4.1 用户与用户组

每个 Linux 用户都有三个关键属性：

```text
用户名（username）  →  登录时用的名字
用户 ID（UID）      →  系统内部真正用来识别的数字
所属用户组（group） →  权限可以按组分配，方便批量管理
```

**为什么要用数字 ID？** 因为名字是给人看的，系统内部用数字识别更直接。比如 root 的 UID 固定是 `0` —— 在 Linux 里，「是不是 root」本质上是「UID 是不是 0」。

**用户组的意义：** 如果有五个人都需要访问同一批文件，逐个授权很麻烦。把他们放进同一个组，一次授权就够。

另外还有一类特殊用户：**系统用户**。它们不对应真人，而是给每个服务用的专用身份。这样即使某个服务被攻破，攻击者拿到的也只是那个服务的有限权限，而不是整台机器。

### 4.2 权限的三组与三种

一个文件的权限分三组，每组三种：

```text
三组受众：
  拥有者（Owner）  →  文件的主人
  组（Group）      →  主人所在的组
  其他人（Other）  →  其余所有用户

三种权限：
  读（Read）       →  能看内容
  写（Write）      →  能改内容
  执行（Execute）  →  能把它当作程序运行
```

**执行权限为什么要单独存在？** 因为「能读一个文件」和「能运行它」是两件事。你可以读一段脚本的内容，但不一定被允许执行它。这个区分带来一个很重要的安全效果：**下载来的东西默认不能直接运行**，除非你明确给它执行权限。

### 4.3 权限是分层判定的

当你尝试操作一个文件时，系统大致是这样判断的：

```text
1. 你是这个文件的拥有者吗？  →  是：用「拥有者」这一组规则
2. 你在文件所属的组里吗？    →  是：用「组」这一组规则
3. 都不是                     →  用「其他人」这一组规则
                             ↓
              按对应规则判定：允许 / 拒绝
```

**关键点：判定是「从前往后、命中就停」。** 这就是为什么有时你会遇到「我明明是文件的主人，为什么还需要 sudo」—— 因为**目录的权限**可能挡住了你，而不是文件本身。

**这是一个容易被忽略的层次：** 要操作一个文件，你不仅要对该文件有权限，还要对**它所在的目录**有相应权限。目录的「执行」权限含义很特别 —— 它决定你能不能「穿过」这个目录。

### 4.4 Permission denied 的判断顺序

遇到这个报错，按顺序问自己：

```text
1. 我在哪？          →  pwd
2. 我要动的是什么？  →  ls 看这个目录
3. 我是谁？          →  当前登录的是哪个用户
4. 这个文件属于谁？  →  它的拥有者和权限是什么
5. 我是在改文件本身，还是在改它所在的目录？
   ↓
只有当答案确实是「我该有权限、且这确实是管理员的活」时，才考虑 sudo
```

**最常见的三种真实原因：**

```text
路径写错了       →  根本不是权限问题，是走错地方了
文件属于别人     →  你确实没权限，需要换身份或换做法
目录权限不够     →  文件本身没问题，是「进不去这个目录」
```

**这三种的处理方式完全不同。** 不加判断就加 sudo，等于用大炮打蚊子 —— 蚊子没打着，墙倒是塌了。

### 4.5 sudo 的工作原理

sudo 并不是「切换成 root 就不回来了」，它的机制是：

```text
1. 检查你的用户是否被授权使用 sudo
2. 要求你再次验证身份（通常是输入你自己的密码）
3. 只对这一条命令，以更高权限执行
4. 执行完，权限立即收回
```

**两个注意点：**

- **需要被授权。** 不是每个用户都能用 sudo。系统里有一份名单，只有名单上的用户才可以。这也意味着它本身就是一道有意的门槛。
- **要重新验证。** 这不是多此一举 —— 它确保「提权」这个动作是你本人在此刻有意做出的，而不是别人趁你离开电脑时顺手敲的。

**sudo 的边界：** 它只提升权限，不提供任何保护。加了 sudo 之后，命令依然是「你写什么就执行什么」，包括写错的部分。

## 5. 类比

把 Linux 的权限体系想象成**一栋写字楼的钥匙系统**：

- **普通用户是你的员工卡** —— 能刷开自己的办公室、公共走廊和会议室，但打不开财务室和机房。
- **root 是物业总钥匙** —— 整栋楼哪扇门都能开。拿着它当然方便，但**你也就失去了「门打不开」这个提醒**。平时你会因为「刷不开机房」而反应过来「我走错地方了」；拿着总钥匙，你只会径直走进去。
- **sudo 是临时借用总钥匙** —— 你去前台登记一下、说明要办什么事，前台把钥匙借你用一次，办完就还回去。**登记这个动作本身就是一道有意的确认。**
- **权限就是门上贴的说明** —— 谁能进、进去能干什么，写得清清楚楚。Permission denied 就是门上的锁告诉你「你不该进这里」。
- **pwd 和 ls 是抬头看门牌** —— 敲门之前先确认这是不是你要找的那扇门。

**这个类比能解释什么：**

- 为什么 root 危险 —— 不是因为它坏，而是因为它去掉了所有提醒你的信号。
- 为什么 sudo 比一直用 root 好 —— 它把「提权」变成了需要登记的有意识动作。
- 为什么 sudo 不保证安全 —— 前台只负责借钥匙，不负责判断你要办的事对不对。
- 为什么 pwd 和 ls 要养成习惯 —— 门牌看错了，钥匙再对也没用。

**类比也有边界：** 写字楼里前台会问你「你要办什么业务」并可能拒绝你；`sudo` 不做这种判断。它只检查「你有没有资格借」，不检查「你借了要干什么」。**这个判断只能由你自己做。**

## 6. NAS 实际场景

### 6.1 一条命令的权限旅程

```text
你敲下一条命令
  ↓
Shell 解析（用你的身份）
  ↓
检查：你的用户对该文件/目录有权限吗？
  ├── 有  →  执行
  └── 没有 →  Permission denied
              ↓
        此时你有两种选择：
          A. 停下来问「为什么」→ pwd / ls / 我是谁 / 这文件属于谁
          B. 直接加 sudo 再试一遍   ← 危险，很多时候问题根本不在这
```

**正确的默认选择是 A。** 只有在确认「这确实是我权限不够、且这件事确实需要管理员来做」之后，才走 B。

### 6.2 三个真实判断

**场景一：新登录 NAS，想删掉一个文件，报 Permission denied**

先别急着加 sudo，按顺序查：

```text
1. pwd        →  我到底在哪个目录？（很可能不是我以为的练习目录）
2. ls         →  这个文件真的在这么？
3. 这个文件是谁建的、属于谁？
4. 我想删的是文件本身，还是删不掉它所在的目录？
```

**三种可能的结果指向完全不同的处理：**

- 如果发现**路径根本不对** —— 这不是权限问题，是走错地方了，`cd` 到正确位置就行。
- 如果文件**属于别人** —— 你确实没权限，需要换一种做法（比如让文件主人处理）。
- 如果是**目录权限不够** —— 文件本身没问题，是「这个目录你进不去」。

**只有第三种里的某些情况，才真正需要 sudo。**

**场景二：为什么教程让我加 sudo，我不加也能跑**

因为教程作者的设备和你的环境可能不同：他的用户可能没有那个文件的权限，而你的有；或者教程写的是「系统级操作」，而你实际上是在自己的目录里操作类似的东西。

```text
加不加 sudo，取决于「这件事是不是在动系统级的东西」
而不是「这条命令看起来重不重要」
```

**判断方法：** 看这条命令操作的对象在哪 —— 自己的家目录里，通常不需要 sudo；系统目录里，多半需要。**但需要不等于应该做**，动系统目录之前先想清楚。

**场景三：为什么用 root 登录之后，什么都顺畅，反而更该警惕**

因为这正是 root 的问题：**所有的「不顺畅」其实都是系统在保护你。** 顺畅说明护栏全没了。

```text
用普通用户：出错被拦住  →  你还有机会发现
用 root：   出错直接执行 →  没有第二次机会
```

**这是一条容易被误解的判断：** 「顺畅」在这里不是效率高的表现，而是安全网消失的表现。

### 6.3 四者对照

| 概念 | 是什么 | 关键边界 |
|---|---|---|
| User | 一个身份，带着一套权限 | 不是「账号」那么简单，权限是跟着身份走的 |
| root | 超级用户，UID 为 0 | 不是「更高级的普通用户」，而是几乎没有限制 |
| sudo | 临时以更高权限执行一条命令 | 只提权，不判断对错 |
| Permission | 谁可以对什么做什么 | 分三组受众、三种动作，且目录权限也会拦人 |

**这张表最该记住的一行：** sudo 只提权，不判断。**它把决定权完整地留给了你。**

## 7. 常见误区

### 误区一：遇到 Permission denied 就加 sudo

这是本周最需要纠正的习惯。`Permission denied` 有三种常见原因：路径走错了、文件属于别人、目录权限不够 —— **其中只有一部分和「权限不够」有关，而且只有更小的一部分需要 sudo。** 不加判断地提权，等于关掉报警器去修火警。

### 误区二：root 只是权限更大的普通用户

不是。普通用户受到的各种限制，root 基本都不受。区别不只是「能做更多事」，而是**「犯错时没有东西拦着你」**。把 root 理解成「更厉害的普通用户」，会导致你低估它的风险 —— 它和普通用户之间是性质差异，不只是程度差异。

### 误区三：sudo 就是切换到 root

不准确。**sudo 是为单独一条命令临时提权，执行完就结束。** 它不是把你变成 root 然后一直待在 root 状态里。这个区别很关键：它让提权成为一个需要你主动重复做出的动作，而不是一种持续状态。

### 误区四：加了 sudo，命令就一定成功、也一定安全

两件事都不对。加了 sudo 之后：
- **不一定成功** —— 路径写错、命令本身不存在，问题依然存在；
- **不一定安全** —— 权限变大了，同样一条错误命令的破坏力只会更大。

sudo 放大的是**能力**，不是**正确性**。

### 误区五：pwd、ls 太简单，不用养成习惯

恰恰相反。终端里最危险的不是复杂命令，而是**在错误的位置敲了正确的命令**。`pwd` 和 `ls` 回答的是「我在哪、这里有什么」这两个最基础也最致命的问题。它们看起来简单，但能避免的事故远比你想象的多 —— **删东西之前先跑一遍，这个习惯比记住任何命令都值钱。**


今天只需要真正记住一句话：

> **权限体系是为了让每个人只做自己该做的事；root 去掉了这层保护，所以只应在必要时用 sudo 临时借用一次 —— 而遇到权限报错，第一件事是确认自己在哪、要动什么，而不是加 sudo。**
