# 第五十六课：LLM、工具与 Function Calling

> 本课的一句话结论：**模型只会输出文字，它「想调用工具」也只是输出一段结构化的文字；真正动手的是模型外面的那个程序 —— 风险不在模型里，在执行它的那段程序里。**

## 1. 今天学习什么

今天要掌握 3 个概念：

1. **LLM（大语言模型，Large Language Model）**：只做一件事 —— 根据输入生成接下来的文字。
2. **工具（Tools）**：模型可以「申请调用」的外部能力，比如读文件、查天气。
3. **Function Calling（函数调用）**：模型输出一段结构化的调用意图，交给外部程序去执行。

你今天要建立的核心结构是：

```text
用户提问
   ↓
LLM 输出文字（可能是答案，也可能是一段调用意图）
   ↓              ↓
直接回答      结构化调用意图  →  外部程序执行  →  结果回传
                                  ↑
                           真正动手的是这里
```

以及本周第一重要的一条区分：

```text
模型建议操作   →  一段文字，本身什么也没发生
系统真实执行   →  外面的程序真的动手了
```

## 2. 为什么要学

上周你知道了模型怎么在本机跑起来，也知道它回答的其实只是「接下来的文字」。

但你会发现，能聊天和能「做事」是两回事。不理解工具调用，会遇到这些问题：

- 为什么模型可以直接读取你 NAS 上的文件？
- 为什么它有时会说「我帮你查一下」，结果什么也没查？
- 为什么有的模型声称能操作浏览器、能发邮件？
- 为什么同一个模型，接上不同工具后能力差别那么大？
- 如果 Agent 把文件删了，到底是谁删的？

**最后一个问题最重要。** 如果分不清「建议」和「执行」，你会错误地以为风险在模型本身，
从而忽略了真正该管住的地方 —— 那段有权限的、真正动手的程序。

**这也是 Day 4 权限边界的前提。** 权限给谁？给那个执行程序，而不是给模型。

## 3. 小白解释

### 3.1 模型只会写字

先建立一条底线。**LLM 只做一件事：根据你给的内容，猜接下来最该出现的文字。**

它不能打开文件、不能上网、不能修改任何东西。它只是一个非常会写字的东西。

```text
输入：帮我看看 /volume1/docs/a.pdf 讲了什么
模型能做：输出一段文字
模型做不到：真的去打开那个文件
```

### 3.2 「工具」是把模型的申请变成现实

既然模型自己做不到，就给它配几个「外挂」——这就是**工具**。

工具就是一个个具体的能力，比如：

```text
read_file     读一个文件
list_files    列出目录里有什么
search_web    上网搜一下
```

模型不能直接使用它们。它能做的只是**申请**：

```text
模型输出：{ "tool": "read_file", "path": "/volume1/docs/a.pdf" }
```

注意，这只是一段文字。**一封信，不是一次行动。**

外面有一个程序收到这封信，它决定要不要照办，然后真的去读文件，再把内容交回给模型。

### 3.3 Function Calling 是「申请单」，不是「执行键」

上面那段「模型输出结构化申请」的动作，就叫 **Function Calling（函数调用）**。

这个中文译名容易误导 —— 听起来像是模型在执行函数，其实不是。它只是**填了一张申请单**：

```text
Function Calling 的全过程：

① 模型填申请单：{ tool: "read_file", path: "…" }
② 外部程序审单：这个工具存在吗？参数合法吗？允许吗？
③ 外部程序执行：真的去读文件
④ 结果交回模型：模型看着内容继续写答案
```

**「审单」这一步才是安全的关键** —— 因为只有这里能拒绝。

### 3.4 一次完整的问答长什么样

把你问 PDF 的整个过程连起来看：

```text
你：我那份 PDF 讲了什么？
         ↓
模型：我不认识这个文件，但我可以申请读取
      → { tool: "read_file", path: "/volume1/docs/a.pdf" }
         ↓
外部程序：工具存在、路径在允许范围内 → 执行 → 读到内容
         ↓
模型：（收到 PDF 全文）这份 PDF 讲的是 …
```

模型从头到尾**一次都没有碰过你的文件**。它只是申请、然后读结果。

## 4. 技术解释

### 4.1 LLM 的输出是 token 序列

LLM 生成的是 token（词元）序列，也就是一段文字。它没有任何「调用外部世界」的通道 ——
这一点在设计上就是如此。

**所以模型永远无法绕过外部程序去操作你的系统。** 它能做的只是输出一段特殊的文字，
而这段文字是否被理睬、被如何理解，完全取决于外面那个程序怎么写。

### 4.2 Function Calling 的机制

典型的流程分为几步：

1. **声明工具**：程序把「有哪些工具、各需要什么参数」告诉模型。
2. **模型选择**：模型判断这次要不要用工具、用哪个、参数填什么。
3. **模型输出调用意图**：以结构化的形式输出，通常包含工具名和参数。
4. **程序解析并执行**：程序解析这段意图，**自行决定**是否执行。
5. **结果回传**：执行结果作为新一轮输入交回模型，模型据此继续。

**关键点在第 4 步**：模型输出的是「意图」，程序执行的是「行为」。
中间那一道关卡，是设计上唯一能拦截的地方。

### 4.3 一次回答可能调用多次工具

模型可以连续申请多次：

```text
申请 list_files → 看到目录里有 3 个文件
申请 read_file  → 读第 1 个
申请 read_file  → 读第 2 个
→ 汇总，输出答案
```

这就是 Day 2 要讲的「循环」的雏形。**调用多少次，是由模型一轮一轮决定的** ——
这也意味着，如果没人限制，它可以一直申请下去。

### 4.4 工具的参数由模型填，因此可能填错

模型填参数时，靠的是「猜最合理的写法」。所以它可能：

- 路径拼错，读不到文件；
- 把参数写成了别的格式；
- 申请一个根本不存在的工具。

**这些都是模型的正常失败，不是系统故障。** 程序要能识别并拒绝非法申请。

### 4.5 谁有权限，谁承担责任

```text
模型      →  建议（无权限，无副作用）
外部程序  →  执行（有权限，有副作用）
```

因此安全设计的原则非常直接：**不要指望模型「不乱来」，要设计成「就算它乱来，也做不了坏事」。**
把权限收在程序这一侧，而不是寄希望于模型的自觉。

## 5. 类比

把整个过程想象成**公司里的「跑腿申请」**：

- **LLM 是一个只能说话的顾问**：它知识多、表达好，但它坐在会议室里，不能出这栋楼。
  它不能自己去档案室查文件。
- **工具是公司各部门的窗口**：档案室、财务、IT —— 每个窗口能办的事不一样。
- **Function Calling 是顾问写的一张申请单**：上面写着「请档案室调取编号 X 的文件」。
- **外部程序是档案室的管理员**：他拿到申请单，**有权决定批不批**。他会核对、会拒绝、
  也会在执行后把文件递回去。

**这个类比能解释什么？**

它会告诉你：顾问写了什么申请单，不等于事情就会发生。**决定权在管理员手里。**
如果管理员什么单子都批、任何柜子都开，那要担心的不是顾问说了什么，而是管理员的权限太大了。

这就是本周的核心：**管住管理员，而不是指望顾问自觉。**

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：模型说「我帮你查一下 NAS 上的文件」**

现实是：它此刻什么也没查，它只是输出了「申请调用 read_file」的文字。
**真正的查询发生在外部程序执行之后。** 如果程序没有真的执行，用户会看到一段「我查了」的话，
但实际什么也没发生 —— 这也是「模型在说谎」的常见来源之一：它描述了意图，却没被执行。

**场景二：模型申请删除一个文件**

```text
模型输出：{ "tool": "delete_file", "path": "/volume1/docs/a.pdf" }
```

**这一刻文件还在。** 是否被删，取决于外部程序有没有这个工具、有没有检查参数、
有没有真的照办。所以设计时要问的不是「模型会不会申请删除」，而是
**「程序里到底有没有删除这个工具」** —— 没有这个工具，申请单就批不了。

**场景三：为什么同一个模型接不同工具后差别巨大**

因为模型的能力上限由「你能让它调用什么」决定。接上搜索工具，它就能查资料；
接上文件工具，它就能读文档。**它本身没变，是外面的能力变了。**

### 6.2 三层结构对照

| 层 | 是什么 | 有没有副作用 | 谁来管 |
|---|---|---|---|
| 模型 | 输出文字 | 没有 | 无法控制它的输出 |
| 调用意图（Function Calling） | 一段结构化文字 | 没有 | 程序负责校验 |
| 外部程序 | 真正执行动作 | **有** | **你 —— 权限就收在这里** |

**这张表要记牢**：唯一有副作用的是最底下一层，也正因为如此，权限和风险都收在这一层。

### 6.3 给 NAS 场景的一句话提醒

```text
模型不碰你的文件，碰你文件的是你让它调用的程序。
所以少给一个工具，就少一份风险。
```

## 7. 常见误区

### 误区一：模型可以自己执行操作

不对，而且这是本周最需要纠正的一条。模型只能输出文字。它输出的「调用意图」要由外部程序
解析并执行才会生效。**模型从来不会自己动手。**

### 误区二：Function Calling 就是模型在调用函数

名字有误导性。Function Calling 是**模型输出一段结构化的调用意图**，而不是模型执行了函数。
执行发生在模型之外，由程序完成。**分清这一点，才能理解风险到底在哪里。**

### 误区三：只要模型够强，Agent 就很安全

安全不取决于模型的强弱，而取决于**外部程序给了它多少权限**。
一个很强的模型接上删除工具、又能访问全部目录，风险比一个普通的模型接只读工具大得多。
**安全是权限问题，不是能力问题。**

### 误区四：模型说「我做到了」就是真的做到了

不一定。模型可能只是描述了意图，而程序并没有执行 —— 或者执行失败了但模型没意识到。
判断「有没有真的做」，要看外部程序的实际结果，而不是模型的说法。

### 误区五：给模型更多工具总是更好

不是。工具越多，可被调用的动作越多，出错和越权的面就越大。
**只加真正需要的工具**，是本周最小权限原则的第一条应用。
