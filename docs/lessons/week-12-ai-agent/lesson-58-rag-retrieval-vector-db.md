# 第五十八课：RAG 与向量数据库

> 本课的一句话结论：**RAG 不指望模型记住你的私有资料，而是在回答之前先把相关资料找出来、递到它面前 —— 检索质量决定回答的上限，它不是「让模型变聪明」，而是「每次都给它递小抄」。**

## 1. 今天学习什么

今天要掌握 3 个概念：

1. **RAG（检索增强生成，Retrieval-Augmented Generation）**：先找资料，再让模型回答。
2. **检索（Retrieval）**：从你的资料库里，找出和问题最相关的几段。
3. **向量数据库（Vector Database）**：把文字变成数字，用「数字相近」代替「意思相近」来找资料。

你今天要建立的核心路径是：

```text
① 检索资料        ② 放入上下文        ③ 生成回答
   Retrieval    →     Context      →    Generation
   找出最相关的几段   连着问题一起送     模型看着资料写答案
```

以及一条要记住的界线：

```text
模型的训练数据里  →  没有你的私有资料
RAG 做的是        →  每次临时把资料递过去，而不是让模型真的「学会」
```

## 2. 为什么要学

你可能已经试过问模型关于自己 NAS 上文件的问题，结果它一本正经地编了一段。

这不是模型坏掉了，而是它的工作原理决定的：

- 为什么模型不知道你那份报修单里写了什么？
- 为什么它会「一本正经地胡说」？
- 为什么有些 AI 助手能回答关于公司文档的问题？
- 为什么把资料直接塞进提问里，效果就变好了？
- RAG 和「把文件喂给模型训练一遍」有什么区别？

**这些问题的答案指向同一件事**：模型的训练数据里没有你的私有资料，
而 RAG 是当前最常见的补救方式。

不理解 RAG，你会误以为「用上 RAG 就等于模型变聪明、回答一定对」——
从而忽略真正决定质量的那一环：**检索找得准不准**。

## 3. 小白解释

### 3.1 模型不知道你的私事

先接受一个事实：

```text
模型的知识 = 它训练时看过的东西
你的文件   = 训练完之后才有的，它没见过
```

所以问它「我那份报修单说了什么」，它只能猜。**因为它的资料库里根本没有这份文件。**

### 3.2 猜不出来，那就「翻书」

既然模型自己没有这份资料，那就在问它之前，**先帮你把资料翻出来。**

```text
不用 RAG：
  你：我那份报修单说了什么？
  模型：嗯……（编一个听起来合理的回答）  ← 幻觉

用了 RAG：
  你：我那份报修单说了什么？
  【系统先去你的文档库里翻，找出报修单里最相关的几段】
  模型：（手里拿着那几段）根据这份报修单，上面写着 …  ← 有据可依
```

**整件事的关键是那句「系统先去翻」。** 模型自己不会翻，是外面的程序帮它翻的。

### 3.3 RAG 的三步，一个都不能少

```text
① 检索资料（Retrieval）
   从你的文档库里，找出和问题最相关的几段
   关键问题：找得准吗？

② 放入上下文（Context）
   把这几段文字，和你的问题一起交给模型
   关键问题：塞得下吗？塞对了吗？

③ 生成回答（Generation）
   模型看着「问题 + 找来的资料」写出答案
   关键问题：它有没有照着资料说？
```

**这三步是一条流水线**，任何一步出问题，最后的答案都会错。

### 3.4 怎么「找出最相关的几段」

这里就是**向量数据库**出场的地方。

它的思路很巧妙：把每一段文字变成一串数字（这串数字叫**向量**），
然后规定：**意思越接近的文字，数字也越接近。**

```text
「如何更换硬盘」      →  [0.82, 0.11, 0.55, …]
「硬盘的更换方法」    →  [0.80, 0.13, 0.54, …]   ← 数字很接近，意思也接近
「今天天气不错」      →  [0.05, 0.91, 0.02, …]   ← 差很远，意思也差很远
```

于是「找出最相关的几段」就变成了一个简单的动作：**找出数字最接近的那几段。**

**向量数据库只负责找。** 它不理解内容、不判断对错、不写答案 —— 它就是个「按意思相近排序」的检索工具。

### 3.5 RAG 不是让模型变聪明

这是最容易被误解的一点。RAG **没有**把任何东西装进模型的脑子里。

```text
模型本身  →  还是原来那个，一字未变
RAG 做的  →  每次提问时，临时把相关资料递到它面前
```

可以理解成：**每次考试都允许带一张小抄**。模型还是那个模型，只是这次手里有资料。

**所以资料找错了，答案照样错。** 检索的质量，决定了 RAG 的上限。

## 4. 技术解释

### 4.1 RAG 要解决的问题

大语言模型有两个已知的局限：

- **知识截止**：训练完成之后发生的事，它不知道。
- **没有私有资料**：你的文档、笔记、内部记录，不在它的训练数据里。

试图让模型「学会」这些私有资料（比如重新训练）代价很高、也不灵活 ——
资料一变，又要重来。RAG 的思路完全不同：**不改模型，改成「每次把资料递给它」。**

```text
重新训练：把资料塞进模型     → 贵、慢、资料一变就过时
RAG     ：把资料放在外面，用时再取 → 便宜、灵活、随时更新
```

### 4.2 检索是怎么做的

检索的核心是「用意思找，而不是用关键词找」。传统的关键词搜索要求字面匹配，
而向量检索比较的是「意思是否接近」。

一个典型的检索流程：

1. **准备阶段**：把文档切成小段（切成一段段，便于精确检索）。
2. **建索引**：把每一段变成向量，存进向量数据库。
3. **查询阶段**：把用户的问题也变成向量。
4. **比对**：在数据库里找出与问题向量最接近的几段。
5. **返回**：把这几段交给下一步。

**「切成小段」这一步很关键**：段太小，信息不完整；段太大，噪音多、也塞不下。
这个取舍直接影响检索质量。

### 4.3 向量数据库的角色与边界

| 它负责 | 它不负责 |
|---|---|
| 存储向量 | 理解内容含义 |
| 按相似度快速找出若干段 | 判断内容是否正确 |
| 大规模检索时的性能 | 生成最终回答 |

**要特别记住「它不负责判断对错」。** 如果原始资料本身写得含糊，或切段切得不合适，
向量数据库照样会「忠实地」把不合适的内容找出来。**它只是一个找东西的工具。**

### 4.4 检索到之后怎么用

找出来的几段，会和用户的问题一起被放进上下文，交给模型。所以：

```text
检索结果的质量  →  决定模型有没有「对的小抄」
上下文塞得下吗  →  决定能不能把该放的都放进去
```

**如果找来的资料不相关，模型要么照错的写，要么无视它自己编。** 两种结果都不好。

### 4.5 一个完整链路

```text
用户提问
   ↓
把问题变成向量
   ↓
向量数据库检索 → 返回最相关的几段
   ↓
「问题 + 这几段资料」一起交给 LLM
   ↓
LLM 生成回答
   ↓
返回给用户
```

**注意：模型在这一整条链路里，只出现在最后一步。** 前面的检索、比对、组装，
都是普通程序在做 —— 和 Day 1 讲的「执行在外面」是同一个道理。

### 4.6 RAG 的常见问题

```text
检索不到    →  资料没建索引，或切段不合适
检索错了    →  找来的段落不相关，答案就歪了
塞不下      →  上下文有限，资料太多反而挤掉重要的
回答不忠实  →  模型没照着资料写，自己发挥了
```

**这四类问题里，只有最后一类和模型有关，前三类都是检索和工程问题。**

## 5. 类比

把 RAG 想象成**开卷考试**：

- **闭卷考试（不用 RAG）**：只能靠脑子里的东西。问到没学过的内容，就只能瞎猜 ——
  这就是模型「编」的原因。
- **开卷考试（用 RAG）**：可以带资料、可以翻书。但翻书需要时间，
  而且**翻错了页，照样答错**。
- **向量数据库是这本书的目录**：它不写答案，只帮你快速定位到「大概在哪一页」。
  目录做得好，你翻得准；目录做得差，你翻半天翻到无关的章节。
- **模型是答题的人**：资料摆在面前，它负责组织语言写出答案。
- **上下文是你能带上考场的资料量**：桌子就那么大，带太多反而乱。

**这个类比能解释什么？**

首先，它解释了「为什么 RAG 不一定对」：开卷考也可能因为翻错页而答错。
**检索决定上限。**

其次，它解释了「为什么 RAG 比重新训练划算」：你不用把整本书背下来（重新训练），
只要考试时带对书就行。**资料换了，换本书就行，不用重新学一遍。**

最后，它解释了一个容易被忽略的点：**答题的人（模型）依然重要。** 资料摆在面前，
有人能准确引用，有人还是会跑题。RAG 提高了下限，但没有取消对模型能力的要求。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：想让 AI 回答关于 NAS 上文档的问题**

```text
✗  直接把问题丢给模型
   → 它没看过你的文档，只能编

✓  用 RAG
   先把 /volume1/docs/ 里的文档切段、建索引（示例路径）
   提问时先检索出最相关的几段，再交给模型
```

**判断：这是 RAG 最典型、最有价值的场景。** 关键在于「建索引」这一步要提前做好。

**场景二：为什么「我把文件都放进去了，它还是答错」**

可能的原因有很多，而且大多不在模型身上：

```text
资料本身写得含糊        → 找出来的段落没法回答
切段切得不合适          → 一个段落被切断了意思
检索找错了段落          → 找来的内容和问题无关
上下文塞不下，丢掉了关键的  → 带了书却翻不到
```

**判断：先查检索，再怪模型。** 这是使用 RAG 最重要的一条排查顺序。

**场景三：文档更新了，要不要重新训练模型**

```text
✗  不需要重新训练 —— RAG 不改模型
✓  只需要更新索引：把新文档重新切段、重新建索引
```

**判断：这正是 RAG 相比「重新训练」的核心优势。** 资料变了，更新外面的索引就行。

### 6.2 RAG 各步的负责方

| 步骤 | 做什么 | 由谁完成 | 出问题时的表现 |
|---|---|---|---|
| 建索引 | 切段、转向量、存库 | 普通程序 | 检索不到、检索不准 |
| 检索 | 找出最相关的几段 | 向量数据库 | 找来的资料不相关 |
| 放入上下文 | 把资料和问题拼起来 | 普通程序 | 塞不下、丢内容 |
| 生成回答 | 写出最终答案 | LLM | 不照着资料说、自己编 |

**看这张表会发现**：四个步骤里，只有最后一步是模型。**RAG 大部分是工程问题，不是模型问题。**

### 6.3 一句话提醒

```text
RAG 不是让模型记住你的资料，而是每次提问时把资料递过去。
所以资料找得准不准，决定了回答对不对。
```

## 7. 常见误区

### 误区一：RAG 让模型的训练数据里真的加进了你的文件

不对。模型一字未改。RAG 是在**提问时临时把资料递到它面前**，用完就没了。
下次提问，还要重新检索一遍。**它是「递小抄」，不是「补课」。**

### 误区二：只要用了 RAG，回答就一定正确

不是。RAG 的答案质量**取决于检索质量**。找错了段落、切段切坏了、上下文塞不下，
都会导致错误答案。而且模型也可能不照着资料说。**RAG 提高下限，不等于保证正确。**

### 误区三：向量数据库会理解并判断内容的对错

不会。它只做一件事：**按「意思相近」把内容找出来。** 它不判断对错、不理解内容、
也不生成回答。资料本身有错，它照样会把错的找出来。

### 误区四：文档更新后需要重新训练模型

不需要。这是 RAG 最主要的好处之一 —— **只更新索引，不动模型**。
重新切段、重新建索引即可，成本远低于重新训练。

### 误区五：把所有资料都塞进上下文就不需要 RAG 了

不一定可行。上下文长度是有限的，塞太多会导致关键内容被挤掉，也会更慢更贵。
**RAG 的价值恰恰在于「先挑出相关的，再放进去」**，而不是把一切都堆进去。

## 8. 知识地图

RAG 是「工具 + 记忆」的具体应用：把外部资料检索出来，递进模型视野。

```text
AI
├── 概念                    （Week 10）
├── 硬件与运行              （Week 11）
└── Agent 与工具            ← 本周在这里
    ├── LLM / Tools / Function Calling   （Day 1）
    ├── Memory / Agent / Workflow        （Day 2）
    │   └── 记忆的「怎么找回来」，就是检索
    ├── RAG / Retrieval / Vector DB      ← 今天
    │   ├── ① 检索资料（Retrieval + 向量数据库）
    │   ├── ② 放入上下文（Context）
    │   └── ③ 生成回答（Generation）
    ├── MCP / Permission Boundary        （Day 4）
    └── Final Review                     （Day 5）
```

本课与其他课的连接：

```text
Week 10         →  知道上下文是有限的，也是模型唯一的视野
Week 12 Day 2   →  长期记忆「怎么找到该递回的内容」
     ↓
Week 12 Day 3   →  RAG：检索资料 → 放入上下文 → 生成回答（本课）
     ↓
Week 12 Day 4   →  检索要在「允许访问的目录」内进行 —— 这就是权限边界
Week 12 Day 5   →  综合测试要求画出 NAS 数据源到 AI 应用的完整链路
     ↓
Week 3          →  资料放在 NAS 上，检索的前提是它们被好好组织过
```

今天只需要真正记住一句话：

> **RAG 的三步是「检索资料 → 放入上下文 → 生成回答」；它不改变模型，只是在回答前先把相关资料递给它 —— 所以检索的质量，决定了回答的上限。**
