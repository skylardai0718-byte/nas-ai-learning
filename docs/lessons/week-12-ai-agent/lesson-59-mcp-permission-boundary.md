# 第五十九课：MCP 与权限边界

> 本课的一句话结论：**MCP 只是把「有哪些工具和数据」用统一的方式描述出来，它本身不授予任何权限；真正决定 Agent 能做什么的，是你给执行程序的权限边界 —— 默认只读、能少给就少给。**

## 1. 今天学习什么

今天要掌握 3 个概念：

1. **MCP（模型上下文协议，Model Context Protocol）**：用统一的方式描述「有哪些工具和数据可用」。
2. **权限边界（Permission Boundary）**：明确划出「能做什么、不能做什么」的那条线。
3. **NAS + AI Agent**：让 Agent 读取 NAS 上的文档这件事，以及它的隐私与误操作风险。

你今天要建立的核心结构是：

```text
MCP            →  统一描述「有什么工具、有什么数据」
权限边界        →  决定「这些工具，允不允许真的动」
                       ↑
              安全和风险真正收在这里
```

以及本课的核心动作：

```text
设计一个「只读访问 NAS 文档」的 Agent
  ✓ 读指定目录
  ✗ 不写、不改、不删
  ✗ 不出这个目录
```

## 2. 为什么要学

前三天你知道了：模型输出意图、程序真正执行；Agent 会自己循环走多步；RAG 会把你的资料递进模型。

把这三件事合起来，就问出了本周最要紧的一个问题：

- 如果 Agent 真的能读你 NAS 上的文件，谁能保证它不乱动？
- 为什么每接一个新工具都要重新对接一遍，有没有统一的方式？
- MCP 是不是就等于「授权」？
- 只读权限是不是就没有风险了？
- 为什么不能直接把整个 NAS 都开放给 Agent？

**这些问题全都指向同一件事：权限。** 而且这是整个 12 周里唯一一周讨论「程序自动操作你的文件」，
所以它也是最需要把风险讲透的一课。

不理解权限边界，你可能会因为「它只是只读、应该没事」而把家庭照片、私人文档、
财务记录全部暴露给一个会犯错、也会把内容回传的系统。

## 3. 小白解释

### 3.1 每接一个工具都要单独对接，很麻烦

Day 1 讲过，模型靠「工具」做事。但问题来了：

```text
你有一个文档库、一个日历、一个笔记应用
每个都想让 AI 用
→ 每接一个，都要单独写一套对接  → 重复、麻烦、容易出错
```

**MCP 想解决的就是这个重复劳动。**

它的思路是：**用一套统一的说法，把「这里有什么工具、有什么数据」描述出来。**
这样不管谁来接，都按同一套规则读这份描述。

```text
没有统一方式：
  A 应用 ──单独对接──→ 文档库
  B 应用 ──单独对接──→ 文档库   （重写一遍）

有统一方式（MCP 的意图）：
  A 应用 ─┐
           ├──按统一方式──→ 文档库
  B 应用 ─┘     （描述一次，谁都能接）
```

### 3.2 MCP 描述「有什么」，但不决定「准不准」

这一点非常关键，也最容易被误解。

```text
MCP 做的是：     告诉对方「这里有哪些工具可以用」
MCP 不做的是：   决定「这些工具允不允许真的被调用」
```

打个比方：MCP 像一本**菜单**。菜单上列着「本店有红烧肉、有清蒸鱼」。
但**菜单不会替厨房决定，谁会真的被允许进厨房、能拿走什么。**

**真正决定允不允许的，是你在后端设的权限。**

### 3.3 权限边界：那条「能做到哪」的线

**权限边界（Permission Boundary）** 就是明确划出的那条线：

```text
线以内  →  允许做
线以外  →  禁止做（哪怕技术上做得到）
```

对「让 Agent 读 NAS 文档」这件事，这条线至少有两个方向：

```text
方向一：能做什么动作？
  只读（Read-only）    →  只能看
  可写（Read-write）   →  能看，也能改、能删

方向二：能碰哪些东西？
  只在一个目录里        →  比如 /volume1/docs/
  还是整个 NAS          →  所有共享文件夹
```

**这两个方向都要收紧。** 只看不写是最基本的，但「能看什么」同样重要。

### 3.4 为什么默认只给读权限

回想 Day 1 的结论：**真正动手的是外面的程序。**

那么，你给程序什么权限，就等于给 Agent 什么权力。而 Agent 是会犯错的：

```text
它可能理解偏了   →  调用了错误的工具
它可能参数填错   →  动了不该动的文件
它可能循环不停   →  同一个操作反复执行
```

**读错了，顶多得到一段错误答案；写错了，数据可能就回不来了。**

```text
只读出错：答案不对 → 重问一次就行
写错出错：文件被改/被删 → 可能无法恢复
```

**所以第一条规矩：默认只给读权限。**

### 3.5 只读也有隐私风险

「只读而已，能有什么风险？」——这是很常见的想法，但它不成立。

**因为读到的东西，可能被送到别的地方去。**

```text
Agent 读到什么  →  可能成为这次提问的一部分
                →  可能被发送到模型服务
                →  可能被记录在日志里
```

**「可读范围」就是你的隐私边界。** 你把多少目录开放给它，就等于把多少内容
交给了「可能被读取、可能被传输、可能被记录」的范围。

**所以最小权限原则（Least Privilege）** 在这里的含义是：

> 只给完成这件事所必需的那一份权限，不多给一分。

不是「反正只读，全开放也没事」—— **能读到的越少越好。**

## 4. 技术解释

### 4.1 MCP 的设计意图

MCP 想解决的是一个工程上的重复问题：**工具和数据源的接入方式各不相同。**

它的设计意图可以概括为：

```text
让「提供工具/数据的一方」和「使用模型的一方」解耦
前者按统一方式描述自己的能力
后者按统一方式读取这些描述并调用
```

**注意这句话里没有「权限」两个字。** MCP 的职责边界是「描述和接入」，
不是「授权和管控」。当然，一个提供方可以只描述自己愿意开放的那些工具 ——
这本身就是一种收紧，但这属于提供方的选择，不是协议自动保证的。

### 4.2 权限边界的三个维度

对一个访问 NAS 的 Agent，权限边界至少要回答三个问题：

| 维度 | 问题 | 收紧方式 |
|---|---|---|
| 动作 | 能做哪些操作？ | 只提供读工具，不提供写/删工具 |
| 范围 | 能访问哪些路径？ | 限定在具体目录，拒绝目录外路径 |
| 身份 | 以什么身份访问？ | 用专门的低权限账号，不用管理员 |

**三个维度缺一不可。** 只限制动作但开放全盘，隐私仍然暴露；
只限制范围但给了写权限，数据仍然危险。

### 4.3 只读 Agent 的权限清单

一个合理的设计长这样：

```text
✓ 允许：读取 /volume1/docs/ 目录下的文件（示例路径）
✓ 允许：列出该目录下的文件名
✓ 允许：读取指定格式的文件（如纯文本、PDF）
✗ 禁止：写入、修改、重命名、删除
✗ 禁止：访问 /volume1/docs/ 之外的任何路径
✗ 禁止：访问包含密钥、凭据、配置的目录
✗ 禁止：执行命令
✗ 禁止：访问网络（除非确实需要）
```

**这份清单里，最容易被忽略的是中间那条「路径限制」。** 很多人只想到「不给写权限」，
却忘了「读权限给了整个盘」本身就是问题。

### 4.4 为什么路径限制容易失效

限制路径需要**真的去做校验**，而不是只写在文档里。常见的失效方式：

```text
用「路径里包含这个目录名」来判断  →  可以被 ../ 绕出去
只检查了开头，没检查真实路径      →  符号链接可以指向别处
工具自己不做校验，靠调用方自觉    →  换个调用方就失效
```

**所以正确的做法是「默认拒绝」**：不在允许清单里的一律拒绝，
而不是「默认允许，发现可疑再拦」。

### 4.5 写入权限为什么危险

即使不考虑恶意，写入本身就有风险：

```text
覆盖   →  原本的内容没了
删除   →  文件没了（除非有备份，但备份也未必及时）
批量   →  一次循环可能改动很多文件
不可逆 →  很多操作没有「撤销」
```

**而且 Agent 的循环（Day 2）会放大这个问题**：一个错误的写操作可能被执行多次。

**结论**：如果确实需要写，也应该先从「限定目录 + 限定操作 + 有备份」开始，
而不是直接开放整个 NAS 的写权限。

### 4.6 数据流向哪里，也要问清楚

```text
文档 → Agent 读取 → 成为上下文 → 发送给模型服务 → 可能被记录
```

**这条链路决定了隐私的范围。** 如果用的是云端模型服务，内容会离开你的设备；
如果用的是本地模型（Week 11），内容留在本机。**这个差别对隐私非常重要，
也是「NAS + 本地 AI」这个组合最实际的价值之一。**

### 4.7 最小权限的落地顺序

```text
① 先只读
② 再限目录
③ 再限文件类型
④ 能不用管理员账号就不用
⑤ 需要写时，单独评估、单独开、单独备份
```

## 5. 类比

把权限边界想象成**图书馆的门禁设置**：

- **MCP 是图书馆的「馆藏目录」**：它告诉你有哪几排书架、有哪些书可以借。
  目录写得再全，也不代表谁都进得来。
- **只读权限是「只能在馆内阅读」**：你可以看，但不能把书带走、不能在上面写字。
- **可写权限是「可以修改馆藏」**：一旦给错人，书可能被改、被撕、被拿走。
- **路径限制是「只能进某一个阅览室」**：不是把你放进整个图书馆。
- **最小权限是「办一张权限刚刚够用的借书证」**：你需要文学区，就别给全馆通行的卡。

**这个类比能解释什么？**

第一，它解释了**为什么 MCP 不等于授权**：有目录，不等于有门禁卡。这是两件事。
很多人把「接上了」当成「可以随便用了」，这正是最危险的误解。

第二，它解释了**为什么只读也可能泄露隐私**：能进阅览室看书，就意味着你能看到书里的内容，
也可能把内容抄出去。**「能读」本身就意味着信息可能离开。**

第三，它解释了**为什么范围要收紧**：你只需要文学区，给你全馆通行证没有任何好处，
只有更大的风险。**权限不是越多越方便，而是刚刚够用最好。**

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：设计一个「帮我查 NAS 文档」的 Agent**

```text
✗  错误设计：
   给管理员账号
   开放整个 /volume1/
   同时提供读、写、删除工具
   → 一次误操作就可能改坏或删掉重要文件

✓  正确设计：
   专门的只读账号
   只开放 /volume1/docs/（示例路径）
   只提供「列目录」和「读文件」两个工具
   每次读取记录日志
```

**判断：这个场景是本周最重要的实践。** 注意「专门账号」和「限定目录」这两条，
它们比「不给写权限」更容易被忽略。

**场景二：有人说「只读没风险，随便开放吧」**

```text
只读的风险不在「改坏数据」，而在「读走数据」：
  → 家庭照片、私人文档、财务记录都可能被读到
  → 读到的内容可能被发送到模型服务
  → 也可能被记录在日志里
```

**判断：「只读」减少了数据被破坏的风险，但没有消除隐私暴露的风险。**
可读范围仍然是需要收紧的边界。

**场景三：能不能让 Agent 自己整理文档、重命名文件**

这是「写权限」的需求。这时要问的不是「能不能做」，而是：

```text
① 有没有备份？（没有就先别开）
② 能不能只开放一个专门的目录，而不是整个盘？
③ 能不能先改成「生成一份建议清单，由人来执行」？
④ 出错了能不能恢复？
```

**判断：很多时候，把写操作改成「生成建议、人来确认」，既满足了需求，又避开了风险。**
这是最实用的一个折中方案。

### 6.2 权限设计对照

| 设计项 | 危险做法 | 安全做法 |
|---|---|---|
| 账号 | 用管理员账号 | 用专门的只读账号 |
| 目录 | 开放整个 NAS | 只开放一个目录 |
| 工具 | 读、写、删都给 | 只给读和列目录 |
| 校验 | 默认允许，可疑再拦 | 默认拒绝，白名单放行 |
| 写入 | 直接开放 | 先生成建议，由人确认 |
| 数据去向 | 不关心 | 明确是本地模型还是云端服务 |

**这张表可以作为你自己设计时的检查清单。** 每一项都问一遍「我是不是选了左边」。

### 6.3 一句话提醒

```text
MCP 描述「有什么」，权限边界决定「准不准」。
默认只读、目录限死、账号降权 —— 剩下的一律不开。
```

## 7. 常见误区

### 误区一：用了 MCP 就等于管好了权限

不对。MCP 的职责是「用统一方式描述有哪些工具和数据」，**它本身不授予也不管控权限**。
权限是你在后端设的。把「接上了」当成「可以放心用」，是本周最危险的误解。

### 误区二：只读权限就没有任何风险

不对。只读降低的是「数据被破坏」的风险，但没有消除「数据被读走」的风险。
读到的内容可能被送进上下文、发送到模型服务、记录进日志。**可读范围就是隐私边界。**

### 误区三：给 Agent 管理员账号更方便

方便，但代价太大。管理员账号意味着一个出错或失控的 Agent 能影响整个系统。
**应该用权限刚刚够用的专门账号** —— 这就是最小权限原则最直接的落地。

### 误区四：限制路径只要写在配置里就够了

不够。路径校验必须**真的执行**，而且要防住 `../` 绕过、符号链接指向外部等情况。
**正确做法是「默认拒绝」的白名单**，而不是「默认允许、发现可疑再拦」的名单。

### 误区五：既然会有风险，那就什么都别用

走向另一个极端也没必要。风险不等于不能用，而是**要按风险决定开放多少**。
从「只读 + 限定目录 + 专门账号」开始，就是一个既实用又可控的起点。
把写操作改成「生成建议由人确认」，更是两者兼得。
