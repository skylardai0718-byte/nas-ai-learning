# 第六十课：最终复习与综合测试

> 本课的一句话结论：**12 周的内容是一条从硬件到 AI 的链 —— 硬件决定能不能跑，存储决定数据放在哪，网络决定能不能访问，Linux 和 Docker 决定怎么运行，自托管决定应用怎么部署，AI 决定它怎么变得更聪明。**

## 1. 今天学习什么

今天不学新概念，而是把 12 周的知识合成一张图，并完成最终综合测试。

要串起来的三个大块：

1. **底层**：硬件 → 存储 → 网络 —— 一台 NAS 是什么、数据存哪里、怎么访问。
2. **运行层**：Linux → Docker → 自托管 —— 应用跑在什么上面、怎么被隔离、怎么部署。
3. **智能层**：AI → Agent —— 模型怎么运行、怎么从「会说话」变成「会做事」。

你今天要建立的核心结构是：

```text
硬件 → 存储 → 网络 → Linux → Docker → 自托管 → AI
```

以及最终要能回答的三个综合问题：

```text
①  看懂一台 NAS 的规格，并说出它没告诉你什么
②  读懂一段 Compose，指出应用、访问入口、数据位置
③  判断模型能不能跑，并画出从模型到应用的完整链路
```

## 2. 为什么要学

前 11 周你一周学一个主题，每一周都是独立的。今天要回答的是最后一个问题：

- 这些知识之间是怎么连起来的？
- 一台 NAS 上的数据，从硬盘到 AI 应用，中间经过哪些层？
- 为什么说「硬件决定能不能跑」？
- 为什么同一个应用，换个部署方式就完全不一样？
- 我怎么知道自己真的学会了，而不是「好像懂了」？

**最后一问最重要。** 这一周结束后，没有下一周的测试来提醒你哪里没懂，
所以要靠一套自己的标准来判断 —— 这就是本课要给出的 **Knowledge Score**。

## 3. 小白解释

### 3.1 12 周，其实是一条链

把这 12 周串起来看，它讲的是一件事的七个环节：

```text
①  硬件      这台机器有什么        →  能不能跑得动
②  存储      数据怎么存、怎么保护   →  数据放在哪、会不会丢
③  网络      设备之间怎么连、怎么访问 →  能不能连上、安不安全
④  Linux     操作系统怎么用        →  怎么在机器上操作
⑤  Docker    应用怎么被隔离        →  怎么装、怎么不互相干扰
⑥  自托管    应用怎么部署          →  服务怎么跑起来、怎么暴露
⑦  AI        模型怎么运行、怎么做事 →  怎么变聪明、怎么自动做
```

**每一环都依赖上一环。** 没有硬件，什么都跑不了；没有存储，AI 没有数据可读；
没有网络，你在外面访问不了；没有 Docker 和自托管，应用装起来会很麻烦。

### 3.2 三个层次：底层、运行层、智能层

```text
智能层     AI / Agent / RAG              ← Week 10–12
─────────────────────────────────────
运行层     Linux / Docker / 自托管        ← Week 6–9
─────────────────────────────────────
底层       硬件 / 存储 / 网络             ← Week 1–5
```

**自下而上，每一层为上一层提供基础。** 遇到问题时，也是自下而上排查：
先看硬件够不够、存储有没有满、网络通不通，再看应用和 AI。

### 3.3 三道综合题，考的是「能不能串起来」

最终的测试不是考某一周的定义，而是考**跨周的串联能力**：

```text
题一：给一串规格  →  你能不能读出「有什么」和「没什么」
      （考 Week 2 硬件 + Week 11 AI 硬件）

题二：给一段 Compose  →  你能不能指出「应用是谁、怎么访问、数据在哪」
      （考 Week 7–8 Docker + Week 3 存储）

题三：给一个硬件和两个模型  →  你能不能判断「能不能跑」，并画出整条链路
      （考 Week 11 + Week 12 + 全部）
```

**能答出这三题，说明这 12 周的知识真的连起来了。**

### 3.4 Knowledge Score 是给自己用的尺子

课程结束时，你需要给自己一个诚实的评估。标准不是「感觉学会了」，而是**有没有证据**：

```text
听过术语，但说不清            →  Beginner
能说个大概，还需要提示         →  Basic
能独立解释，会做基础场景题     →  Working Knowledge
能比较方案、能排查常见问题     →  Comfortable
能讲给新手听，并指出边界和误区 →  Strong
```

**关键在「证据」两个字。** 复述过、答对过题目，才算证据。**没学过的领域就老实写 Beginner，
不要为了让进度好看而给自己加分** —— 这是这个评分体系唯一的要求。

### 4.3 Knowledge Score 的证据标准

- **Beginner**：听过术语，但无法准确解释。
- **Basic**：能说出大意，但仍需要提示。
- **Working Knowledge**：能独立解释，并完成基础场景题。
- **Comfortable**：能比较方案、排查常见问题。
- **Strong**：能向新手讲清楚，并指出边界与常见误区。

未正式学习的领域保持 `Beginner（尚未开始）`，不为了让进度曲线好看而提前加分。

**使用方式**：每个领域，回想你这 12 周做过的复述和测试，找出**最匹配的一级**。
不要取最高的一次表现，取**你稳定能做到的水平**。

### 4.4 三类最终综合测试场景

**场景一：读懂一台 NAS 的规格**

```text
Intel N150 / 16GB DDR5 / 2×2.5GbE / PCIe 3.0 x1 / 2×SATA / 1×NVMe
```

| 部分 | 含义 | 可能的限制 |
|---|---|---|
| Intel N150 | 低功耗入门级 CPU | 适合文件服务与轻量应用，不适合重负载转码或大模型 |
| 16GB DDR5 | 内存容量与类型 | 够跑若干容器；跑大模型会被容量卡住 |
| 2×2.5GbE | 两个 2.5G 网口 | 比千兆快，但需交换机、网线、对端设备都支持 |
| PCIe 3.0 x1 | 一条短插槽 | 带宽有限，不适合高性能扩展卡 |
| 2×SATA | 两个硬盘接口 | 盘位少，扩容空间有限 |
| 1×NVMe | 一个 NVMe 槽 | 适合做系统盘或缓存 |

**规格没有告诉你什么？** 它没说内存能不能加、没说机箱能装几块盘、
没说散热和噪音、没说实际读写性能、也没说厂商的软件支持情况。
**读规格的第一步，是分清「写了什么」和「没写什么」。**

**场景二：读懂一段 Compose**

```yaml
services:
  app:
    image: example/app:latest
    ports:
      - "8080:80"
    volumes:
      - /volume1/appdata:/config
      - /volume1/data:/data
    environment:
      - TZ=Asia/Shanghai
```

| 字段 | 回答的问题 | 这一段的意思 |
|---|---|---|
| `image` | 跑的是什么应用 | 使用 `example/app` 这个镜像 |
| `ports` | 从哪里访问 | 访问 NAS 的 8080 端口，转发到容器内的 80 |
| `volumes` | 数据放在哪里 | 配置存在 `/volume1/appdata`，数据存在 `/volume1/data` |
| `environment` | 用什么参数运行 | 设置了时区等运行参数 |

**三个要点**：应用是 `app`；访问入口是 `NAS 地址:8080`；数据在宿主机的两个目录里 ——
**删掉容器，数据还在，因为它们在容器的外面。**

**场景三：这台设备能跑哪个模型**

```text
设备：8GB VRAM
模型：7B Q4  与  70B
```

```text
7B Q4   →  量化后体积较小，8GB VRAM 有机会加载 → 可能能跑，但具体还取决于量化格式、上下文长度、引擎实现
70B     →  即使量化，体积也远超 8GB      →  单卡基本不可能；要靠多卡、内存卸载或更小的量化，且会非常慢
```

**完整链路图：**

```text
NAS 上的文档（数据源）
        ↓
   推理引擎（加载模型、执行推理）
        ↓
       模型（7B Q4）
        ↓
       API（对外提供接口）
        ↓
    AI 应用（对话界面 / Agent / RAG）
        ↓
        用户
```

**判断的关键**：能不能跑，取决于**模型体积与可用显存/内存的关系**；
跑得好不好，还取决于带宽、量化格式、上下文长度和推理引擎的实现。
**规格只给了其中一部分答案。**

## 5. 类比

把这 12 周想象成**盖一栋房子**：

- **硬件是地基和材料**：地基不牢，上面盖什么都不稳。
- **存储是仓库**：决定东西放哪、怎么保管、丢了怎么办。
- **网络是道路**：决定外面的人能不能进来、走哪条路进来。
- **Linux 是水电管线**：看不见，但所有东西都靠它运转。
- **Docker 是标准房间**：每个房间自成一体，互不干扰，想拆就拆。
- **自托管是把房间装修成能用的空间**：让别人也能进来使用。
- **AI 是住在房子里的人**：他能不能干活，取决于房子给了他什么条件。

**这个类比能解释什么？**

它解释了**为什么排查要自下而上**。房子漏水，你不会先去问住客有没有意见，
而是先看管线、再看墙体。同样，AI 回答不对，先看数据在不在、检索对不对，
而不是先怀疑模型。

它也解释了**为什么每一环都不可跳过**。你可以只盖地基不住人，但不能只住人没有地基。
**12 周的顺序不是随意的，它就是这个依赖关系。**

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：有人拿一串规格问你「这台够用吗」**

```text
不要直接回答「够」或「不够」，而是先反问：
① 你要跑什么？（文件共享？影音？本地模型？）
② 数据有多少？需要几块盘？
③ 要不要在外面访问？
④ 要不要跑 AI？跑多大的模型？

→ 规格本身不含「够不够」的答案，答案取决于用途。
```

**判断：读规格的第一步不是看数字大小，而是先问用途。** 这是 Week 2 教的核心态度。

**场景二：一个服务打不开了，从哪查起**

```text
自下而上：
① 硬件   → 机器还开着吗？盘还好吗？
② 存储   → 空间满了吗？卷挂上了吗？
③ 网络   → 能 ping 通吗？端口对吗？
④ 系统   → 权限对吗？进程还在吗？
⑤ 容器   → 容器起来了吗？日志说了什么？
⑥ 应用   → 配置改过吗？版本变了吗？
```

**判断：从下往上排查，比一上来就重装应用有效得多。** 这张清单就是 12 周的实用价值。

**场景三：给一个「NAS + 本地 AI + RAG」架构说给非技术用户听**

```text
「你的文档放在 NAS 上（仓库），
 本机跑着一个模型（住在房子里的人），
 你提问的时候，它会先去文档里找相关的几段（开卷考试），
 再根据这几段回答你。
 整个过程都在你自己的设备上完成，内容不外传。」
```

**判断：能用这样的话讲清楚，就是 Strong 的表现。** 这也是 roadmap 里
「把核心概念准确地讲给非技术用户」这条最终能力。

## 7. 常见误区

### 误区一：把 12 周当成 12 个互不相关的主题

它们是一条链：硬件 → 存储 → 网络 → Linux → Docker → 自托管 → AI。
**每一环都依赖上一环**，排查时也要自下而上。把它们连起来，才是这套课程真正的收获。

### 误区二：以为读完课程就等于「学会了」

读完不等于学会。判断标准是**证据**：能不能不看笔记复述、能不能独立解释、
能不能做对基础场景题。**没有证据的「感觉懂了」，在 Knowledge Score 里不算数。**

### 误区三：为了让进度好看而抬高自己的等级

不要这样做。没有正式学过的领域老实写 `Beginner（尚未开始）`，
**这不是失败，只是还没开始。** 虚高的评分只会让你在真正需要的时候才发现自己不会。

### 误区四：读规格只看数字大不大

规格不能脱离用途。16GB 内存对文件服务绰绰有余，对跑大模型就捉襟见肘。
**先问「要用来做什么」，再看数字。** 而且要注意规格**没写**的部分 ——
能不能扩展、散热如何、软件支持怎样，这些往往更重要。

### 误区五：出了故障就从最上层开始重装

AI 应用回答不对，先看数据在不在、检索对不对，而不是先重装模型。
**逐层往下查，比直接推倒重来更有效，也更不伤数据。**
