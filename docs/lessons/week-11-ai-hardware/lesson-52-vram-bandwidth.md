# 第五十二课：VRAM 与显存带宽

> 本课的一句话结论：**显存（VRAM）容量决定模型能不能装下，显存带宽决定数据搬得快不快 —— 「能不能跑」和「跑得快不快」是两个不同的问题。**

## 1. 今天学习什么

今天要掌握 4 个概念：

1. **VRAM（显存）**：GPU 自带的专用内存，模型必须装进这里才能高效运行。
2. **Memory Bandwidth（显存带宽）**：显存和计算单元之间搬运数据的速度。
3. **CUDA Core**：GPU 里通用的并行计算单元。
4. **Tensor Core**：针对矩阵运算优化的计算单元。

你今天要建立的核心结构是：

```text
VRAM 容量（GB）   →  模型装不装得下   →  决定「能不能跑」
显存带宽（GB/s）  →  数据搬得多快     →  决定「跑得快不快」
```

以及一条容易被忽略的事实：

```text
显存里  ≠  只放模型
还有：上下文、系统占用、别的程序
```

**本课的重点是前两条**。CUDA Core 和 Tensor Core 只需要知道「它们是算力相关的单元」，不必深入。

## 2. 为什么要学

上一课你知道 LLM 推理主要看 GPU。但「看 GPU」还是个很粗的说法 —— GPU 有好几项指标，它们分别管什么？

不理解这些指标，你会在这些地方卡住：

- 为什么有时显存「够」，模型却还是跑不起来？
- 为什么两块显存容量一样的设备，生成速度差很多？
- 为什么听说「量化一下就能跑了」，量化到底改变了哪个数字？
- 为什么模型跑久了会突然变慢或报错？
- 为什么「核心数很多」不代表「这个模型就能跑」？

不学这一课，你会把所有显存相关的参数混成一团，看到规格表也不知道该看哪一行。

**这一课是本周的枢纽** —— Day 3 的量化改变的是「模型体积」，Day 5 的综合判断要同时用到容量和带宽。今天先把这两个概念分清楚。

## 3. 小白解释

### 3.1 显存是工作台，不是仓库

先区分两个很容易混淆的概念：

```text
硬盘 / 存储  →  仓库    东西可以长期放在这里，但不方便随时取用
内存 / 显存  →  工作台  正在加工的东西必须摆在这里
```

模型文件平时躺在存储里。要运行它，就必须把它**搬上工作台**。

```text
存储里的模型文件  →（加载）→  显存里的模型  →  开始计算
```

**如果工作台摆不下，模型就没法完整地搬上来。** 这就是「显存容量决定能不能跑」的直观含义。

### 3.2 为什么光有容量还不够 —— 带宽在做什么

模型装上工作台之后，每生成一个词，都要把大量的数据在显存和计算单元之间搬一遍。

```text
生成一个词  →  把庞大的参数数据过一遍  →  得到下一个词
生成下一个词  →  再搬一遍……
```

所以速度不只取决于「算得多快」，还取决于**数据搬得多快**。

这就是**显存带宽（Memory Bandwidth）** —— 它衡量的是单位时间里能搬运多少数据。带宽越高，同样的数据搬得越快，生成就越快。

用一句话区分这两件事：

```text
容量  →  能不能把东西摆上工作台   →  决定能不能开始
带宽  →  东西搬得快不快           →  决定做得快不快
```

### 3.3 为什么「显存够」有时还是跑不起来

因为显存里不只放模型。至少还有三类东西要占地方：

```text
① 模型本身
② 上下文（对话历史）
   对话越长，需要留的空间越多
③ 系统和别的程序
   桌面环境、其他应用也可能用掉一部分
```

所以「显存 8GB」和「模型 4GB」之间，看着有 4GB 余量，实际上：

```text
8GB  减去  系统占用  减去  其他程序  减去  上下文  =  真正可用的余量
```

**这就是为什么判断时不能只看「模型体积 < 显存容量」这一条。** 型号规格上写着 8GB，不代表这 8GB 全部归模型使用。

### 3.4 CUDA Core 和 Tensor Core：先只记定位

这两个名字看起来很像，但本课只需要知道它们的**定位**：

```text
CUDA Core   →  GPU 里通用的并行计算单元，什么并行计算都能参与
Tensor Core →  专门针对矩阵运算优化的单元，做这类运算时效率更高
```

它们影响的是「**算得多快**」，而这个「快」的前提是——**模型已经装进去了**。

换句话说：

> **核心数再多，也解决不了「装不下」的问题。**

所以看到「有多少个核心」这类描述时，先别急着下结论。要判断一个模型能不能跑，第一眼看的应该是**显存容量**。

## 4. 技术解释

### 4.1 VRAM 的作用与约束

VRAM（Video RAM，显存）是 GPU 板上的专用内存，它的两个特点是：

- **靠近计算单元**：数据从显存搬到计算单元的距离很短，所以访问快。
- **容量有限**：比系统内存小得多，且通常不能像内存那样随意扩充。

在 LLM 推理里，VRAM 主要承担三部分开销：

```text
模型权重  +  上下文缓存（KV Cache）  +  运行时开销
```

其中**上下文缓存**值得单独记住：它随对话长度增长。一段很长的对话，可能需要额外好几个 GB。这就解释了为什么「刚启动没问题，聊久了就出问题」。

**判断的边界**：只看「模型体积 vs 显存容量」两个数字，**不足以**判断能否稳定运行。还必须知道上下文长度、系统占用和并发情况。

### 4.2 Memory Bandwidth 的作用

Memory Bandwidth（显存带宽）的单位通常是 GB/s，含义是「每秒能在显存和计算单元之间搬运多少 GB 数据」。

它和「算力」是两回事：

```text
算力（FLOPS）  →  每秒能做多少次运算
带宽（GB/s）   →  每秒能搬多少数据
```

对 LLM 推理来说，瓶颈常常在带宽一侧。原因是：生成每一个词，都要把规模庞大的权重数据过一遍，而运算本身相对简单 —— 于是**搬运速度**就成了决定生成速度的关键。

**用一个粗略的直觉记法**：

```text
同样大小的模型  →  带宽越高  →  每秒能生成的词越多  →  感觉越快
```

**判断的边界**：带宽只影响速度，**不影响能否加载**。带宽再高也装不下装不下的模型；反过来，容量够但带宽低，就是「能跑，但慢」。

### 4.3 CUDA Core 与 Tensor Core 的定位

- **CUDA Core**：GPU 的通用并行计算单元。各种并行计算任务都会用到它。
- **Tensor Core**：为矩阵乘法这类运算做了专门优化的单元，在这类运算上效率更高。

这两个概念在本课程里**只需要定位，不需要深入**。原因是：它们回答的是「算得快不快」，而本周最核心的问题「能不能装下」由显存容量回答。

一个实用的提醒：

> **看到「核心数」时，问自己：这个数字解决的是「算得快」还是「装得下」？** 如果模型根本装不进显存，核心数再多也无法让它运行起来。

### 4.4 两个问题必须分开问

把本课的逻辑整理成一条判断链：

```text
第一步：模型多大？（体积，GB）
          ↓
第二步：显存够装吗？（容量 vs 体积 + 上下文 + 开销）
          ↓ 装得下
第三步：带宽多少？（决定生成速度）
          ↓
第四步：还缺哪些信息？→ 见 Day 5
```

**每一步都要停下来问「这一步的结论有没有边界」。** 例如「容量够」这个结论，边界是没有考虑上下文增长和系统占用；「带宽高」这个结论，边界是它只谈速度、不谈能不能装。

## 5. 类比

把 LLM 推理想象成**一间厨房**：

- **显存是厨房的台面**：所有食材（模型数据）必须摊在这张台面上才能加工。台面太小，食材就摆不开。
- **显存带宽是台面到灶台之间的传递速度**：台面再大，如果每次只能一小把一小把地递过去，做菜照样慢。
- **模型体积是要摆上来的食材总量**。
- **上下文是随对话不断增加的备菜**：聊得越久，临时摆上来的东西越多，台面会被逐渐占满。
- **CUDA Core / Tensor Core 是灶台的功率**：火力再猛，也得先有食材摆在台面上。

这个类比能解释什么：

**它解释了为什么「台面大」和「出菜快」是两件事。** 台面（容量）解决的是「能不能开工」；传递速度（带宽）解决的是「开工后快不快」；而火力（算力）只在食材已经就位时才有意义。

它还能解释为什么「聊久了会出问题」：**备菜（上下文）是不断累积的**，台面被逐渐占满，最终摆不下新的东西。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：只想判断模型能否加载**

```text
先看：模型体积（GB）  ≤  显存容量（GB）之后还剩多少余量
```

**但这个判断的边界是**：它只回答了「能不能装下」，完全没有回答「跑起来快不快」，也没有考虑上下文和系统占用。

```text
判断：体积够小 → 看起来能加载
它没告诉你：速度、上下文能开多长、系统占了多少
```

**场景二：想知道生成会不会很慢**

这时要看的是带宽，而不是容量：

```text
容量大 ≠ 速度快
两个容量相同的设备，带宽可能差很多 → 生成速度差别明显
```

**判断的边界**：带宽只决定速度区间，它**不会**告诉你「慢到什么程度算不可接受」—— 那取决于你的使用方式，是要即时对话，还是可以等一会儿。

**场景三：想判断能不能一边聊天一边开很多程序**

这时问题就从单看模型，变成了「显存中还要分出去多少」：

```text
要同时考虑：模型 + 上下文 + 系统 + 其他程序
```

**判断的边界**：规格表只给了显存总量，没有告诉你系统和别的程序实际会占用多少 —— 这部分只能在实际使用中观察。

**这三条合起来，就是本课的核心判断习惯：容量谈「能不能」，带宽谈「快不快」，而两者都不能单独下结论。**

### 6.2 两个指标的分工

| 规格 | 决定什么 | 典型单位 | 规格没告诉你什么 |
|---|---|---|---|
| 显存容量（VRAM） | 模型能否被完整加载 | GB | 系统与其他程序占多少、上下文能开多长 |
| 显存带宽（Bandwidth） | 数据搬运与生成的速度 | GB/s | 慢到什么程度算不可接受、实际主观体验 |
| CUDA Core / Tensor Core | 并行计算的算力定位 | 数量 / 代际 | 与「能否加载」无关；不等于整体速度 |

### 6.3 一个容易被忽略的细节：显存是共享的

同一台设备上，显存不只是给 AI 用。桌面环境、其他应用、系统进程都可能占用一部分。

**所以在做判断时，用「标称容量」去对比「模型体积」是偏乐观的。** 实际可用的部分通常更小。这也是为什么工程上会强调「留出余量」，而不是卡着容量上限去配置。

## 7. 常见误区

### 误区一：显存容量和显存带宽是同一回事

不是。容量（GB）回答「装不装得下」，带宽（GB/s）回答「搬得快不快」。**两者作用完全不同，且不能相互替代。** 容量大带宽低，就是「能跑但慢」；容量小带宽高，就是「快，但装不下更大的模型」。

### 误区二：显存够大，运行就一定快

不对。容量只解决「能不能装下」，速度主要由带宽决定。**一块大容量但低带宽的显存，装上模型后可能出词很慢。**「够大」和「够快」是两条独立的判断。

### 误区三：显存里只有模型

不是。显存里至少还有**上下文缓存**（随对话长度增长）、**系统与桌面环境**、以及**其他程序**的占用。所以标称显存和「能给模型用的显存」不是一个数。这解释了为什么「模型体积小于显存容量」并不保证长期稳定运行。

### 误区四：核心数越多，模型就一定能跑

核心数（无论 CUDA Core 还是 Tensor Core）属于算力范畴，影响的是「算得多快」。**它不能解决「装不下」的问题。** 如果模型体积超过可用显存，再多的核心也无法让它运行起来。判断能否加载，第一眼要看的是显存容量。

### 误区五：显存带宽越高，模型就越小

因果完全说反了。带宽是「搬运速度」，和模型体积没有任何关系。模型体积由**参数量和每个参数的位数**决定 —— 那是 Day 3 的内容。带宽再高，也不会让模型变小一点。
