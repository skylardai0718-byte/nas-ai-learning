# 第五十四课：Local AI 软件栈

> 本课的一句话结论：**本地 AI 不是一个软件，而是一条链路：模型是「知识」，推理引擎负责让它跑起来，API 是对外的接口，应用才是你看到的界面 —— 每一层各司其职。**

## 1. 今天学习什么

今天要掌握 3 个概念，以及它们组成的四层结构：

1. **推理引擎（Inference Engine）**：让模型在实际硬件上运行起来的程序。
2. **API**：对外的标准接口，让别的程序能调用推理引擎。
3. **应用（Application）**：你直接使用的界面。

你今天要建立的核心结构是：

```text
Model  →  推理引擎  →  API  →  应用
模型     真正干活的     对话    你看到的
文件     计算程序       接口    界面
```

以及几个常见工具的定位：

```text
llama.cpp   →  推理引擎
Ollama      →  推理引擎 + 管理 + 简单 API
LM Studio   →  推理引擎 + 图形界面
Open WebUI  →  应用（通过 API 连接引擎）
```

**今天只讲「谁扮演什么角色」，不讲怎么安装、也不讲具体界面长什么样。**

## 2. 为什么要学

你可能已经在网上见过这些名字：Ollama、LM Studio、llama.cpp、Open WebUI。它们经常被混在一起说，让人搞不清到底哪个是哪个、需要装几个。

不理解这条链路，你会遇到这些问题：

- 为什么装了界面之后，还要另外装一个「引擎」？
- 为什么有些工具既能下载模型又能聊天，有些只管其中一个环节？
- 为什么应用能换，而模型不用换？
- 为什么同一个模型可以在不同软件里跑？
- 为什么「装了软件」不等于「模型已经就绪」？

不学这一课，你会把这些工具当成一堆互相竞争的产品，靠试错去拼凑，而看不清它们其实是**一条链上的不同环节**。

**这一课把前三天串起来**：你已经知道模型要装进显存、体积由位数决定 —— 今天讲的是「谁负责把模型加载进去、谁负责把它呈现给你」。

## 3. 小白解释

### 3.1 模型是一个文件，它自己不会运行

这是最容易误解的一点：

```text
模型文件  →  只是一堆参数数据
          它不会自己动起来
          要有人「加载它、驱动它、把它算出来」
```

用类比：**模型文件像一本菜谱。** 菜谱本身不会变出一道菜 —— 你需要厨房、需要厨师、需要有人按照菜谱操作。

```text
菜谱      →  模型文件
厨师      →  推理引擎
传菜的窗口 →  API
餐厅、菜单 →  应用
```

**所以「下载了模型」和「能用模型」之间，还差好几个环节。**

### 3.2 推理引擎：真正干活的那一层

**推理引擎（Inference Engine）** 是负责让模型跑起来的程序。它要做的事包括：

```text
· 把模型加载到显存 / 内存
· 按模型的运算方式进行计算
· 管理上下文（对话历史）
· 输出生成的文字
```

同一件事，可以有不同的引擎去做 —— 这就像同一本菜谱，不同厨房都能做。所以**模型和引擎是可以分开的**：模型不变，换一个引擎也能跑。

### 3.3 API：让别的程序能调用它

引擎自己跑起来了，但它是「干活的」，不一定是「好用的」。这时候需要一个接口，让别的程序能把需求递进去、把结果取出来。

```text
应用  →（把问题发给 API）→ 引擎  →（算完）→ API  →（返回答案）→ 应用
```

**API（应用程序接口）** 就是这层「传菜窗口」。它的意义在于**解耦**：

```text
没有 API：应用必须自己懂模型怎么跑
有 API：  应用只需要会「递问题、收答案」
```

**这就是为什么界面和引擎可以来自不同的项目** —— 它们通过 API 对接，互不需要了解内部细节。

### 3.4 应用：你真正看到的东西

**应用（Application）** 是最终给你用的那一层，通常是一个对话界面。它做的事情包括：

```text
· 显示对话框
· 记录你的对话
· 通过 API 把问题发给引擎
· 把引擎的回答显示出来
```

**关键区分**：应用**自己不运行模型**。它只是界面和调度 —— 真正把模型算出来的是引擎。

所以：

> **换一个应用，模型不用重新下载；换一个模型，应用也不用换。** 这正是分层的价值。

## 4. 技术解释

### 4.1 四层各自的职责

| 层 | 职责 | 是否必需 | 换了它会怎样 |
|---|---|---|---|
| Model | 提供参数与能力 | 必需 | 换模型＝换「知识」与能力 |
| 推理引擎 | 让模型在硬件上运行 | 必需 | 换引擎＝换实现方式，模型可不变 |
| API | 提供标准调用接口 | 视情况 | 换接口＝换通信方式 |
| 应用 | 提供使用界面 | 视情况 | 换应用＝换使用体验 |

**说明「是否必需」这一列**：如果引擎自带界面（比如一个桌面应用把引擎和界面打包在一起），那 API 和应用就是它内部的一部分，不需要你单独配置。这解释了为什么有的工具「装一个就够用」—— 因为它把几层打包在了一起。

### 4.2 常见工具的定位

```text
llama.cpp   →  推理引擎
              偏底层，直接负责把模型跑起来

Ollama      →  推理引擎 + 模型管理 + 一个简单的 API
              把「跑模型」这件事打包得更省事

LM Studio   →  推理引擎 + 图形界面
              把整套流程做成一个桌面应用

Open WebUI  →  应用
              一个对话界面，通过 API 连接到引擎
```

**必须强调的两点边界**：

1. **本课不涉及安装与配置**，也不描述这些工具的具体界面或功能细节 —— 它们都在持续演进，细节不是学习重点。
2. **这些工具的定位可能随发展而变化**，一个工具也可能覆盖多层。所以要记住的是**分层的思想**，而不是背诵某工具「属于第几层」的固定答案。

### 4.3 为什么分层是有意义的

如果没有分层，整个系统会耦合在一起：

```text
不分层：换个界面 → 模型和计算逻辑都要跟着改 → 麻烦且易错
分层：  换界面 → 通过 API 对接 → 引擎和模型都不用动
```

分层带来的实际好处：

- **可替换**：界面不满意可以换，模型不用重下。
- **可组合**：同一个引擎可以同时服务多个应用。
- **可理解**：出问题时能定位在哪一层 —— 是模型装不下，还是引擎没启动，还是应用连不上 API。

**最后一点尤其重要**：分层不只是架构设计，也是**排查的思路**。这和我们前几周学过的分层排查（硬件 / 系统 / 应用 / 网络）是同一个道理。

## 5. 类比

把本地 AI 想象成一家**餐厅**：

- **模型文件是菜谱**：记录着怎么做菜，但本身不会做菜。
- **推理引擎是厨房和厨师**：按照菜谱真正把菜做出来。菜谱再好，没有厨房也吃不上。
- **API 是传菜窗口**：前厅和后厨之间递菜的地方。前厅不需要知道后厨怎么运作。
- **应用是餐厅前厅和菜单**：你看到的、点菜的地方。顾客只和前厅打交道。
- **显存是厨房台面**：食材必须摆在上面才能加工（呼应 Day 2）。

这个类比能解释什么：

**它解释了为什么「换个菜单，不用重开厨房」。** 你可以在同一家餐厅换一份菜单（换应用），后厨和菜谱都不用动 —— 因为中间隔着传菜窗口（API）。

它也解释了为什么「有了菜谱还不能吃饭」：**菜谱只是文件，必须有人、有设备把它执行起来。** 这正是「下载了模型≠能用模型」的原因。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：想让 NAS 上有一个能聊天的界面**

```text
需要：模型（提供能力）+ 推理引擎（让它跑）+ 应用（给你界面）
三者都到位，才能真正开始用
```

**这个判断的边界是**：本课只讲「需要哪几层」，不涉及「具体怎么装」。而且能否跑得动，还取决于前三天讲的容量、体积等因素。

```text
判断：需要模型 + 引擎 + 应用三层
它没告诉你：这台 NAS 的内存显存是否装得下这个模型
```

**场景二：已经装了一个聊天界面，但提示连不上**

这时要按分层去排查：

```text
是引擎没启动？        → 看引擎那一层
是 API 地址配错了？   → 看接口那一层
是模型没加载完？      → 看模型那一层
```

**判断的边界**：分层能帮你**定位方向**，但具体是哪个原因，需要实际检查 —— 本课不提供排查命令。

**场景三：想换一个更好用的界面**

```text
换应用  →  模型和引擎不用动，只要新界面能连上 API
```

**判断的边界**：这个结论成立的前提是**分层清晰、通过 API 对接**。如果原来的工具把各层紧紧地捆在一起（引擎、界面打包成一个整体），换界面可能就没这么简单了。

### 6.2 四层结构一览

| 层 | 角色 | 常见工具（举例） | 换掉它的影响 |
|---|---|---|---|
| Model | 提供知识与能力 | 各类模型文件 | 能力与体积变化 |
| 推理引擎 | 让模型真正跑起来 | llama.cpp、Ollama、LM Studio | 实现方式变化，模型可复用 |
| API | 提供标准接口 | 由引擎或中间层提供 | 通信方式变化 |
| 应用 | 提供使用界面 | Open WebUI 等界面 | 使用体验变化 |

### 6.3 为什么「装了一个软件」还不等于「能用了」

一个完整的可用状态，需要这几件事同时成立：

```text
① 有模型文件        →  而且是能装下的那个版本
② 引擎能启动        →  并且识别到你的硬件
③ 模型成功加载      →  体积没有超过可用显存
④ 应用能连上 API    →  地址、端口配对正确
```

**这四步里任何一步没到位，表现都是「用不了」** —— 但原因完全不同。分层理解的价值就在这里：它让你知道该往哪一层找问题，而不是笼统地觉得「AI 坏了」。

## 7. 常见误区

### 误区一：应用层自己运行模型

不对。应用只提供界面和调度 —— 它把你的问题通过 API 发给引擎，然后显示引擎返回的结果。**真正把模型算出来的是推理引擎。** 这也是为什么界面可以换、模型不用重下：它们本来就是两层。

### 误区二：模型和推理引擎是同一个东西

不是。模型是参数文件（「知识」），推理引擎是让这些参数运行起来的程序（「执行者」）。**同一个模型可以被不同的引擎加载**，同一个引擎也能加载不同的模型。混为一谈，就会以为「换个软件就得重新下载模型」。

### 误区三：装了 Ollama 就自动有了聊天界面

不一定。不同工具打包的层数不一样：有的把引擎和界面做在一起，有的只提供引擎和 API。**「装了某个软件」之后你到底拥有了哪几层，取决于它打包了什么** —— 不能一概而论，也不该凭软件名字去猜。

### 误区四：模型越大，应用界面就会越好用

混淆了两层。模型决定「能力」，应用决定「使用体验」。**界面好不好用和模型大小没有关系** —— 一个体验很好的界面可以搭配一个很小的模型，一个很小的界面也能连上很大的模型。这两件事要分开评价。

### 误区五：分层只是理论，实际用起来没差别

有实际差别。分层让你能做三件事：**换掉某一层而不动其他层**、**同时让多个应用共用一个引擎**、以及**出问题时定位到具体是哪一层出错**。尤其是第三点 —— 如果所有东西糊成一团，你只能靠猜。分层本身就是排查工具。

## 8. 知识地图

前三天讲「硬件和模型」，今天讲「它们之间的软件」。

```text
Local AI
├── 硬件                    （Day 1–3）
│   ├── CPU / GPU / NPU
│   ├── VRAM / 带宽
│   └── 模型体积与量化
├── 软件栈                  ← 今天在这里
│   ├── Model               （提供能力）
│   ├── 推理引擎            （让它跑起来，如 llama.cpp）
│   ├── API                 （对外接口）
│   └── 应用                （使用界面，如 Open WebUI）
└── 综合判断                （Day 5）
    └── 7B Q4 / 8GB VRAM
```

本课与其他课的连接：

```text

     ↓
Week 11 Day 4  →  软件栈：模型由谁加载、由谁呈现（本课）
     ↓
Week 11 Day 5  →  综合判断 7B Q4 / 8GB VRAM

```

今天只需要真正记住一句话：

> **本地 AI 是一条链：模型是知识，推理引擎让它跑起来，API 是对外接口，应用是你看到的界面** —— 分层让你能替换某一环、复用其他环，也让「用不了」时知道该往哪一层找。
