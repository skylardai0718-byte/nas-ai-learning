# 第三十二课：Docker、Image 与 Container

> 本课的一句话结论：**镜像是硬盘上一份只读的模板，容器是从这份模板启动出来的运行实例 —— 模板不会自己运行，只有容器才真正占用 CPU 和内存。**

## 1. 今天学习什么

今天要掌握 3 个概念：

1. **Docker**：目前最常用的容器工具，负责「打包」和「运行」两件事。
2. **镜像（Image）**：只读模板，包含应用和它的全部依赖。
3. **容器（Container）**：从镜像启动起来的一个运行实例。

你今天要建立的核心结构是：

```text
镜像（Image）       容器（Container）
只读模板     ──启动──→   运行实例
```

以及一条必须记牢的数量关系：

```text
一个镜像   →   可以启动出   很多个容器
                                  ↑
                  反过来不成立：一个容器只来自一个镜像
```

```text
Image  N  ──→  Container 1
          ──→  Container 2
          ──→  Container 3
```

## 2. 为什么要学

昨天讲了「隔离」这个思路：给每个应用一个独立的小环境。

但紧接着有三个很自然的问题：

**「这个小环境具体是什么东西？存在哪里？」「它怎么变成真正在跑的程序？」「我下载的那个东西，到底是模板还是运行中的程序？」**

这就是今天要回答的。

不理解镜像和容器的区别，会遇到这些问题：

- 为什么下载一个服务时，下载的是一个「镜像」，但它还没在运行？
- 为什么同一个镜像可以启动出好几个实例，它们之间会不会互相影响？
- 为什么「删除容器」和「删除镜像」是两个不同的操作？
- 为什么有时候容器删了，镜像还在，磁盘空间没释放？
- 为什么有人说 Docker「不是虚拟机」，它们的区别到底在哪？

**这是本周最关键的一课。** 镜像和容器的区分没建立起来，后面的卷、端口、网络都会讲不清 —— 因为它们全都在描述「容器」这个对象。

## 3. 小白解释

### 3.1 Docker 做两件事

**Docker** 是目前最常用的容器工具。它的工作可以概括成两步：

```text
第一步：打包
  把应用 + 它需要的全部依赖，做成一个只读的模板
        ↓
第二步：运行
  从这个模板启动一个真正跑起来的实例
```

就这两件事。听起来简单，但整个生态都建立在这两步之上。

用类比：

```text
打包  =  写好食谱，并把食材按量分装好，封成一个料理包
运行  =  拿这个料理包，真正开火做出一份菜
```

**「料理包」和「做出来的菜」是两个不同的东西** —— 这就是今天要讲的两个核心对象。

### 3.2 镜像：硬盘上的一份模板

**镜像（Image）** 是那个「料理包」。

它的特点：

```text
只读        →  一旦做好，内容就不能改
静止的      →  它不在运行，不占用 CPU
可以被复制  →  可以下载、上传、共享给别人
包含依赖    →  应用需要的东西全都在里面
```

**镜像存在硬盘上。** 一个镜像就是一堆文件，它描述的是「这个应用该长什么样」。

**请特别注意：镜像不在运行。** 它像一张蓝图纸，而不是造好的房子。

### 3.3 容器：真正跑起来的那个

**容器（Container）** 是从镜像启动出来的实例。

```text
镜像  ──启动──→  容器
（模板）          （实例）
```

它的特点：

```text
运行中      →  有进程在跑，占用 CPU 和内存
可读写      →  运行期间可以在里面产生新文件
一次性的    →  删掉之后，里面的改动默认一起消失（第 33 课详讲）
来自镜像    →  每个容器都基于某个镜像
```

**所以「下载了一个镜像」不等于「服务已经在跑」。** 镜像下载完，什么都不会发生；只有从它启动出容器，服务才真正开始运行。

### 3.4 一个类比：模具与蛋糕

这是本课最重要的一个类比：

```text
镜像  =  模具 + 配方
容器  =  用这个模具真正烤出来的一个蛋糕
```

它解释了很多事：

- **模具可以做出很多个蛋糕** —— 一个镜像可以启动很多个容器。
- **模具不会自己变成蛋糕** —— 镜像不会自己运行。
- **蛋糕坏了，模具还是好的** —— 容器出问题，删掉重新启动一个就行，镜像不受影响。
- **改模具要重新做，不影响已做好的蛋糕** —— 镜像更新后，已有的容器还在用旧的那一份。
- **模具放在柜子里不占火力，蛋糕在烤箱里占地方** —— 镜像不占 CPU，容器占。

**这个类比解释不了的**：它不能说明「容器里的进程其实就是你 NAS 上的一个普通进程」。这一点需要技术解释，不能靠类比。

## 4. 技术解释

### 4.1 Docker 的定位

Docker 不是一种新的操作系统，也不是一台虚拟机。它是一套**管理容器**的工具，主要提供四件事：

```text
1. 构建   把应用和依赖打包成镜像
2. 分发   把镜像传输到别的机器（通过镜像仓库）
3. 运行   从镜像启动容器
4. 管理   查看、停止、删除容器和镜像
```

**「镜像仓库（Registry）」** 是存放镜像的地方，最常用的是公共的 Docker Hub。你从教程里看到的「下载某个镜像」，通常就是从这类仓库拉取。

### 4.2 镜像的构成

一个镜像由若干**层（Layer）**叠加而成。每一层是构建过程中的一步：

```text
第 1 层：基础的操作系统环境（精简版）
第 2 层：装上运行环境
第 3 层：装上第三方库
第 4 层：放上应用本身的代码
```

**层是可以复用的。** 如果两个镜像的前三层完全一样，它们会共享这部分内容，不会各存一份。这也是为什么镜像的磁盘占用往往比你想的少。

**层是只读的。** 一旦构建完成，就不能修改 —— 想改就得加一层新的，或者重新构建。

**为什么要理解「层」？** 因为当你看到「镜像占了多少空间」和「容器产生了新数据」时，就能分清哪部分属于模板、哪部分属于运行实例。

### 4.3 容器运行时的可写层

容器启动时，Docker 会在镜像的最上面加一个**可写层（Writable Layer）**：

```text
┌─────────────────────────────┐
│  可写层    ← 容器运行中产生的新文件    │  ← 属于容器，随容器删除而消失
├─────────────────────────────┤
│  只读层    ← 来自镜像的一切           │  ← 属于镜像，容器删了它还在
├─────────────────────────────┤
│  只读层                               │
├─────────────────────────────┤
│  只读层                               │
└─────────────────────────────┘
```

**这张图是本周最重要的图之一**，它一次解释了三件事：

1. 为什么容器可以「改文件」而镜像不变（改动都落在最上面的可写层）。
2. 为什么删掉容器后，运行期间写的文件会消失（可写层跟着容器一起没了）。
3. 为什么数据必须放到容器外（第 33 课的卷和绑定挂载，就是为了解决这一层会消失的问题）。

### 4.4 镜像与容器的数量关系

```text
一个镜像  →  可以启动  0 个、1 个、或多个容器
一个容器  →  一定来自 1 个镜像
```

**为什么一个镜像要启动多个容器？** 常见场景：

- 同一个服务跑两个实例，分担访问压力。
- 同一个镜像，用不同的配置（不同的环境变量）各起一个，做不同的事。
- 测试新配置时，另外起一个，不影响正在服务的那个。

**多个容器之间默认是互相隔离的**（第 31 课讲的隔离），它们共享同一个镜像，但运行时的改动各在各的可写层里，互不可见。

### 4.5 三个操作，三个不同的对象

这三个操作很容易混，必须分清它们各自作用在谁身上：

| 操作（概念层面） | 作用对象 | 结果 |
|---|---|---|
| 下载 / 构建 | 镜像 | 硬盘上多了一份模板 |
| 启动 / 停止 | 容器 | 运行实例开始了或停下了 |
| 删除容器 | 容器 | 实例和它的可写层一起消失，镜像还在 |
| 删除镜像 | 镜像 | 模板消失，但前提是没有容器还在用它 |

**两个最常见的困惑：**

- **「我删了容器，磁盘空间怎么没怎么释放？」** 因为镜像还在 —— 镜像通常才是占空间的大头。容器删了只是把可写层清掉了。
- **「为什么删不掉镜像？」** 因为还有容器（哪怕是已停止的）在引用它。要先删掉容器，才能删镜像。

### 4.6 一条示例命令

```bash
docker run 某个镜像名
```

**这条命令不需要背，只需要理解它在概念上做了什么：**

```text
docker run 某个镜像名
     ↑        ↑
   运行的动作  从哪个模板

概念含义：从「某个镜像」启动「一个新的容器」
                            ↑
                运行的是容器，不是镜像
```

命令名叫 `run` 而不是 `start-image`，正是为了提示你：**被运行的是容器**。同一个镜像每执行一次，就多一个容器。

**它没有告诉你什么：** 这条命令不会说明容器启动后在做什么、数据放在哪里、能不能被外部访问。那分别是第 33、34 课的内容。

## 5. 类比

把镜像和容器想象成**模具与蛋糕**：

- **镜像是模具加配方**：一套完整的设计，规定了「用这个做出来的东西长什么样」。模具是静止的，放在柜子里不会自己动。
- **容器是用模具做出来的蛋糕**：真正存在、占地方、可以被享用。
- **一个模具能做很多个蛋糕**：一个镜像可以启动很多个容器。
- **做坏的蛋糕扔掉，模具还是好的**：容器出问题就删掉重来，镜像完全不受影响。
- **想改配方得重新做模具**：镜像更新需要重新构建，而已经做好的蛋糕不会因此改变。
- **蛋糕上的奶油装饰是可以改的**：容器运行期间的改动落在可写层，不影响模具。

**这个类比能解释什么：**

| 类比中的事 | 对应的技术事实 |
|---|---|
| 模具放在柜子里不用火 | 镜像不占 CPU、不在运行 |
| 一个模具做多个蛋糕 | 一个镜像启动多个容器 |
| 蛋糕坏了模具没事 | 容器可随时删除重建 |
| 蛋糕装饰可以改 | 容器有可写层 |
| 改配方要重做模具 | 镜像更新需要重新构建 |
| 房间里的蛋糕被清走，模具还在柜子里 | 删容器不删镜像 |

**这个类比解释不了的：** 它不能说明「容器内部其实还是宿主系统上的一个普通进程」。蛋糕和模具是两个物理对象，而容器和镜像的关系更接近「进程与程序文件」的关系。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：从教程复制了一条启动命令，执行后「什么都没发生」**

```text
执行命令
   ↓
屏幕上一堆下载进度
   ↓
下载结束，命令返回
   ↓
你以为服务已经在跑了
   ↓
浏览器打开，打不开
```

**判断：先分清此刻你到底完成了哪一步。** 如果只是「拉取了镜像」，那服务确实还没开始运行 —— 镜像只是模板，不会自己跑。**正确的判断顺序是：先确认镜像在不在，再确认有没有从它启动出容器，最后才谈访问。** 把这三步分开，能省下大量「为什么打不开」的困惑。

**场景二：想升级服务，犹豫该动哪个**

```text
升级的通常做法：
  1. 拿到新版本的镜像
  2. 删掉旧容器
  3. 用新镜像启动一个新容器
```

**判断：升级动的是「容器」，换来的是「镜像」。** 这里立刻引出一个关键问题：**旧容器里的数据怎么办？** 如果数据就存在容器的可写层里，第 2 步会把它一起删掉。这正是第 33 课要解决的 —— 升级之前，必须先确认数据放在容器外面。

**场景三：磁盘快满了，想清理**

```text
情况 A：容器很多，但大多已停止
情况 B：镜像很多，很多是从没用过的
```

**判断：这两件事要分开处理。** 已停止的容器仍然占着它们的可写层；没用的镜像往往占得更多。清理前要先想清楚：**哪些镜像还在被容器引用（不能直接删），哪些容器的数据还没持久化（删了就没了）。** 不清不楚地清理，是自托管新手最常见的「数据丢失」原因之一。

### 6.2 概念与现象的对照

| 你观察到的现象 | 对应的对象 | 说明 |
|---|---|---|
| 下载了很久，但服务没启动 | 镜像 | 只是拿到了模板 |
| 服务正常访问，重启 NAS 后还在 | 容器 | 运行实例存在（是否自动启动另说） |
| 删掉容器后配置全丢 | 容器的可写层 | 数据没放到容器外 |
| 删掉容器后磁盘没释放多少 | 镜像仍在 | 镜像通常是占用大头 |
| 同一个镜像起了两个实例，互不干扰 | 两个容器 | 各自独立的可写层 |
| 镜像更新了，但服务行为没变 | 旧容器 | 容器仍基于旧的镜像 |

**表格要读出的重点**：同一件「我以为是一件事」的事，往往牵扯到两个不同的对象。**分清对象，才能分清该处理哪一个。**

### 6.3 本课与「能不能用」的关系

```text
你现在能回答的问题：
✓ 镜像和容器分别是什么
✓ 一个镜像能起几个容器
✓ 为什么下载完镜像服务还没开始跑
✓ 为什么删了容器磁盘空间没释放

你现在还不能回答的问题：
✗ 容器里的数据怎么才不会丢（第 33 课）
✗ 我在浏览器里怎么访问容器里的服务（第 34 课）
✗ 两个容器之间怎么互相找到（第 35 课）
```

## 7. 常见误区

### 误区一：认为镜像是「正在运行的应用」

这是本课最需要纠正的一条。镜像是硬盘上的只读模板，它不运行、不占 CPU、也不产生数据。真正在运行的是从镜像启动出来的**容器**。很多「为什么我装好了却打不开」的困惑，根源就是把「下载了镜像」当成了「服务已经在跑」。

### 误区二：认为一个镜像只能启动一个容器

不是。同一个镜像可以启动任意多个容器，每个容器有自己独立的运行状态和可写层，互不干扰。这正是「同一个服务跑多个实例」和「同镜像不同配置」得以实现的原因。

### 误区三：把「删除容器」和「删除镜像」混为一谈

这是两个不同的操作，作用在两个不同的对象上。删容器只清掉运行实例和它的可写层，镜像仍然在硬盘上；删镜像要等没有容器再引用它才能进行。混为一谈的后果通常是：以为清理干净了，磁盘却没释放；或者想删镜像却删不掉，不知道原因。

### 误区四：以为容器里改的东西会永久保留

容器运行期间产生的文件都写在最上面的可写层，而这一层是**跟着容器走的**。删掉容器，可写层一起消失。想让数据活下来，必须把它放到容器外面 —— 这是明天一整课的内容，也是自托管里最容易造成数据丢失的一环。

### 误区五：认为 Docker 就是「更轻的虚拟机」

不是。虚拟机模拟的是一整台计算机，里面跑着完整的操作系统；容器里的进程**本质上仍然是你 NAS 上的一个普通进程**，只是被隔离机制「蒙住了眼睛」，让它以为自己独占一台机器。所以容器启动快、开销小，但也因此和宿主机共享内核 —— 这既带来好处（轻），也带来限制（依赖内核能力的功能未必可用）。
