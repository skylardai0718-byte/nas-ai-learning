# 第三十一课：依赖、环境一致性与隔离

> 本课的一句话结论：**软件装不上、跑不对，绝大多数时候不是软件坏了，而是它需要的东西（依赖）在你这台机器上不齐或者版本不对 —— 容器化的思路就是让每个应用带着自己需要的一切，不与系统互相干扰。**

## 1. 今天学习什么

今天要掌握 3 个概念：

1. **依赖（Dependency）**：一个程序要跑起来，必须先具备的其他东西。
2. **环境一致性（Environment Consistency）**：让同一个软件在不同机器上面对同一套依赖。
3. **隔离（Isolation）**：不去改动你的系统，而是给每个应用一个独立的小环境。

你今天要建立的核心结构是：

```text
一个应用要能跑起来
├── 应用本身的代码
├── 依赖：运行环境（如某个语言版本）
├── 依赖：第三方库（如某个图像处理库）
└── 环境：配置、时区、编码等
        ↓
   任何一项对不上
        ↓
   装不上 / 起不来 / 行为异常
```

以及本周会一直用到的一条主线：

```text
问题：软件的依赖太容易互相冲突
        ↓
思路：隔离（各自带各自的东西）
        ↓
工具：Docker（本周第 32 课开始正式讲）
```

**注意：今天不讲具体命令。** 今天只把「为什么需要容器」这件事讲透 —— 如果这一步没想明白，后面学命令就只是背命令。

## 2. 为什么要学

你可能会想：我又不写程序，为什么要关心「依赖」？

因为你自托管的每一个服务，本质上都是一个别人写好的程序。它装不上的时候，报错信息里出现的几乎全是依赖问题。

不理解依赖和环境一致性，会遇到这些问题：

- 为什么同一个教程，别人照着做能成，我照着做就报错？
- 为什么软件提示「缺少某某组件」，装了之后又提示「版本不对」？
- 为什么升级了系统里某个东西之后，另一个本来正常的服务反而坏了？
- 为什么有的服务要求「必须先装 Python 3.11」，而我系统里是 3.10？
- 为什么卸载一个服务之后，系统里还残留一堆东西，甚至别的服务也被影响了？

**这一课是所有 Docker 内容的地基。** 后面你会学到镜像、容器、卷，它们全都是为了解决今天提出的这些问题而存在的。

## 3. 小白解释

### 3.1 什么是「依赖」

**依赖**就是「这个程序要跑起来，得先有别的什么东西」。

生活里的例子：

```text
要煮一锅饭
├── 依赖：米
├── 依赖：能用的电饭锅
└── 依赖：水
少任何一样，饭都做不成
```

软件也一样：

```text
某个照片管理服务
├── 依赖：某个版本的运行环境
├── 依赖：几个第三方代码库
└── 依赖：一个数据库
```

**依赖的特点：它是有版本的。** 「有 Python」不够，得是「有 Python 3.11」；「有那个库」不够，得是「那个库的 2.1 版」。版本不对，程序就可能不工作。

**依赖还有第二个特点：它会互相冲突。** 服务甲需要某个库的新版，服务乙需要同一个库的旧版。如果两个都装在同一个系统里，总有一个要失望。

### 3.2 什么是「环境一致性」

**环境一致性**是说：同一个软件，无论在谁的机器上运行，面对的依赖应该是同一套。

为什么这件事很难？因为每台机器的状态都不一样：

```text
开发者的电脑
├── 系统是某个版本
├── 装过一堆开发工具
└── 某个库刚好是程序需要的版本

你的 NAS
├── 系统是另一个版本
├── 装过别的服务
└── 那个库是另一个版本，或者根本没装
```

于是就有了那句程序员的口头禅：**「在我机器上明明能跑啊。」**

这句话不是推卸责任，而是在描述一个真实的现象：**软件的运行结果，取决于它所处的环境，而不只取决于软件本身。**

**传统安装的做法**是把软件装进系统，让它使用系统里的依赖。这样做的问题是：这个软件和系统、和其他软件，从此绑在了一起。你动了其中一个，可能就影响了另一个。

### 3.3 什么是「隔离」

**隔离**换了个思路：**不去动系统，而是给每个应用一个独立的小环境，让它带着自己需要的一切。**

```text
传统安装
  应用 A ─┐
  应用 B ─┼──→ 共用同一个系统环境（互相影响）
  应用 C ─┘

隔离安装
  应用 A ──→ [自带依赖的小环境 A ]
  应用 B ──→ [自带依赖的小环境 B ]   互不干扰
  应用 C ──→ [自带依赖的小环境 C ]
```

用类比：

```text
传统安装   =  把家具直接搬进你家客厅，和你原有的东西混在一起，还占地方
隔离安装   =  搬进来一个个集装箱，家具都装在箱子里，
              箱子之间互不影响，搬走时整个箱子一起搬走
```

**隔离带来的三个好处：**

1. **不再冲突**：两个应用要同一个库的不同版本？各自带各自的，互不干涉。
2. **环境可复制**：这个「小环境」可以被完整复制，所以别人的机器上也能得到同样的结果。
3. **清理干净**：不要了就把整个小环境扔掉，系统里不留残余。

### 3.4 隔离不是什么

隔离听起来很美好，但要说清它的边界：

```text
隔离解决的：依赖冲突、环境不一致、清理不干净
隔离不解决的：软件本身的 bug、配置写错、硬件不够用
```

- 如果程序本身有缺陷，放进隔离环境里依然有缺陷。
- 如果密码填错了、端口填错了，隔离帮不了你。
- 如果内存不够，再好的隔离也跑不动。

**隔离是「让环境变得可预测」，不是「让软件变得没问题」。** 这条边界要一直记住。

## 4. 技术解释

### 4.1 依赖的层次

软件依赖通常分成几层，从下往上：

| 层次 | 内容 | 例子 |
|---|---|---|
| 操作系统层 | 内核、系统库 | 系统的基础运行库 |
| 运行时层 | 语言运行环境 | 某种语言的解释器或虚拟机 |
| 库层 | 第三方代码包 | 图像处理库、数据库驱动 |
| 应用层 | 程序自己的代码 | 这个服务本身的文件 |
| 配置层 | 参数与数据 | 端口、时区、账号 |

**传统安装的问题在于：上面几层是共享的。** 两个应用如果对同一层提出不同要求，就会冲突。

### 4.2 为什么版本冲突几乎无解

假设两个服务都需要同一个库：

```text
服务甲  需要  库 v2
服务乙  需要  库 v1
```

在传统安装模式下，系统里只能选一个版本：

- 装 v1 → 服务甲坏了。
- 装 v2 → 服务乙坏了。
- 两个都装 → 绝大多数系统只允许一个库的一个版本被「全局」找到，所以实际上还是只能选一个。

**这不是配置技巧能绕过去的，而是「共享同一套依赖」这个前提本身带来的限制。** 要绕开它，就必须放弃「共享」—— 这就是隔离的动机。

### 4.3 环境一致性的三个层面

一致性可以分成三层来理解：

```text
1. 依赖一致：需要的东西种类和版本都一样
2. 配置一致：时区、编码、语言环境等设置一样
3. 行为一致：在相同输入下，得到相同结果
```

三层是递进的。依赖一致了，配置可能还不一致；配置一致了，行为也未必完全一致（还要看数据、硬件等）。

**所以「一致性」是一个程度问题，不是一个开关。** 容器化把前两层做到了高度一致，这已经解决了绝大多数「在我机器上能跑」的问题。

### 4.4 隔离的实现思路

隔离在技术上通常靠**命名空间（Namespace）**和**资源限制**这类机制实现：让一个进程「看不到」它不该看到的东西（别的进程、别的文件、别的网络），从而产生「它独占一台机器」的错觉。

**关键点：容器里的进程，本质上仍然是跑在你 NAS 上的一个普通进程。** 它不是一台独立的机器，只是被「蒙住了眼睛」。

这一点非常重要，因为它是第 32 课区分「容器」和「虚拟机」的基础。

### 4.5 隔离的代价

隔离不是免费的：

- **占空间**：每个隔离环境都要带自己的一份依赖，不共享，所以比传统安装占更多磁盘。
- **多一层抽象**：出问题时，需要判断是应用的问题，还是这层「打包」引入的问题。
- **学习成本**：多了一套概念和工具要理解。

**这就是权衡**：用一点磁盘空间和一层抽象的复杂度，换取「不再为依赖冲突头疼」。对自托管场景来说，这笔交换通常是划算的。

## 5. 类比

把软件安装想象成**做饭**：

- **依赖是食材和厨具**：想做某道菜，得有对应的食材和锅。缺一样就做不成。
- **传统安装像合用一间公共厨房**：所有人共用一口锅、一套调料。你想做川菜要放花椒，别人要做甜点不能有花椒味 —— 冲突了。
- **环境不一致像「我这口锅的火力和你那口不一样」**：同一个菜谱，出来的结果不同。
- **隔离像每人一个独立的料理台加一套自己的厨具**：你带你的花椒，他带他的糖。各做各的，互不影响。用完把整个料理台搬走，厨房干干净净。
- **隔离的代价像每个料理台都要配一整套厨具**：占地方，但省心。

**这个类比能解释什么：**

| 类比中的事 | 对应的技术事实 |
|---|---|
| 公共厨房里调料冲突 | 同一个库的不同版本不能共存 |
| 同一菜谱火力不同结果不同 | 环境不一致导致行为不一致 |
| 独立料理台 | 隔离的运行环境 |
| 料理台要各配一套厨具 | 隔离占更多磁盘 |
| 搬走料理台厨房就干净 | 删除环境不留残余 |
| 食材坏了做不出好菜 | 隔离解决不了软件本身的 bug |

**这个类比解释不了的：** 它不能说明「隔离环境里跑的其实还是你机器上的一个普通进程」这件事 —— 那需要技术解释，不能靠类比。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：照着教程装服务，卡在某一步装不上**

传统安装一个自托管服务时，经常要依次装：系统组件 → 语言运行环境 → 第三方库 → 应用本身。

```text
教程写着：先装某个运行环境
你装上后发现：教程用的是新版本，你系统里只能装到旧版本
        ↓
后面的步骤全部报错
        ↓
你开始不停地搜索「某错误怎么解决」
        ↓
折腾两小时后，系统里已经装了一堆不知道干什么的东西
```

**判断：这不是你不够聪明，而是「共享依赖」这个模式本身的脆弱之处。** 教程写得再详细，也无法预知你的系统里已经有什么。**这也是为什么你现在应该转向容器化的安装方式。**

**场景二：升级了系统，另一个服务坏了**

```text
系统更新 → 某个共享的库被升级了
        ↓
依赖旧版本的服务 → 启动失败
```

**判断：这是「共享依赖」的典型后果。** 在容器化的模式下，这个服务自带它需要的旧版本，系统的更新不会波及它。

**场景三：想同时装两个类似的服务，它们要的版本不同**

```text
服务甲要库 v1，服务乙要库 v2
传统安装：只能二选一，或者花大量时间想办法共存
```

**判断：这一类需求，几乎就是容器化最擅长的场景。** 两个容器各自带各自的版本，同时运行，互不干扰。

### 6.2 三种安装方式的对比

| 维度 | 传统安装 | 容器化安装 | 手动编译安装 |
|---|---|---|---|
| 依赖装在哪里 | 系统里，全局共享 | 容器内部，各自独享 | 系统里，但路径可能自定义 |
| 是否影响系统其他部分 | 影响较大 | 基本不影响 | 影响中等 |
| 换一台机器要重做什么 | 重来一遍全部步骤 | 拉取同一个镜像即可 | 重来一遍，且更容易出错 |
| 卸载是否干净 | 常留残余 | 删除容器和镜像即可 | 常留残余 |
| 占用的磁盘 | 较少（共享依赖） | 较多（各带一份依赖） | 视情况 |
| 出问题时的排查难度 | 难，牵扯整个系统 | 相对聚焦在容器内 | 最复杂 |

**表格要读出的重点**：容器化并不是「各方面都更好」，它是在**牺牲一部分磁盘空间和一层抽象**的前提下，换取**环境一致性**。对自托管用户来说，这个交换的收益通常远大于代价。

```text

```

## 7. 常见误区

### 误区一：认为依赖只是「多装几个软件」

依赖不只是「有没有」，更是「版本对不对」。绝大多数依赖问题的实质是**版本不匹配**，而不是完全缺失。所以「我把能装的都装了」并不能解决问题，反而可能因为装错版本而让情况更糟。

### 误区二：把环境一致性理解成「统一操作系统」

环境一致性的意思是：让软件面对**同一套依赖和配置**，而不是让所有设备都用同一个操作系统。两台完全相同的系统，如果装的库版本不同，依然是不一致的。反过来，不同系统上跑同一个容器，反而可能得到一致的结果。

### 误区三：以为隔离能让软件本身变得更好

隔离只处理「环境」这一层。程序本身的 bug、写错的配置、不足的硬件，隔离一样都解决不了。把有缺陷的软件放进容器，它仍然有缺陷 —— 只是不再因为环境问题而额外出错。

### 误区四：觉得隔离没有代价

隔离的代价是真实的：每个应用各带一份依赖，磁盘占用明显增加；多了一层打包机制，出问题时多一层需要排查；概念变多，学习成本上升。了解代价，才能在「什么时候该用、什么时候不必用」上做出判断。

### 误区五：认为传统安装已经过时、没有价值

不是。传统安装依然适合很多场景：系统本身需要的组件、只有你自己用且不常升级的工具、对资源极度敏感的环境。容器化是一种**更适合「多个第三方服务共存」**的方式，而不是「唯一正确」的方式。工具的价值取决于场景。
