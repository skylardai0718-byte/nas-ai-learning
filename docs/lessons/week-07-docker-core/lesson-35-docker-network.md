# 第三十五课：Docker 网络

> 本课的一句话结论：**端口映射解决「外面的人怎么进来」，Docker 网络解决「容器之间怎么互相找到」—— 前者靠宿主机端口，后者靠容器名，两者的方向正好相反。**

## 1. 今天学习什么

今天要掌握 1 个新概念，并把整周串起来：

1. **Docker 网络（Docker Network）**：让多个容器处在同一个网络里，能用名字互相找到。

以及本周的完整链条（今天要闭卷画出来）：

```text
Image  镜像
   ↓  启动
Container  容器
   ↓  需要保存数据
Volume / Bind Mount  数据放在容器外
   ↓  需要被外部访问
Port Mapping  把里面的端口接到外面
   ↓  多个容器之间互相访问
Docker Network  用名字互相找到
```

## 2. 为什么要学

前面四天解决的都是「单个容器」的问题：它是什么、数据怎么留、怎么访问。

但现实中，一个完整的自托管服务往往不止一个容器：

```text
一个典型的组合
├── 应用容器（你访问的那个界面）
└── 数据库容器（应用把数据存进去）
```

**这两个容器之间要通信。** 应用需要告诉数据库「把这条记录存起来」，数据库要回应它。

于是出现一个新问题：

**「应用容器该用什么地址去访问数据库容器？」**

不理解 Docker 网络，会遇到这些问题：

- 为什么教程里让数据库地址填 `db`，而不是一个 IP？
- 为什么用了 `127.0.0.1` 就连不上另一个容器？
- 为什么容器重建之后，原本能连上的服务突然连不上了？
- 端口映射和 Docker 网络有什么区别，为什么两个都需要？
- 为什么有的容器之间「默认就能通」，有的却要专门建一个网络？

**今天是本周的收束课。** 概念讲完了，重点是把它们串成一条线。

## 3. 小白解释

### 3.1 一个很自然的错误：用 127.0.0.1

先看大多数人第一次会犯的错：

```text
应用容器要访问数据库，配置里填了：127.0.0.1
        ↓
连不上
```

**为什么？** 因为 `127.0.0.1` 的意思是「我自己」。

```text
在应用容器里，127.0.0.1 = 应用容器自己
                          ↑
                    不是数据库容器
```

每个容器都有自己的「自己」。填 `127.0.0.1`，等于在跟自己说话，当然找不到数据库。

用类比：

```text
你在自己家里喊「我在这里」
        ↓
隔壁房间的家人听不到
        ↓
因为「我」指的是喊话的人，不是家人
```

### 3.2 那么该填什么

正确做法是填**容器名**：

```text
应用容器的配置里写：db
                    ↑
              这是数据库容器的名字
```

**它的前提是：这两个容器在同一个 Docker 网络里。**

```text
同一个 Docker 网络
┌─────────────────────────────┐
│   应用容器  ──用名字──→  数据库容器  │
│      db 的地址就是「db」            │
└─────────────────────────────┘
```

**「用名字而不是用地址」这件事为什么重要？** 因为容器的地址是会变的 —— 容器重建一次，地址可能就变了。如果配置里写的是写死的地址，容器重建后配置就失效了。**名字是稳定的，地址不是。**

### 3.3 两种「访问」的方向

这是今天最需要分清的一点：

```text
端口映射    →   外面的人怎么进来
Docker 网络 →   容器之间怎么互相找到
```

画成图会更清楚：

```text
        外面（你的浏览器）
              │
              │  端口映射：8080:80
              ↓
        ┌──────────────┐
        │   应用容器     │
        └──────┬───────┘
               │  Docker 网络：用名字「db」
               ↓
        ┌──────────────┐
        │   数据库容器   │
        └──────────────┘
```

**两条通路各管一段。** 缺了端口映射，你进不去；缺了 Docker 网络，两个容器连不上。**它们不是替代关系，而是互补关系。**

### 3.4 为什么要有「网络」这个东西

你可能会问：为什么不能像端口映射那样，直接连过去？

因为容器之间需要一个共同的空间来「认识彼此」：

```text
Docker 网络的三个作用：
1. 提供一个共同的空间，让容器之间能通信
2. 提供名字解析：把容器名翻译成实际地址
3. 起到隔离作用：不在同一个网络里的容器互相看不见
```

**第 3 点尤其重要**：不同的服务如果放在不同的网络里，它们就互相不可见。这既减少了干扰，也减少了「一个服务出问题波及另一个」的可能。

## 4. 技术解释

### 4.1 Docker 网络的基本机制

Docker 网络在技术上是这样工作的：

```text
1. 每个网络是一个独立的虚拟网络
2. 接入同一网络的容器，各自分到一个内部地址
3. Docker 内置名字解析：容器可以直接用「容器名」访问同网络的其他容器
4. 不在同一网络的容器，默认无法通过名字或地址互相访问
```

**第 3 点是关键**：它相当于给容器网络内置了一个「通讯录」。你不需要知道对方的具体地址，说名字就行。

### 4.2 与宿主机网络的关系

需要区分三个层次：

| 层次 | 说明 |
|---|---|
| 容器内部网络 | 容器自己的网络空间，有独立的内部地址 |
| Docker 网络 | 若干容器共享的虚拟网络，容器之间用名字通信 |
| 宿主机网络 | NAS 所在的局域网（Week 4 学的 LAN） |

**关系是这样的：**

```text
宿主机（NAS）的局域网
   │
   │  端口映射（8080:80）
   ↓
容器内部网络 ── 通过 Docker 网络接到其他容器
```

**换句话说：端口映射是「从宿主机伸进容器」的那根管子；Docker 网络是「容器之间互连」的那张网。**

### 4.3 容器名为什么比地址可靠

```text
如果配置里写地址：
  数据库容器地址 172.x.x.x
  容器重建 → 可能分到新地址 → 配置失效
        ↓
  应用连不上数据库

如果配置里写名字：
  数据库容器名字 db
  容器重建 → 名字不变（只要你用同一个名字启动）→ 配置继续有效
```

**这就是「服务名」的意义：它把「连接目标」和「具体地址」解耦。** 这个概念在 Week 8 学 Compose 时还会更强地出现 —— Compose 里每个服务有一个名字，服务之间就用名字互相访问。

### 4.4 与宿主机通信的区别

一个常见的混淆是「容器怎么访问宿主机上的东西」和「容器怎么访问另一个容器」。这两件事不一样：

| 目标 | 怎么做 |
|---|---|
| 访问同一个 Docker 网络里的另一个容器 | 用容器名 |
| 访问宿主机（NAS）上的服务 | 通常用一个约定的特殊地址，具体以文档为准 |
| 被外部访问 | 做端口映射 |

**这三者不要混。** 尤其是第一和第二个：一个用名字，一个用特殊地址，写错了就连不上。

### 4.5 一条示例命令

```bash
docker run --network 某个网络名 某个镜像名
```

**不需要背，只需要理解它在做什么：**

```text
docker run  --network 某个网络名  某个镜像名
                  ↑
           把这个容器接进某个 Docker 网络

概念含义：让这个容器和该网络里的其他容器可以
          用名字互相找到。
```

**它没有告诉你什么：** 这条命令不会说明这个网络里还有哪些容器、它们的名字是什么、应用该填哪个名字。**这些信息要从服务文档和你的部署配置里找。**

### 4.6 本周知识链条的闭卷检查

请尝试不看上面，自己画一遍：

```text
Image → Container → Volume → Port → Network
```

对照一下每一环回答的问题：

| 环节 | 回答的问题 | 反过来说，缺了它会怎样 |
|---|---|---|
| Image 镜像 | 这个应用和依赖长什么样？ | 没有可复制的环境 |
| Container 容器 | 它现在跑起来了吗？ | 只是一个死模板 |
| Volume 卷 / 挂载 | 删掉它，数据还在吗？ | 升级一次丢一次数据 |
| Port 端口映射 | 我在浏览器里怎么访问？ | 服务在跑但进不去 |
| Network 网络 | 它怎么找到另一个容器？ | 应用连不上数据库 |

**这张表就是本周的骨架。** 能默写出来，就说明这一周的概念真的通了。

### 4.7 边界：Docker 网络不解决什么

```text
Docker 网络解决的：容器之间的连接、名字解析、隔离
Docker 网络不解决的：
  ✗ 外部怎么访问（那是端口映射的事）
  ✗ 数据会不会丢（那是卷的事）
  ✗ 应用本身的配置是否正确（那是环境变量的事）
  ✗ 跨主机的容器通信（那是更复杂的编排，超出本周范围）
```

**最后一条值得说明**：Docker 网络主要解决的是**同一台机器上**容器之间的通信。如果两个容器跑在不同的机器上，就需要更复杂的方案 —— 这不在本周范围内，知道有这个边界就够了。

## 5. 类比

把 Docker 网络想象成**一栋办公楼里的内部电话系统**：

- **容器是楼里的各个房间**：每个房间里有一个人（一个服务）。
- **网络是这栋楼的内部电话系统**：只有接入系统的房间之间才能互相拨号。
- **容器名是房间的名字**：「财务部」「档案室」—— 你拨名字，不用记分机号码。
- **地址是会变的，名字不会**：房间可能重新分配，但「档案室」永远叫档案室。
- **端口映射是大楼对外的门**：外面的人从大门进来，走的是另一条通路。
- **不在电话系统里的房间，互相打不通**：不同网络的容器默认互相不可见。
- **在自己房间里喊「我在这里」没用**：`127.0.0.1` 只指自己，不会传到隔壁。

**这个类比能解释什么：**

| 类比中的事 | 对应的技术事实 |
|---|---|
| 内部电话系统 | Docker 网络 |
| 拨名字而不是分机号 | 用容器名访问，不用 IP |
| 房间会重分配，名字不变 | 容器重建后地址变、名字可保持 |
| 大楼对外的门是另一条路 | 端口映射与 Docker 网络是两套通路 |
| 没接入系统的房间打不通 | 不在同一网络的容器不可见 |
| 在自己房间喊话传不出去 | 127.0.0.1 只指容器自身 |
| 不同楼层各有自己的电话系统 | 不同网络互相隔离 |

**这个类比解释不了的：** 它不能说明「宿主机上的服务该怎么访问」—— 那既不是打内部电话，也不是走大门，而是另一套约定，类比覆盖不到。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：应用容器的日志里反复出现「连接数据库失败」**

```text
应用容器运行正常
数据库容器也运行正常
        ↓
但应用就是连不上数据库
        ↓
检查三件事：
  1. 应用配置里填的地址是什么？
  2. 两个容器在不在同一个 Docker 网络里？
  3. 填的是不是容器名？
```

**判断：先看地址填的是什么，再看两个容器在不在同一个网络。** 最常见的两个原因是：

- 填了 `127.0.0.1`（那是容器自己）
- 两个容器不在同一个网络里（那就谈不上用名字找）

**这两个原因都属于「配置」层面，而不是「服务坏了」** —— 和容器本身的状态无关。

**场景二：容器重建之后，原本能连上的服务连不上了**

```text
第一次部署：一切正常
        ↓
重建了数据库容器
        ↓
应用连不上了
```

**判断：回想一下当初配置里填的是名字还是地址。**

```text
填名字 → 重建后仍然有效（前提：名字没变、仍在同一网络）
填地址 → 重建后地址可能变，配置失效
```

**这也是为什么「用名字连接」是更好的做法** —— 它把「连谁」和「连到哪」分开了。

**场景三：为什么教程说「不需要给数据库做端口映射」**

```text
数据库容器 → 只被应用容器访问，不被外部访问
        ↓
它需要的是「在 Docker 网络里能被应用找到」
        ↓
不需要做端口映射
```

**判断：区分「谁需要访问它」。**

```text
需要被浏览器访问   →  做端口映射
只需要被其他容器访问 →  放进同一个 Docker 网络就够
```

**这还带来一个安全上的好处**：不做端口映射，就意味着数据库在局域网上没有入口，只有同一个网络里的容器能碰到它。**「不需要的东西就不开」是一个值得养成的习惯。**

### 6.2 两个概念的分工对照

| 问题 | 用哪个概念解决 | 关键写法 |
|---|---|---|
| 我在浏览器里怎么打开这个服务 | 端口映射 | `8080:80`（外面:里面） |
| 应用怎么连上数据库 | Docker 网络 | 填容器名，如 `db` |
| 数据库要不要暴露给局域网 | 不需要 → 不做映射 | 只放进内部网络 |
| 换一台机器部署，配置要怎么改 | 用名字就不用改 | 名字不变，配置不变 |
| 两个不相关的服务会不会互相干扰 | 放进不同网络 | 互相不可见 |

**表格要读出的重点**：**这两种需求看起来都是「连接」，但方向相反，解决手段也完全不同。** 分不清方向，就会出现「给数据库也做了端口映射」「应用里填了 127.0.0.1」这类问题。

### 6.3 本周收束：一句话串起五个概念

```text
一个自托管服务被包装成 Image（模板），
启动成 Container（实例），
数据放在 Volume（容器之外），
通过 Port Mapping（让外面能访问），
通过 Docker Network（让容器之间能找到彼此）。
```

**这五句话，就是本周要带走的东西。**

## 7. 常见误区

### 误区一：认为端口映射和 Docker 网络是同一件事

不是。端口映射管「外面的人怎么进来」，Docker 网络管「容器之间怎么互相找到」。方向相反，解决的问题也不同。把两者混为一谈，会出现「给不该暴露的数据库做了端口映射」或「应用里填了外部访问地址」这类错误。

### 误区二：认为容器之间可以直接用 127.0.0.1 通信

不行。在容器内部，`127.0.0.1` 指的是这个容器自己，而不是宿主机，也不是别的容器。填了它，应用等于在跟自己说话。要访问同一网络里的另一个容器，应该用它的容器名。

### 误区三：认为容器的 IP 地址是固定的

不是。容器重建后分到的地址可能变化。所以配置里应该用容器名，而不是地址。用名字连接，容器重建后配置依然有效 —— 这正是 Docker 网络内置名字解析的价值。

### 误区四：认为所有容器默认都在同一个网络里、都能互相访问

不是。容器需要被接入同一个网络才能互相用名字访问；不在同一网络的容器之间默认不可见。这个「默认不可见」既是限制，也是保护 —— 它让不相关的服务不会互相干扰。

### 误区五：认为每个容器都应该做端口映射

不需要。只有「需要被外部访问」的服务才需要端口映射。数据库这类只被其他容器访问的服务，放进内部网络就够了，映射出去反而增加了暴露面。**「不必要就不开放」是本周最实用的一条安全习惯。**
