# 第三十三课：Volume 与数据持久化

> 本课的一句话结论：**容器是可丢弃的实例，写在容器里的数据会随容器一起消失；凡是「丢了就找不回来」的数据，必须放到容器之外的卷（Volume）或绑定挂载（Bind Mount）里。**

## 1. 今天学习什么

今天要掌握 3 个概念：

1. **持久化（Persistence）**：让数据活得比容器更久。
2. **卷（Volume）**：由 Docker 管理的存储空间，把数据放在容器之外。
3. **绑定挂载（Bind Mount）**：把你指定的一个真实目录，直接接到容器里的某个路径。

你今天要建立的核心结构是：

```text
容器（可丢弃）              数据（要留住）
┌──────────────┐          ┌──────────────┐
│  可写层       │  ←删了   │              │
│  会一起消失   │          │              │
├──────────────┤          │   卷 / 挂载   │  不受容器删除影响
│  镜像的只读层 │          │              │
└──────────────┘          └──────────────┘
        │                        ↑
        └──── 数据放在这里 ───────┘
              就不会跟着消失
```

以及一个判断标准：

```text
这份数据丢了，我能不能重新弄出来？
├── 能    →  可以不持久化（缓存、临时文件）
└── 不能  →  必须持久化（配置、照片、数据库）
```

## 2. 为什么要学

昨天讲清了：容器是可丢弃的实例，运行期间写的文件都在可写层，删掉容器它们就一起消失。

**但这只说出了问题，没说怎么办。** 现实是：一个自托管服务最宝贵的东西 —— 你的照片、你的配置、你的数据库 —— 恰恰就是「丢了找不回来」的那些。

不理解持久化，会遇到这些问题：

- 为什么升级服务之后，之前的所有设置和内容都不见了？
- 为什么教程反复强调「先做好数据映射」，我却不知道在说什么？
- 卷和绑定挂载都是「把数据放外面」，我该选哪个？
- 为什么我删掉容器后，数据还在磁盘上占着空间？
- 备份的时候，我到底该备份什么？

**这是本周风险最高的一课。** 镜像和容器搞混，只是困惑；持久化搞错，可能直接丢数据。所以今天要讲得慢一点、具体一点。

## 3. 小白解释

### 3.1 容器为什么留不住数据

回到昨天那张图：

```text
容器 = [ 可写层 ]  ← 运行期间产生的文件都写在这里
       [ 只读层 ]  ← 来自镜像
       [ 只读层 ]
```

**可写层是长在容器上的。** 容器没了，这一层就没了。

```text
你在容器里存了照片
        ↓
删掉容器（升级、重建、清理）
        ↓
照片一起消失
```

**这不是 bug，是设计。** 容器的定位就是「用完可以扔」—— 想升级？删掉旧的，用新镜像起一个。想让配置生效？删掉重建。如果每次重建都会丢数据，那这个设计就没法用了。

**所以解决方式不是「让容器别丢数据」，而是「把数据放到容器管不着的地方」。**

### 3.2 持久化：把数据放到容器外面

**持久化（Persistence）** 的意思是：让数据的保存位置不依赖容器。

```text
数据不放在：容器内部（会消失）
数据放在：  容器外部（不受影响）
```

用酒店类比：

```text
容器      =  酒店房间
可写层    =  房间里的东西
退房      =  删掉容器
         ↓
房间里的东西全被清掉
         ↓
所以你的东西要放在行李箱里，
行李箱是你的，走到哪个房间都跟着你
```

**行李箱就是卷或绑定挂载。**

### 3.3 两种做法：卷和绑定挂载

把数据放到容器外面，有两种常见方式：

**卷（Volume）**

```text
由 Docker 管理的存储空间
位置对使用者透明（你不用关心它具体在硬盘的哪个角落）
配置简单
```

**绑定挂载（Bind Mount）**

```text
你明确指定：NAS 上的「哪个目录」 ↔ 容器里的「哪个路径」
你可以在文件管理器里直接看到这些文件
```

用类比：

```text
卷        =  交给酒店保管的储物柜（你不用管放在哪，要用时给你）
绑定挂载  =  你自己拿着钥匙的保险箱（你知道它在哪，随时能打开看）
```

**两者都在解决同一件事：把数据放到容器之外。** 区别只在「谁来管这个位置」。

### 3.4 该选哪个

一个简单的判断：

```text
你想在文件管理器里直接看到、直接编辑这些文件吗？
├── 想    →  绑定挂载
└── 不想  →  卷

你会自己手动备份这个目录吗？
├── 会    →  绑定挂载（路径明确，好备份）
└── 不会  →  卷（交给 Docker 管）
```

**两者没有绝对优劣。** 很多人喜欢绑定挂载，因为路径明确、看得见、好备份；也有人喜欢卷，因为不用自己操心路径和权限。**关键是：必须选一个，不能让数据留在容器里。**

## 4. 技术解释

### 4.1 可写层的机制

容器启动时，Docker 在镜像的只读层之上叠加一个可写层。所有运行期间的写入操作都落在这里。

**为什么这样设计？** 因为镜像要能被多个容器共享。如果容器的改动直接写进镜像，那么一个容器的改动就会污染所有基于该镜像的容器。加一层可写层，等于给每个容器一块自己的「草稿纸」。

**代价就是：这块草稿纸是临时的。** 容器删除，草稿纸一起撕掉。

### 4.2 卷的工作方式

卷是 Docker 管理的存储单元，有几个特点：

- **生命周期独立于容器**：容器删了，卷还在。
- **可以被多个容器挂载**：同一个卷接到多个容器上，它们看到的是同一份数据。
- **位置由 Docker 管理**：通常在系统的一个专门区域，路径由 Docker 决定。
- **可以通过命令单独管理**：查看、删除、备份都是独立操作。

**注意：卷不会随容器自动删除。** 这是好事（数据不会因为误删容器而丢失），但也意味着「删了容器磁盘却没释放」的情况，多半就是卷还在。

### 4.3 绑定挂载的工作方式

绑定挂载直接把宿主系统的一个真实路径接到容器里：

```text
NAS 上的路径             容器里的路径
/data/photos      ←──→   /photos
```

特点：

- **路径由你决定**：你可以指定任意一个存在的目录。
- **你和其他程序都能访问**：NAS 上的其他工具、文件管理器、备份程序，都能直接看到这些文件。
- **权限由宿主系统决定**：这是绑定挂载最常见的坑 —— 如果容器里的用户没有权限访问那个目录，服务会报权限错误。

**「权限问题」这一点要特别注意**：不少自托管服务启动失败，原因就是绑定挂载的目录属于另一个用户，容器里的进程读不了或写不了。第 31 课的「隔离」在这里体现为：容器里的用户和宿主上的用户不是同一套概念。

### 4.4 两者的取舍

| 维度 | 卷（Volume） | 绑定挂载（Bind Mount） |
|---|---|---|
| 谁决定存放位置 | Docker | 你 |
| 能否在文件管理器直接看到 | 一般不能 | 能 |
| 配置复杂度 | 较低 | 需要指定路径并注意权限 |
| 备份方式 | 通过 Docker 或找到实际路径 | 直接备份该目录 |
| 权限问题 | 较少 | 较常见 |
| 适合的场景 | 数据库、内部状态 | 媒体文件、需要人工干预的配置 |

**表格要读出的重点**：不是「哪个更先进」，而是「哪个更符合你的使用习惯」。**能看得见、能自己备份，对初学者往往更重要** —— 所以不少入门教程会优先用绑定挂载。

### 4.5 一条示例命令

```bash
docker run -v 宿主路径:容器路径 某个镜像名
```

**不需要背，只需要理解它在说什么：**

```text
docker run  -v  宿主路径:容器路径  某个镜像名
             ↑       ↑        ↑
          卷/挂载   外面的   里面的
          的标志    位置     位置

概念含义：启动一个容器，并把「外面的某个位置」
          接到「容器里的某个位置」，
          于是这个位置上的数据不会随容器消失。
```

**注意这里和端口映射（第 34 课）的写法很像，都是「A:B」。** 但含义不同：

```text
-v 8080:80        这里是「端口 : 端口」（明天讲）
-v /data:/photos  这里是「目录 : 目录」（今天讲）
```

**它没有告诉你什么：** 这条命令不会说明那个目录里原本有什么、权限对不对、这个服务到底需要挂载哪些目录。**这些信息只能从服务的文档里找** —— 而这也正是「读懂项目文档」成为一项重要能力的原因。

### 4.6 备份意味着什么

理解持久化之后，「备份」这件事就变得具体了：

```text
要备份的不是「容器」
要备份的是「容器外面的那些数据」
        ↓
也就是：卷里的内容 + 所有绑定挂载的目录 + 配置文件
```

**一个实用的自检问题**：

> 如果我现在把所有容器都删掉，然后重新按原来的配置启动一遍，我的数据还在吗？

如果答案是「在」，说明持久化做对了。如果答案是「不在」，那现在就该调整。

## 5. 类比

把容器想象成**酒店房间**，数据想象成**你的行李**：

- **房间是短住的**：退房时房间会被彻底清空，这是酒店的规定，不是它坏了。
- **房间里放的东西会随退房消失**：容器里的数据随容器删除而消失。
- **你的行李放在行李箱里**：行李箱是你自己的，走到哪个房间都跟着你。
- **卷像酒店保管的储物柜**：你不用管它放在哪，需要时酒店给你取来。
- **绑定挂载像你自己带的保险箱**：钥匙在你手里，你随时能打开检查里面的东西。
- **升级服务像换房间**：换房间时，只要行李跟着走，住哪个房间都不影响你的东西。
- **退房后发现东西忘在房间里**：容器删除后才发现数据没挂载出来。

**这个类比能解释什么：**

| 类比中的事 | 对应的技术事实 |
|---|---|
| 房间退房时被清空 | 容器删除时可写层消失 |
| 这是酒店规定不是故障 | 容器的一次性是可丢弃设计，不是 bug |
| 行李跟着人走 | 数据放在容器之外 |
| 酒店储物柜 | 卷（Docker 管理位置） |
| 自己带的保险箱 | 绑定挂载（你指定路径） |
| 换房间不掉东西 | 容器重建不影响已持久化的数据 |
| 东西忘在房间里 | 未做持久化导致数据丢失 |

**这个类比解释不了的：** 它不能说明「权限问题」—— 行李箱不会被酒店门锁拦住，但绑定挂载的目录会因为没有权限而读写失败。那属于技术细节，类比无法覆盖。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：升级服务前，先做哪一步**

```text
看到新版本发布
   ↓
想直接删掉旧容器、启动新容器
   ↓
停一下：先问数据在哪里
```

**判断：升级之前，先确认「数据放在哪」。** 具体要确认三件事：

1. 这个服务把数据写在容器内的哪个路径？
2. 这个路径有没有被挂载到容器外面？
3. 挂载的那个位置，里面确实有数据吗？

**这三个问题都能回答了，才可以动手删容器。** 这花不到五分钟，但能避免最糟糕的结果。

**场景二：容器启动失败，日志里写着「Permission denied」**

```text
绑定挂载的目录 /data/app-config
        ↓
容器里的进程（以某个用户身份运行）
        ↓
没有权限读写这个目录
        ↓
启动失败
```

**判断：这不是「挂载没用」，而是「挂载对了但没有权限」。** 和 Week 6 学的一样：先判断路径对不对、用户是谁、权限够不够，而不要一上来就用最高权限去跑 —— 那会抵消掉隔离带来的好处。

**场景三：想备份，但不知道备份什么**

```text
方案 A：备份整个容器
方案 B：备份绑定挂载的目录 + 配置文件
```

**判断：选 B。** 容器本身是可以随时重建的（镜像 + 配置就能还原），真正的价值在数据里。而且容器内部结构对使用者并不透明，备份起来既不可靠也不必要。**把「需要备份的东西」整理成一份清单，是自托管长期使用的基本功。**

### 6.2 数据与处理方式对照

| 数据类型 | 丢了会怎样 | 建议 |
|---|---|---|
| 照片、视频原文件 | 找不回来 | 必须绑定挂载或卷 |
| 应用配置文件 | 需要重新配置一遍 | 必须持久化 |
| 数据库文件 | 数据全没了 | 必须持久化，且要单独备份 |
| 缩略图缓存 | 会重新生成 | 可以不持久化 |
| 临时下载目录 | 影响不大 | 可以不持久化 |
| 日志 | 想追溯问题时有用 | 建议持久化，但可定期清理 |

**表格要读出的重点**：**「要不要持久化」是一个判断，不是一条铁律。** 全都持久化会让配置变复杂、磁盘占用变大；完全不持久化则可能丢数据。按「丢了能不能重新弄出来」这个标准，一项一项判断。

### 6.3 本课与「能不能用」的关系

```text
你现在能回答的问题：
✓ 为什么删掉容器数据会消失
✓ 卷和绑定挂载分别是什么、怎么选
✓ 升级服务前要先确认什么
✓ 备份应该备份什么

你现在还不能回答的问题：
✗ 我在浏览器里怎么访问容器里的服务（第 34 课）
✗ 那些时区、密码的配置写在哪里（第 34 课）
✗ 两个容器之间怎么互相找到（第 35 课）
```

## 7. 常见误区

### 误区一：认为容器里的数据会自动保留

不会。容器运行期间写入的文件都落在可写层，而可写层跟着容器走。删掉容器，这些文件一起消失。凡是「丢了找不回来」的数据，都必须提前放到卷或绑定挂载里 —— 这是本课最核心的一条。

### 误区二：把「删除容器」当成「清理干净」

删掉容器只是移除了运行实例及其可写层，镜像还在、卷还在。所以会出现「删了容器磁盘却没释放」的情况。清理是一件需要分清对象的事，不能笼统地「删掉再说」。

### 误区三：认为卷和绑定挂载有绝对的优劣

两者解决的是同一个问题，区别只在「存放位置由谁决定」。卷省心，绑定挂载直观。哪个更合适，取决于你是否需要直接看到和手动管理这些文件。没有普适的最优解。

### 误区四：以为挂载了就不会有权限问题

挂载只解决「数据放在哪」，不解决「谁能读写」。绑定挂载的目录权限由宿主系统决定，而容器里的进程以另一个用户身份运行，两者对不上就会报权限错误。看到权限报错时，要先分析，不要直接给最高权限。

### 误区五：认为备份就是「把整个容器存下来」

容器是可重建的，备份它意义有限；真正需要保存的是数据本身。而且容器内部结构对使用者不透明，直接备份既不可靠也不方便恢复。正确的做法是：把数据和配置整理成一份明确的清单，定期备份这些位置。
