# 第三十四课：端口映射与环境变量

> 本课的一句话结论：**容器默认与外界隔绝，端口映射决定「外面的人怎么进来」，环境变量决定「容器里的应用怎么被配置」—— 前者管通路，后者管参数。**

## 1. 今天学习什么

今天要掌握 2 个概念：

1. **端口映射（Port Mapping）**：把容器内部的端口接到宿主系统上，让外部能访问。
2. **环境变量（Environment Variable）**：从外部向容器传递配置，而不必写死在镜像里。

你今天要建立的核心结构是：

```text
外部世界                宿主机（NAS）             容器
                        ┌──────────┐            ┌──────────┐
浏览器访问 8080  ──────→ │  8080    │ ────────→  │    80    │  应用
                        └──────────┘            └──────────┘
                              ↑                        ↑
                        你决定这个端口           应用决定这个端口
```

以及一个「两条通路」的结构：

```text
                容器
                 ↑
    ┌────────────┴────────────┐
    │                         │
端口映射                    环境变量
（外面的人怎么进来）        （应用被配置成什么样）
    │                         │
 管「通路」                 管「参数」
```

## 2. 为什么要学

昨天解决了「数据怎么留住」。今天要解决两个新问题：**「我怎么访问它？」「那些配置写在哪里？」**

这两个问题看起来不相关，其实都是「容器默认与外界隔绝」带来的后果 —— 隔离带来干净，也带来「进不去、也传不进去」。

不理解这两个概念，会遇到这些问题：

- 为什么容器启动成功了，我在浏览器里却打不开？
- `8080:80` 里两个数字分别是什么意思，为什么不是同一个数？
- 为什么配置文件里写的是 `TZ=Asia/Shanghai` 这种形式，而不是勾选框？
- 为什么同一个镜像，别人部署出来和我的不一样？
- 密码、密钥这些信息到底该写在哪里才是安全的？

**这两个概念也直接对应 Week 5 学过的内容** —— 端口映射就是端口概念的延续，只是这次「门」开在容器上。

## 3. 小白解释

### 3.1 容器默认是「关着门」的

第 31 课讲了隔离的好处。现在看看它的另一面：

```text
隔离的好处：容器里的东西不会影响你的系统
隔离的代价：外面的东西也进不来
```

所以一个容器启动成功、进程在跑、日志没有报错 —— **但这不代表你在浏览器里能访问它。** 它只是「在里面跑着」，门还没开。

**端口映射（Port Mapping）就是开门。**

### 3.2 端口映射：把外面的门接到里面的门牌

写法长这样：

```text
8080:80
  ↑    ↑
宿主机端口  容器内端口
```

读法是：**把外面的 8080，接到里面的 80。**

```text
NAS（宿主机）              容器
   8080        ────────→    80
（你决定这个）            （应用决定这个）
```

用类比：

```text
容器里的端口  =  房间里面的门牌号（由住的人决定）
宿主机端口    =  这栋楼对外开的门（由你决定）
端口映射      =  在大门上贴个条：敲 8080，转接到里面 80 号房间
```

**为什么两个数字不能总是同一个？** 因为它们归不同的人管：

- **右边的 80**：这是应用在容器里监听的端口，通常由这个软件的开发者决定。除非文档明确说明可以改，否则不该动。
- **左边的 8080**：这是你在 NAS 上访问时用的端口，由你决定。你可以选任何没被占用的数字。

**「左边可以随便改，右边一般不要动」** —— 这是理解 `8080:80` 的关键。

### 3.3 为什么左边的端口要自己选

因为 NAS 上不止一个服务。如果每个服务都想用同一个数字，就会冲突。

```text
影音服务   8096:8096
照片服务   2283:2283
新服务     8080:80      ← 左边选个没被占用的
```

**左边的数字是你在这台 NAS 上的「对外门牌」。** 选的时候要满足两个条件：

1. 没有被别的服务占用；
2. 你记住它，因为以后访问就要用它。

### 3.4 环境变量：从外面递进去的配置

**环境变量（Environment Variable）** 是另一种「从外面给容器传信息」的方式。

它解决的问题是：**同一个镜像，要能服务于不同的人、不同的环境。**

```text
如果配置写死在镜像里：
  每个人想要不同的时区 → 每个人都要自己改镜像
        ↓
  镜像就没法共享了

用环境变量：
  镜像保持通用
  每个人启动容器时传入自己的配置
        ↓
  同一个镜像，人人可用
```

写成示例是这样的：

```text
TZ=Asia/Shanghai
ADMIN_USER=admin
ADMIN_PASSWORD=CHANGE_ME
```

**注意上面这些全都是示例值，不是真实值。** 最后一行特意写成 `CHANGE_ME` 是想提醒你：这一项应该由使用者自己填，不应该照抄别人的。

用类比：

```text
镜像      =  一台出厂设置统一的设备
环境变量  =  你在使用前根据自己的需要调的那些设置
```

### 3.5 环境变量里的敏感信息

环境变量最常见的用途之一，是传密码、密钥、令牌。这也是它最需要注意的地方。

```text
✓  可以写进笔记：环境变量是干什么的、有哪些常见的变量名、值该怎么填
✗  不要写进笔记：真实的密码、密钥、令牌、访问凭据
```

**为什么要这么小心？** 因为笔记、截图、配置文件经常会被分享出去。一个真实的密码写在里面，等于这个密码被公开了 —— 而且它常常是「一把钥匙开很多门」的那种。

**养成习惯**：写示例时用 `CHANGE_ME`、`example-token` 这类明显的占位符。看到自己笔记里有看起来像真实密码的字符串，就应该警觉。

## 4. 技术解释

### 4.1 端口映射的方向与写法

端口映射的写法是 `宿主端口:容器端口`：

```text
8080:80
  ↑    ↑
 外面  里面
```

**方向不要记反。** 一个帮助记忆的方式：**左边的数字是你在浏览器地址栏里要敲的那个。** 你在 NAS 上访问服务时写的是 `NAS地址:左边那个数字`。

```text
配置里写：8080:80
浏览器访问：192.168.1.10:8080
                          ↑
                    用的是左边那个
```

### 4.2 端口冲突发生在哪一侧

**端口冲突发生在宿主机这一侧**，也就是冒号左边的数字。

```text
服务甲  8080:80
服务乙  8080:80     ← 冲突！两个都想占用宿主机上的 8080
```

而冒号右边不会冲突，因为每个容器有自己独立的「内部空间」：

```text
服务甲  8080:80    ┐
服务乙  8090:80    ┘  容器里都是 80，互不影响
```

**这一点非常重要**，它解释了为什么端口映射能同时解决「两个服务都用同一个内部端口」的问题 —— 因为它们的内部分开，只需要在外面对应到不同的门。

### 4.3 端口映射与 Week 5 的关系

Week 5 学过：IP 定位设备，端口定位设备上的服务。现在这套概念原封不动地用上了：

```text
Week 5：  192.168.1.10:8096
                ↑       ↑
              设备     设备上的服务

Week 7：  192.168.1.10:8080
                ↑       ↑
              设备   被映射出来的容器服务
```

**唯一的区别是：这次的「服务」本来待在容器里，端口映射让它在 NAS 上有了一个门牌。** 概念是同一套 —— 这也是为什么网络基础要先学。

### 4.4 环境变量的传递方式

环境变量可以从几个地方传给容器：

| 来源 | 说明 | 适合的场合 |
|---|---|---|
| 启动时直接指定 | 每条配置写一次 | 临时测试 |
| 配置文件 | 写在一个文件里，启动时读取 | 长期使用（Week 8 的 Compose 就属于这类） |
| 由系统或密钥管理工具提供 | 从外部注入，不落在配置文件里 | 对安全要求较高的场景 |

**关键理解：环境变量是「运行时」传进去的，不是「构建时」写死的。** 所以同一个镜像可以启动出配置完全不同的多个容器 —— 这正是昨天说的「一个镜像起多个容器」的一种实际用法。

### 4.5 优先级与常见变量

环境变量通常有一个**覆盖规则**：镜像里可能有默认值，你在启动时传入的值会覆盖它。

```text
镜像自带的默认值
        ↓  被覆盖
你启动时传入的值
        ↓
最终生效的值
```

一些很常见的变量名（不同软件不完全相同，以文档为准）：

```text
TZ          时区
PUID / PGID  运行身份（关系到文件权限，和第 33 课的权限问题直接相关）
UMASK       新建文件的默认权限
```

**这些名字不需要背。** 需要建立的认识是：**每个服务的环境变量清单，只能从它自己的文档里找** —— 这也是「读文档」能力为什么重要。

### 4.6 一条示例命令

```bash
docker run -p 8080:80 -e TZ=Asia/Shanghai 某个镜像名
```

**逐段理解它说了什么：**

```text
docker run                    启动一个容器
  -p 8080:80                  端口映射：外面 8080 → 里面 80
  -e TZ=Asia/Shanghai         环境变量：把时区设为上海
  某个镜像名                   从哪个镜像启动
```

**注意 `-p` 和 `-e` 这两个标志各自对应一个概念：**

```text
-p  →  Port Mapping     管「通路」
-e  →  Environment      管「参数」
```

**它没有告诉你什么：** 这条命令不会说明这个服务应该用哪个端口、需要哪些环境变量、哪些变量是必填的。**这些信息只在服务自己的文档里**，命令本身不提供。

### 4.7 安全边界

端口映射有一个容易被忽略的后果：

```text
一旦做了端口映射
        ↓
这个端口在局域网内是开放的
        ↓
如果同时做了端口转发（Week 5），它在互联网上也是开放的
```

**所以端口映射不只是「内部配置」，它决定的是「谁能访问到这个服务」。** 结合 Week 5 的结论：**优先在局域网内使用；需要远程访问时，优先用私有通道（如 VPN / Tailscale），而不是直接把端口暴露到公网。**

## 5. 类比

把容器想象成**一栋独立的小房子**：

- **房子是封闭的**：不主动开门，外面进不去。
- **里面的房门牌由住户决定**：容器内部的端口由应用决定。
- **外面的院门由你决定**：宿主机端口是你选的。
- **端口映射是「院门口贴的转接条」**：敲院门的某个号码，转接到里面某个房间。
- **环境变量是「搬进去之前填的一张设置单」**：时区、名字、密码都写在上面，住户按单子开始工作。
- **同一款房子可以配不同的设置单**：同一个镜像，可以启动成配置不同的多个容器。
- **转接条贴出去，路过的人都能看到门牌**：端口映射意味着这个服务在这台机器上可被访问。

**这个类比能解释什么：**

| 类比中的事 | 对应的技术事实 |
|---|---|
| 房子封闭，外面进不去 | 容器默认不与外界连通 |
| 里面门牌住户定 | 容器内端口由应用决定 |
| 外面院门我定 | 宿主机端口由使用者决定 |
| 转接条贴在外门 | 端口映射写在宿主机一侧 |
| 两户都叫 80 号房也不冲突 | 每个容器内部空间独立 |
| 设置单按需填写 | 环境变量运行时传入 |
| 同款房子不同设置 | 一个镜像启动多个不同配置的容器 |
| 门牌公开可见 | 映射后该端口可被访问 |

**这个类比解释不了的：** 它不能说明「环境变量里的密码会被记录下来，可能泄露」—— 房子不会自己把设置单的内容抄送给别人，但配置文件、截图和日志会。

## 6. NAS 实际场景

### 6.1 三个真实判断

**场景一：容器启动了，但浏览器打不开**

```text
容器状态正常、日志无报错
        ↓
浏览器访问 NAS 地址，打不开
        ↓
第一件事：确认有没有做端口映射
```

**判断：先分清「服务起没起来」和「门开没开」。** 这是两件独立的事：

```text
服务没起来    →  看容器日志
服务起来了但进不去 →  看有没有端口映射，以及映射的左边是哪个数字
```

很多新手会在这两者之间反复折腾，其实只要问一句「我该用哪个端口访问」，就能立刻定位到问题在哪一侧。

**场景二：两个服务都想用同一个内部端口**

```text
服务甲内部监听 80
服务乙内部监听 80
        ↓
传统安装：冲突，必须改一个
容器化：不必改，两边都保持 80
        ↓
只需在宿主机侧对应到不同的数字
```

**判断：这就是容器带来的一个很实际的好处。** 两个服务「内部都是 80」，互不冲突，因为它们的内部空间是分开的；只有在宿主机这一侧才需要区分。

**场景三：从网上抄来一份配置，里面有密码**

```text
教程里的示例配置
        ↓
写着 ADMIN_PASSWORD=CHANGE_ME
        ↓
你照着填了自己的真实密码
        ↓
把这份笔记/截图分享出去
```

**判断：这就是最典型的泄露方式。** 正确做法是：**笔记里只保留占位符，真实值只放在实际运行的那份配置文件里，而且那份文件不公开。** 如果一份示例里出现了看起来很真实的值（一串随机字符、一个像邮箱的用户名），那要么是演示用的假数据，要么就是别人不小心泄露了 —— 两种都不该照抄。

### 6.2 两个概念与两类现象对照

| 现象 | 相关概念 | 排查方向 |
|---|---|---|
| 服务起来了，但浏览器打不开 | 端口映射 | 有没有映射？左边是哪个端口？ |
| 提示端口已被占用 | 端口映射 | 宿主机侧的端口被别的服务占了 |
| 时区不对、语言乱码 | 环境变量 | 对应的变量有没有设置 |
| 文件权限报错 | 环境变量 + 挂载 | 运行身份相关的变量和目录权限 |
| 同一个镜像，别人部署效果不同 | 环境变量 | 传入的配置不同 |
| 服务在局域网能访问，外网不能 | 端口映射 + 网络 | 这是 Week 5 的范畴，正常现象 |

**表格要读出的重点**：**症状相似，原因可能在不同层。** 「打不开」可能是端口问题，「行为不对」可能是环境变量问题。先分清症状属于哪一类，再去找对应的概念。

### 6.3 本课与「能不能用」的关系

```text
你现在能回答的问题：
✓ 为什么容器起来了还是访问不到
✓ 8080:80 两个数字分别是什么
✓ 配置为什么用环境变量传
✓ 哪些信息绝对不能写进笔记

你现在还不能回答的问题：
✗ 两个容器之间怎么互相访问（第 35 课）
✗ 怎么把这一整套写成一个文件（Week 8）
```

## 7. 常见误区

### 误区一：把 `8080:80` 的方向记反

写法是「宿主机端口 : 容器端口」，也就是「外面 : 里面」。记反会带来一连串错误：以为浏览器该用 80 访问、以为改右边是改对外端口。一个稳妥的记法是：**左边那个数字，才是你在浏览器地址栏里敲的那个。**

### 误区二：认为容器启动了就等于能访问

不是。容器启动只说明进程在跑；能不能被访问，取决于有没有做端口映射。这是两件独立的事，混在一起会导致排查时找错方向 —— 明明日志没有错误，却一直在翻日志。

### 误区三：认为两个容器不能同时用同一个内部端口

可以。容器内部空间是彼此独立的，两个容器都可以在内部监听同一个端口，互不冲突。冲突只发生在宿主机这一侧，也就是映射写法冒号左边的数字上。误解这一点，会导致不必要地去修改应用内部的端口配置。

### 误区四：把环境变量当成「随便写写」的备注

环境变量是实打实的配置，写错会导致服务行为异常甚至启动失败。同时它又常常承载密码和密钥，因此有双重风险：写错会出错，写漏会泄露。**正确做法是：变量名和用途可以记录，真实的值不记录。**

### 误区五：认为端口映射只是「内部配置」，和安全无关

端口映射决定的是「这个服务在这台机器上是否可被访问」。一旦配合端口转发，它就直接关系到能否从互联网访问。所以它既是配置问题，也是安全问题 —— 需要和 Week 5 的结论一起考虑：优先局域网，远程访问优先用私有通道。
