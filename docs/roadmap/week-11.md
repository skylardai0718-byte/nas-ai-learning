## 本周目标

完成后，你应能：

1. 解释 CPU、GPU、NPU 的基本分工，并为一个具体场景判断该由谁来承担计算。
2. 说明显存（VRAM）容量决定「模型能不能装下」，显存带宽决定「跑起来快不快」。
3. 用「位数减半、体积大致减半」的直觉，粗略估算同一个模型在不同量化下的体积。
4. 画出 `Model → 推理引擎 → API → 应用` 这条软件栈，并说出 Ollama、LM Studio、llama.cpp、Open WebUI 各自扮演的角色。

>
> **本周的边界提醒：** 本周讨论的是「能不能跑」的原理，不是「买哪台机器」。**不比较跑分、不推荐具体型号或品牌、不写成购买指南。** 你学到的是判断框架：什么约束决定了结果，以及规格表上没有写出的信息会怎样影响结论。

## Day 1：CPU、GPU 与 NPU

**新概念：** CPU、GPU、NPU

**总时长：** 55 分钟

### 今日目标

- 说清 CPU、GPU、NPU 三者的分工，理解它们是配合而不是互相取代。
- 知道 GPU 与 NPU 的关键差别在于「通用」与「专用」。
- 能为「低频问答、图像识别、LLM 推理」三类任务，判断硬件角色。

### 学习（25 分钟）

先建立一个总图：

```text
CPU  →  通用处理器，什么都能做，但一次只擅长处理少数几件事
GPU  →  大量并行计算，同一个简单动作同时做很多次
NPU  →  为神经网络推理专门设计的加速器，只做这一类事
```

它们的关系不是「新的一定取代旧的」：

```text
        ┌──────────────────────────────────────┐
        │              整个系统                 │
        ├────────┬─────────┬─────────┬─────────┤
        │  CPU   │   GPU   │   NPU   │  其他   │
        │ 调度   │ 大规模  │ 神经网络 │ 专用    │
        │ 通用   │ 并行    │ 推理加速 │ 芯片    │
        └────────┴─────────┴─────────┴─────────┘
          谁在干活，取决于任务适合谁
```

三类任务，先给一个粗判断：

```text
低频问答   →  偶尔问一句、等一两秒也无所谓  →  CPU 常常就够
图像识别   →  大量重复的矩阵运算           →  GPU 或 NPU 更合适
LLM 推理   →  需要容量 + 大规模并行         →  主要看 GPU 与显存
```

本周只需记住：**硬件角色的选择，取决于任务的「能不能并行」和「需要多大容量」。**

## Day 2：VRAM 与显存带宽

**新概念：** CUDA Core、Tensor Core、VRAM、Memory Bandwidth

**总时长：** 55 分钟

### 今日目标

- 分清 VRAM 容量与带宽各自决定什么。
- 理解「装得下」和「跑得快」是两个不同的问题。
- 知道 CUDA Core 与 Tensor Core 只是定位，不是本课重点。

### 学习（25 分钟）

本周最重要的一条区分：

```text
VRAM 容量（GB）  →  模型能不能装进来  →  决定「能不能跑」
显存带宽（GB/s） →  数据搬运多快      →  决定「跑得快不快」
```

画成两个独立的问题：

```text
问题一：装得下吗？
  模型体积（GB）   vs   显存容量（GB）
  装不下 → 根本跑不起来，或者要靠更慢的方式

问题二：跑得快吗？
  每生成一个词都要把大量数据搬一遍
  带宽越高 → 搬得越快 → 生成越快
```

还要记住一条：**显存不只有模型在用。** 上下文（对话历史）、系统与其他程序，都会占掉一部分。所以「模型装得下」和「机器跑得动」之间，中间还有一段距离。

CUDA Core 和 Tensor Core 先只记定位：

```text
CUDA Core   →  通用的并行计算单元
Tensor Core →  针对矩阵运算优化的计算单元
两者影响算得多快，但装不装得下，首先看 VRAM 容量。
```

## Day 3：模型大小与量化

**新概念：** Model Size、FP16、INT8、INT4、Quantization

**总时长：** 55 分钟

### 今日目标

- 理解模型体积大致由「参数数量 × 每个参数的位数」决定。
- 理解量化的本质：用更少的位数表示每个参数。
- 对同一个 7B 模型，建立不同量化下体积的粗略直觉。

### 学习（25 分钟）

任何模型的大小，都有一个粗略的关系：

```text
模型体积  ≈  参数数量 × 每个参数占的字节数
```

先看「位数 → 字节」的对应：

```text
FP16  →  16 位  →  约 2 字节 / 参数
INT8  →   8 位  →  约 1 字节 / 参数
INT4  →   4 位  →  约 0.5 字节 / 参数
```

**量化（Quantization）** 的本质，就是把每个参数从「用较高位数表示」换成「用较低位数表示」。位数减半，体积大致减半。

以 7B 模型（约 70 亿参数）为例，粗略估算：

```text
FP16（2 字节）   70 亿 × 2 字节  ≈  14 GB
INT8（1 字节）   70 亿 × 1 字节  ≈   7 GB
INT4（0.5 字节） 70 亿 × 0.5 字节 ≈   4 GB 左右
```

这就是为什么同一个模型，有的版本十几 GB，有的只有几 GB —— 它们是同一个模型的不同量化版本。

代价也要说清：

```text
位数越少  →  体积越小  →  更容易装下
位数越少  →  精度损失  →  回答质量可能下降
```

**这是一个取舍，不是「越小越好」。**

### 复述（12 分钟）

- 用一句话说清量化的本质。
- 回答：为什么同一个模型会有不同大小的版本？
- 回答：以 7B 模型为例，FP16、INT8、INT4 的体积大致是多少？

### 测试（13 分钟，不给答案）

## Day 4：Local AI 软件栈

**新概念：** 推理引擎、API、应用

**总时长：** 55 分钟

### 今日目标

- 画出 `Model → 推理引擎 → API → 应用` 这条软件栈。
- 说出 Ollama、LM Studio、llama.cpp、Open WebUI 各自扮演的角色。
- 理解「引擎」和「应用」为什么是两层，而不是一回事。

### 学习（25 分钟）

本地 AI 不是一个软件，而是一条链路：

```text
Model  →  推理引擎  →  API  →  应用
模型     真正干活的      对话    你看到的
文件     计算程序        接口    界面
```

每一层各司其职：

```text
Model           权重文件，是「知识」本身，不会自己运行
推理引擎        让模型在硬件上跑起来的程序（如 llama.cpp）
API             对外的标准接口，让别的程序能调用引擎
应用            直接给你用的界面（如 Open WebUI）
```

几个常见工具按角色放置：

```text
llama.cpp   →  推理引擎（底层，追求效率与可控）
Ollama      →  推理引擎 + 管理 + 一个简单的 API（打包好的一层）
LM Studio   →  推理引擎 + 图形界面（把整套流程做进一个桌面应用）
Open WebUI  →  应用（一个对话界面，通过 API 连接到引擎）
```

**关键区分：** Open WebUI 自己不会运行模型 —— 它只管界面，真正算的是引擎。所以才需要把「界面」和「引擎」看成两层。

## Day 5：这台机器能跑这个模型吗

**新概念：** （综合应用，无新概念）

**总时长：** 55 分钟

### 今日目标

- 用一条完整链路，判断 `7B Q4 / 8GB VRAM` 这样的场景。
- 区分「能不能加载」和「会不会慢」两个问题。
- 说清规格表没告诉你、但会影响结论的信息。

### 学习（20 分钟）

拿到一个具体场景，按这个顺序判断：

```text
场景：7B 模型，Q4 量化；机器有 8GB 显存

第一步：模型要多大？
  7B × 0.5 字节  ≈  4 GB 左右

第二步：装得下吗？
  4 GB 模型  vs  8 GB 显存
  看起来装得下 —— 但要留出余量

第三步：会不会慢？
  要看显存带宽，而不是只看容量

第四步：还缺哪些信息？
  见下面
```

**「装得下」和「跑得好」是两回事。** 8GB 显存装 4GB 模型看起来有余量，但以下信息都还没确认：

```text
· 上下文长度：对话越长，需要的显存越多
· 其他占用：系统、桌面环境、别的程序也在用显存
· 显存带宽：决定生成速度，规格表上常被忽略
· 量化方式：Q4 也有不同实现，体积与质量不完全相同
· 模型类型：不同架构对显存的需求不一样
```

所以完整的回答不是「能跑」或「不能跑」，而是：

> **看起来能加载，但没有更多信息，无法判断会不会慢，也无法保证长时间对话不溢出。**

这就是本周要建立的判断习惯：**先给结论，再给边界。**
