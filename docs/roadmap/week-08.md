# 第八周详细计划：Docker Compose 与部署阅读

## 本周目标

完成后，你应能：

1. 说出 Compose、YAML、Service 三者的关系，并知道 Compose 文件是「命令的另一种写法」。
2. 从一份 Compose 文件中读出 `image`、`ports`、`volumes`、`environment` 四个字段分别说明什么。
3. 理解容器的生命周期，分得清「停止」「重建」「删除」，并知道升级前为什么要备份。
4. 拿到一份 README，能找出镜像、访问端口、数据目录和必填变量。
5. 完成一次仅在局域网开放的示例部署：先预测访问地址和数据位置，再验证。

> 每天 45–60 分钟。测试题不立即公布答案；作答后，再按“完全理解 / 基本理解 / 表面理解 / 存在误区”批改。
>
> **本周的安全提醒：** 本周开始接触真实的部署文件。**示例中的密码、令牌一律使用 `CHANGE_ME` 这样的占位符，绝不要把真实凭据写进 Compose 文件、`.env` 或笔记** —— 这类文件经常被误传到公开仓库。**练习服务一律只在局域网内部运行，不要把暴露在公网的服务当作练习对象。** 重点是能读懂别人的文件，不是照抄配置。

## Day 1：Compose、YAML 与 Service

**新概念：** Docker Compose、YAML、Service

**总时长：** 55 分钟

### 今日目标

- 理解 Compose 文件是把一长串 `docker run` 参数写成的结构化清单。
- 知道 YAML 靠缩进表达层级，缩进就是语法。
- 知道一个 Service 就是「一个容器该怎么运行」的说明。

### 学习（25 分钟）

上周你见过那种很长的命令：一堆参数用反斜杠接着，敲错一个字就得重来，而且关掉窗口就找不回来了。

Compose 的做法是把这些参数写进一份文件：

```text
命令（活在历史里）         →    文件（存得住、能给别人看）
docker run -p 8080:80 ...  →    compose.yaml 里的 ports 一行
```

文件的结构是这样的：

```text
compose.yaml
└── services:              ← 顶层，列出这个项目要跑的所有容器
    ├── notes:             ← 一个 Service（描述一个容器）
    └── database:          ← 另一个 Service（描述另一个容器）
```

YAML 的规则只有一条真正重要：**用缩进表示「谁属于谁」**。

```text
services:
  notes:               ← 缩进两格，属于 services
    image: ...         ← 再缩进两格，属于 notes
```

多缩一格、少缩一格，含义就完全不同 —— 空格在这里不是排版，是语法。

**要同时记住边界**：Compose 文件只是描述，它不会自己变出镜像，不会替你检查配置，也不会在你保存文件的那一刻自动生效。

### 复述（12 分钟）

- 说明 Compose、YAML、Service 三者分别是什么。
- 回答：为什么说 Compose 文件是「命令的另一种写法」？
- 回答：为什么 YAML 里缩进错了会出问题？

### 测试（13 分钟，不给答案）

1. Compose、YAML、Service 分别指什么？
2. 判断：只要把 `compose.yaml` 保存好，服务就会自动运行起来。
3. 判断：YAML 里的缩进只是为了好看，可以随意调整。
4. 一个 Service 描述的是什么？
5. 一份 Compose 文件里的多个 Service 之间是什么关系？

### 今日产出（5 分钟）

写出这份文件的骨架：

```text
compose.yaml
└── services:
    ├── ______:     ← 一个 Service
    └── ______:     ← 另一个 Service
```

## Day 2：image、ports、volumes、environment

**新概念：** image、ports、volumes、environment

**总时长：** 55 分钟

### 今日目标

- 读懂四个关键字段，并知道它们的边界。
- 知道 `"8080:80"` 的读法：左边是宿主机，右边是容器。
- 能从一份 README 里找出镜像、端口、数据目录和必填变量。

### 学习（25 分钟）

四个字段各回答一个问题：

```text
image        →  用什么       （哪个程序）
ports        →  从哪进       （访问入口）
volumes      →  数据在哪     （会不会丢）
environment  →  怎么配置     （要填什么）
```

`ports` 和 `volumes` 的冒号读法是同一套，**左边是外面，右边是里面**：

```text
"8080:80"            →  访问 设备地址:8080
./data:/app/data     →  数据存在本地的 ./data 目录
```

**从 README 找这四样东西**，按这个顺序：

| 你要找的 | 通常写在哪 | 关键词 |
|---|---|---|
| 镜像 | 安装 / 部署章节 | `image`、`docker pull` |
| 端口 | 安装章节或「访问」说明 | `port`、`访问`、`localhost` |
| 数据目录 | 挂载说明或「备份」章节 | `volume`、`data`、`backup` |
| 必填变量 | 「配置」或「环境变量」章节 | `environment`、`required`、`Variables` |

三条实用判断：README 的「快速开始」里出现的变量通常是必填的；「备份」章节提到的目录就是装着数据的那一个；如果让你复制 `.env.example`，说明真实的值放在外部文件里。

**别忘了边界**：`volumes` 只保证容器重建时数据还在，**不保证数据不会丢** —— 备份是另一件事。`.env` 只是把密码换了个地方，**并没有加密**。

### 复述（12 分钟）

- 分别说明四个字段各回答什么问题。
- 回答：为什么 `volumes` 是数据安全的界线？
- 回答：README 里只写了「访问 8080」，你还缺哪些信息？

### 测试（13 分钟，不给答案）

1. `image`、`ports`、`volumes`、`environment` 分别说明什么？
2. 判断：`"8080:80"` 中，你应该访问的是 80。
3. 判断：有了 volumes，数据就不会丢失。
4. 一份 Compose 文件里写着 `./data:/app/data`，数据实际存在哪里？
5. `environment` 里出现 `${DB_PASSWORD}` 是什么意思？

### 今日产出（5 分钟）

给一份示例 Compose 文件逐段写中文旁注，标出四个字段各自说明什么。

## Day 3：创建、停止、日志、升级

**新概念：** Container Lifecycle、Logs、Upgrade

**总时长：** 55 分钟

### 今日目标

- 分清「停止」「重建」「删除」三种操作。
- 知道改了 Compose 文件之后，怎样才能生效。
- 知道出问题时先看日志，以及升级前为什么必须先备份。

### 学习（25 分钟）

容器的一生是一个循环：

```text
创建 → 运行 → 停止 → 重建（升级）
```

关键区分：

```text
停止（Stop）    →  东西还在，可以再启动
删除（Remove）  →  容器没了，只能重建
重建（Recreate）→  按新描述造一个新的，旧的扔掉
```

**文件改动什么时候生效：**

```text
改了 environment / ports / image  →  需要重建才生效
只改了挂载目录里的文件            →  通常立刻生效
什么都没改，程序卡住              →  重启即可
```

**日志是程序唯一说话的地方。** 服务打不开时，第一反应不是反复重启，而是看日志最后几行 —— 它通常会直接写出原因（缺变量、端口冲突、连不上依赖）。分享日志前记得去掉敏感内容。

**升级的正确顺序：**

```text
1. 看新版本说明  2. 备份数据目录  3. 记录当前版本
4. 改版本号      5. 重新应用      6. 看日志       7. 访问验证
```

第 2 步不能跳过：**程序可以回滚，数据结构未必能降级。**

### 复述（12 分钟）

- 说明「停止」和「删除」的差别。
- 回答：为什么改了文件之后服务没变化？
- 回答：为什么升级前必须先备份？

### 测试（13 分钟，不给答案）

1. 容器的「停止」和「删除」有什么不同？
2. 判断：改完 `compose.yaml` 后，服务会自动按新配置重建。
3. 判断：出问题时最有效的做法是立即重启容器。
4. 升级前必须先做什么？为什么？
5. 服务打不开时，第一步应该看什么？

### 今日产出（5 分钟）

画一张「容器生命周期与数据去向」的图，标出每一步之后 volumes 里的数据是否还在。

## Day 4：一次局域网部署

**新概念：** Local Deployment、Predict then Verify

**总时长：** 55 分钟

### 今日目标

- 用一个只用示例数据、不含任何凭据的服务完成一次部署。
- 在动手前预测访问地址和数据位置，动手后逐条验证。
- 说清这次部署「是否对公网开放」以及理由。

### 学习（25 分钟）

练习对象要满足三个条件：

```text
1. 不需要账号和密码
2. 不接触任何真实数据
3. 只在局域网内部，不对公网开放
```

目录结构保持简单，文件和资料放在一起：

```text
~/hello-web/
├── compose.yaml
└── site/                 ← 数据目录，会被挂进容器
    └── index.html        ← 只放示例文字
```

示例文件（镜像名为教学用虚构名称）：

```yaml
services:
  hello:
    image: example/hello-web:1.0
    ports:
      - "8081:80"
    volumes:
      - ./site:/usr/share/web/static:ro
    environment:
      - SITE_TITLE=Practice Only
```

**动手前先写下四个预测：**

```text
用什么？   ______________
从哪进？   ______________
数据在哪？ ______________
缺什么？   ______________
```

**验证方式**：看日志最后几行 → 浏览器访问「设备地址:8081」→ 回到文件管理器改一下 `index.html`，刷新页面看是否立刻变化。**能变化，就证明挂载路径找对了。**

**预测和实际对不上时，那正是这次练习最有价值的部分。**

### 复述（12 分钟）

- 说明这次部署的四个字段分别是什么。
- 回答：怎么验证「数据目录确实被挂进了容器」？
- 回答：为什么练习服务必须只在局域网内？

### 测试（13 分钟，不给答案）

1. 为什么第一轮练习必须使用示例数据？
2. 判断：页面能打开，就说明这次部署是完整的。
3. 判断：把 `ports` 从 8080 改成 8081，只需要改这一处，访问时用新端口即可。
4. 怎么验证「数据目录挂对了」？
5. 为什么练习阶段不建议打开开机自动启动？

### 今日产出（5 分钟）

完成一张部署记录表：服务是什么、访问地址、数据位置、必填变量、是否对公网开放、如何验证正常。

## Day 5：Compose 综合题

**新概念：** （综合应用，无新概念）

**总时长：** 55 分钟

### 今日目标

- 从需求描述推出四个字段，把不完整的模板补齐。
- 把一份 `docker run` 命令翻译成 Compose 文件。
- 指出一份 Compose 文件「没有告诉你什么」。

### 学习（20 分钟）

从需求到字段，是有对应关系的：

```text
「用某个程序，版本 2.3」    →  image
「通过 8090 端口访问」      →  ports
「数据要保存下来」          →  volumes
「有一个必填的口令」        →  environment
```

**翻译规则**（README 只给命令时）：

```text
--name notes        →  服务名
-p 8080:80          →  ports 一行
-v ./data:/app/data →  volumes 一行
-e APP_MODE=simple  →  environment 一行
镜像名              →  image
```

注意 `-d` 不会出现在结果里 —— Compose 默认就在后台运行。**这类「命令里有、文件里没有」的项，不是漏了。**

**补齐之后一定要问这一句：**

> 这份文件没有告诉你什么？

```text
该不该对公网开放？
数据谁来备份？备份放在哪？
密码存在这里安全吗？
升级会不会丢数据？
```

**Compose 文件只描述「容器怎么跑」，不回答上面任何一个问题。** 能主动指出这些空缺，才是本周真正的能力。

### 复述（12 分钟）

用两分钟口头讲清这个流程：

- 从需求推出四个字段，并说出理由。
- 说明「这份文件没告诉你什么」。
- 说明改了字段之后要怎么才能生效。

### 周测（13 分钟，不给答案）

1. 判断：Compose 文件里没写密码，说明这个部署是安全的。
2. 判断：字段填齐了，部署就完整了。
3. 判断：看到 `image: example/myapp` 没写标签，说明它一定是最新版本，所以最好。
4. 给你一份不完整的模板和一段需求，补齐四个字段并逐条说明理由。
5. 找出示例 Compose 文件里至少两处问题，并说明怎么改。
6. 用不超过 150 字说明：一份 Compose 文件能告诉你什么、不能告诉你什么。
