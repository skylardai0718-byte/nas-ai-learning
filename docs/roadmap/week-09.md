## Day 1：项目六问法

**新概念：** 项目六问法

**总时长：** 55 分钟

### 今日目标

- 掌握一套统一的六问框架，用来分析任何一个 Self-hosted 项目。
- 理解为什么「先问框架，再看教程」能省下大量试错。
- 能对六问中的每一问给出你自己的答案模板。

### 学习（25 分钟）

本周开始，你不再只是学单个概念，而是学**怎么读一个项目**。

面对一个陌生的 Self-hosted 项目，大多数人会直接去抄教程、执行命令。问题是：教程不会告诉你「为什么这样配」，一旦出问题就无从下手。

**项目六问法**就是一套固定的提问清单。任何项目，先问这六个问题：

```text
① 它解决什么问题？        →  这个服务存在的意义
② 硬件需求是什么？        →  CPU / 内存 / 存储 / 是否需要特殊硬件
③ 运行在哪里？            →  裸机 / Docker / VM
④ 怎么联网访问？          →  局域网 / 端口 / 远程方式
⑤ 数据存在哪里？          →  配置、数据库、媒体文件的位置和持久性
⑥ Docker 在其中起什么作用？→  它到底是 Docker、依赖 Docker，还是与 Docker 无关
```

这六问的顺序本身就是逻辑：先说价值，再说资源，最后才是部署细节。**很多人反过来，先折腾部署，最后才发现硬件跑不动，或者数据放错了地方。**

本周后面三天，都用这六问去分析具体服务。今天先把框架本身吃透。

- 回答：六问里哪一问最容易被初学者忽略？为什么？

3. 判断：硬件需求只包括 CPU 和内存。
4. 「运行在哪里」这一问，可能的答案有哪几种？
5. 为什么「数据存在哪里」这一问对 NAS 用户尤其重要？

## Day 2：用六问法分析 Jellyfin

**新概念：** Jellyfin、硬件转码（Hardware Transcoding）

**总时长：** 55 分钟

### 今日目标

- 用项目六问法完整分析一个影音服务。
- 理解「服务端 / 客户端」的分离，以及媒体数据放在哪里。
- 知道「硬件转码」是什么，以及它为什么依赖特定硬件。

### 学习（25 分钟）

**Jellyfin** 是一个开源的媒体服务器：把你硬盘里的视频、音乐整理成一个可以像流媒体网站一样浏览和播放的库。

用六问分析它：

```text
① 解决什么问题
   把散落在硬盘上的影音文件，变成带封面、简介、播放进度的媒体库，
   并让手机、电视、电脑都能看。

② 硬件需求
   本体很轻。真正吃资源的是「转码」—— 播放端不支持原格式时，
   服务器要实时把视频转成播放端能接受的格式。

③ 运行在哪里
   通常跑在 Docker 里，也可以装在裸机上。

④ 怎么联网访问
   局域网内用「设备地址:端口」访问；出门访问属于远程访问问题，
   参考 Week 5 的结论 —— 优先建立私有通道，而不是把端口暴露到公网。

⑤ 数据存在哪里
   两部分：媒体文件（你的视频，通常挂载进来的大容量存储）
   和配置/数据库（缩略图、观看记录、用户设置，需要持久化保留）。

⑥ Docker 的作用
   Docker 负责把 Jellyfin 和它的运行环境打包在一起，方便升级和迁移；
   但它不负责你的媒体文件 —— 媒体是通过挂载从宿主机进容器的。
```

**硬件转码（Hardware Transcoding）** 需要重点解释：

```text
转码 = 把视频从一种格式/分辨率/码率，实时转换成另一种

软件转码：用 CPU 硬算 → 通用，但很吃 CPU，可能卡顿
硬件转码：交给专门的处理单元（如核显里的编解码单元）→ 省 CPU、更快
```

硬件转码的边界：它**依赖特定硬件**，而且**不同硬件支持的格式不一样**。买机器前要看它能不能转你手里的视频格式 —— 规格表通常不会直接告诉你这件事。

### 复述（12 分钟）

- 用六问法口头过一遍 Jellyfin。
- 回答：转码是什么？为什么它是影音服务的主要性能瓶颈？
- 回答：Jellyfin 的媒体文件和它的数据库，在「数据存在哪里」这一问里有什么不同？

### 测试（13 分钟，不给答案）

1. Jellyfin 解决什么问题？
2. 判断：Jellyfin 播放卡顿一定是因为网络慢。
3. 判断：硬件转码不依赖硬件，任何机器效果一样。
4. Jellyfin 的媒体文件和配置数据库，哪个更需要定期备份？
5. 出门访问家里的 Jellyfin，为什么不建议直接把端口暴露到公网？

## Day 3：Pi-hole、Immich 与 Tailscale

**新概念：** Pi-hole、Immich、Tailscale

**总时长：** 55 分钟

### 今日目标

- 用六问法快速定位三个不同用途的服务：网络、照片、远程访问。
- 理解这三个服务分别在系统的哪一层起作用。
- 认识这类服务的隐私边界：它们接触到哪些个人数据。

### 学习（25 分钟）

今天用六问法快速过三个服务。**三选一深入**，其余两个做到能定位即可。另外，Home Assistant（智能家居）和 Vaultwarden（密码管理）第一轮只需要知道它们大概做什么、在哪一层。

```text
Pi-hole —— 网络层的广告拦截
① 解决什么问题：在整个家庭网络层面拦截广告和追踪域名
② 硬件需求：很轻，低功耗小机器就能跑
③ 运行在哪里：Docker 或裸机，通常在网络入口附近
④ 怎么联网访问：它本身是 DNS 服务，家里设备把 DNS 指向它
⑤ 数据存在哪里：查询记录、黑名单/白名单配置
⑥ Docker 的作用：打包运行环境，配置目录需要持久化

Immich —— 照片与视频备份
① 解决什么问题：自建的照片备份与浏览，替代云相册
② 硬件需求：照片多了需要较大存储；机器学习功能吃资源
③ 运行在哪里：Docker（它本身就是围绕容器部署设计的）
④ 怎么联网访问：局域网访问；远程访问参考 Week 5 结论
⑤ 数据存在哪里：照片原件 + 数据库 + 缩略图，三者都要备份
⑥ Docker 的作用：Immich 由多个容器组成，Docker 是它正常工作的前提

Tailscale —— 远程访问通道（Week 5 已学过原理）
① 解决什么问题：让外面的设备安全地访问家里网络，不用开放端口
② 硬件需求：几乎可以忽略
③ 运行在哪里：每台设备装客户端，不是「一个服务跑在 NAS 上」
④ 怎么联网访问：它本身就是联网方式
⑤ 数据存在哪里：主要是密钥和登录状态，配置很少
⑥ Docker 的作用：可以容器化，但它更适合直接装在需要联网的设备上
```

**安全提醒**：Pi-hole 会记录全家设备的访问域名，Immich 存的是私人照片，Tailscale 涉及登录密钥。这三类数据都属于隐私。**不要在公开笔记里贴真实的查询日志、照片、账号或密钥。**

## Day 4：Virtual Machine、Hypervisor 与 VM vs Docker

**新概念：** Virtual Machine、Hypervisor、VM vs Docker

**总时长：** 55 分钟

### 今日目标

- 准确理解虚拟机（VM）是什么，以及它和物理机的关系。
- 理解 Hypervisor 的作用。
- 从「是否带完整操作系统、隔离程度、资源开销」三个角度，准确比较 VM 和 Docker。

### 学习（25 分钟）

前面几周都在讲 Docker。今天要知道：**容器不是唯一的隔离方式，虚拟机是另一种，而且两者解决的问题并不完全一样。**

**虚拟机（Virtual Machine，VM）**：在一台物理机上，模拟出一台完整的计算机。这台「计算机」有自己的操作系统、自己的内核，看起来就像一台真实的机器。

**Hypervisor（虚拟机管理程序）**：负责创建和运行虚拟机的软件层。它把物理机的 CPU、内存、硬盘、网络切分给各个虚拟机，并保证它们互不干扰。

```text
物理机（真硬件）
└── Hypervisor          （切分资源的软件层）
    ├── VM 1            （完整操作系统 + 应用）
    ├── VM 2            （完整操作系统 + 应用）
    └── VM 3            （完整操作系统 + 应用）
```

**VM 和 Docker 的三个核心差别：**

```text
                 VM                        Docker 容器
是否带完整 OS    带（每个 VM 一个内核）      不带（共用宿主机内核）
隔离程度         很高（硬件级隔离）          较强（进程级隔离）
资源开销         大（每台 VM 都要跑一个 OS）  小（共享内核，只跑进程）
```

**这里必须讲准，不能简单说「Docker 更轻所以更好」：**

- VM 带完整操作系统，所以**更强隔离**，但每台都要单独占内存、占磁盘、启动慢。
- Docker 共用宿主机内核，所以**更快更省**，但隔离性弱于 VM —— 内核是共享的。
- 如果你需要**跑一个和宿主机完全不同的操作系统**（比如在 NAS 上跑一个独立的 Linux 发行版），Docker 做不到，得用 VM。
- 如果你只是**想方便地部署一个应用、快速升级**，Docker 更合适。

**选择的依据是需求，不是「谁更先进」。**

## Day 5：Proxmox、KVM 与虚拟化周测

**新概念：** Proxmox、KVM

**总时长：** 55 分钟

### 今日目标

- 认识 Proxmox 和 KVM，知道它们在家庭实验室里的位置。
- 能综合运用六问法和 VM/Docker 的判断，为场景选择运行方式。
- 完成本周周测与 Weekly Review。

### 学习（20 分钟）

**KVM（Kernel-based Virtual Machine）** 是 Linux 内核自带的虚拟化技术 —— 它是 Hypervisor 的一种实现。它负责最底层的工作：让 Linux 内核能创建和运行虚拟机。

**Proxmox** 是一个建立在 KVM 之上的虚拟化管理平台 —— 它把 KVM（以及别的技术）包装成一个有网页界面、方便管理的系统。你可以理解为：KVM 是发动机，Proxmox 是带仪表盘和方向盘的整车。

```text
物理机
└── Proxmox         （网页管理界面 + 管理功能）
    └── KVM         （真正的虚拟化引擎）
        ├── VM：一个完整的操作系统
        └── 也可以跑 Docker 容器（在某个 VM 或直接在系统上）
```

**为什么家庭用户会用到 Proxmox？** 因为它让你在一台机器上，跑好几个互相隔离的完整系统：一个做 NAS、一个做实验、一个跑别的东西 —— 各玩各的，一个坏了不影响另一个。

**但也要知道它的边界**：Proxmox 本身有学习成本，硬件也有要求（虚拟化需要 CPU 支持）。如果只是想在 NAS 上跑一两个应用，用 Docker 就够了 —— **不要为了「高级」而引入你不需要的复杂度。**

本周综合题：给定场景，选择裸机、Docker 还是 VM。

```text
场景 A：在 NAS 上跑一个影音服务  →  Docker（一个应用，方便升级）
场景 B：想体验一个完全不同的操作系统  →  VM（需要独立 OS）
场景 C：想在 NAS 上跑大量互相隔离的实验  →  Proxmox + VM
```
