# 第十二周详细计划：AI Agent、RAG 与 NAS + AI

## 本周目标

完成后，你应能：

1. 说清 LLM 只能输出文字，工具调用是「模型给出意图、外部程序真正执行」。
2. 解释 Agent 是「LLM + 工具 + 记忆 + 循环」，而不是万能且完全自主的程序。
3. 画出 RAG 的三步路径：检索资料 → 放入上下文 → 生成回答。
4. 设计一个只读访问 NAS 文档的 Agent，并指出隐私与误操作风险。
5. 从 NAS 硬件一路画到 AI 应用，完成 12 周的最终综合测试。

> 每天 45–60 分钟。测试题不立即公布答案；作答后，再按“完全理解 / 基本理解 / 表面理解 / 存在误区”批改。
>
> **本周的安全提醒：** 本周是全部 12 周里唯一涉及「让程序自动操作你的文件」的一周。**练习和笔记中不要写真实的文件路径、真实的文档内容、API 密钥或访问令牌；示范权限设计时一律使用示例路径（如 `/volume1/docs/`）。默认只给 Agent 读权限，不要给写权限。**重点是理解权限边界为什么重要，不是照着配置跑起来。

## Day 1：LLM、Tools 与 Function Calling

**新概念：** LLM、Tools、Function Calling

**总时长：** 55 分钟

### 今日目标

- 理解 LLM 的输出永远是文本，它本身不能执行任何操作。
- 理解工具的调用是「模型给出结构化意图，外部程序真正执行」。
- 能区分「模型建议操作」和「系统真实执行操作」。

### 学习（25 分钟）

前两周你知道了模型是什么、怎么跑起来。今天开始看它怎么「做事」。

先记住一条底线：

```text
LLM 只会做一件事：根据输入，生成接下来的文字。
它不能读文件、不能发请求、不能改数据库。
```

那它是怎么「查天气」「读文档」的？靠**工具（Tools）**。

```text
你问：我 NAS 上那份 PDF 讲了什么？

模型自己做不到 —— 它看不到你的文件
模型能做的是：输出一段结构化的文字，说「请帮我调用 read_file，参数是 …」
```

这段「结构化的调用意图」，就叫 **Function Calling（函数调用）**。

```text
模型输出：{ "tool": "read_file", "path": "/volume1/docs/a.pdf" }
             ↓
        外部程序收到这个意图
             ↓
        外部程序真的去读文件
             ↓
        把读到的内容再交回模型
```

**关键区分（本周第一重要）：**

```text
模型建议操作   →  一段文字，安全无害
系统真实执行   →  外面那个程序真的动手了
```

模型从来不会「自己执行」。它只是建议。执行与否、执行什么，由外面的程序决定 ——
**所有权限和风险，都压在这个程序身上。**

### 复述（12 分钟）

- 用一句话说明 LLM 到底能做什么、不能做什么。
- 回答：Function Calling 发生在模型里，还是模型外？
- 回答：为什么说「模型建议操作」和「系统真实执行」是两件事？

### 测试（13 分钟，不给答案）

1. LLM 的输出本质上是什么？
2. 判断：模型可以直接读取你 NAS 上的文件。
3. 判断：Function Calling 是模型直接执行了操作。
4. 模型说「我要调用 read_file」，接下来是谁在动手？
5. 如果 Agent 误删了文件，责任在于模型还是外部程序？

### 今日产出（5 分钟）

## Day 2：Memory、Agent 与 Workflow

**新概念：** Memory、Agent、Workflow

**总时长：** 55 分钟

### 今日目标

- 理解记忆（Memory）解决「模型不记得上下文之外的事」的问题。
- 说清 Agent 的构成：LLM + 工具 + 记忆 + 循环。
- 区分 Agent 和固定 Workflow 的差别。

### 学习（25 分钟）

模型有一个天生的限制：**它只看得到这一次交给它的内容。**

```text
第 1 轮：你问「我上周提到的那个文件在哪？」
模型：不知道 —— 它没有「上周」
```

**记忆（Memory）** 就是人为补上这一段：把之前的对话、或者外部存下来的信息，在需要时再塞回上下文。

于是有了 **Agent（智能体）** 的基本公式：

```text
Agent  =  LLM  +  工具（Tools）  +  记忆（Memory）  +  循环（Loop）
```

这个「循环」是关键 —— 它不是问一次答一次，而是：

```text
想 → 调用工具 → 看结果 → 再想 → 再调用 → …
直到它认为可以给出答案
```

**但这里要破除一个很常见的误解：**

> Agent 不是万能的、完全自主的程序。

它每一步都受限于：模型本身的能力、你给它的工具、你能让它看到的信息、以及允许它做多久。
换句话说，**它的边界是你画的，不是它自己长的。**

与之相对的是 **Workflow（工作流）**：步骤由人预先写死。

```text
Workflow：步骤固定      A → B → C，每次都一样
Agent  ：步骤由模型自己决定，走几步、走哪条路都不一定
```

固定 Workflow 更可预测、更好排查、风险更低；Agent 更灵活，但也更难控制。
**不是越自主越好** —— 能写死的流程，就不要交给模型即兴发挥。

### 复述（12 分钟）

- 说出 Agent 的四个组成部分。
- 回答：记忆解决的到底是什么问题？
- 回答：Agent 和 Workflow 的核心差别是什么？为什么 Workflow 有时更合适？

### 测试（13 分钟，不给答案）

4. 一个每天固定把备份日志整理成表格的任务，用 Workflow 还是 Agent 更合适？

## Day 3：RAG 与向量数据库

**新概念：** RAG、Retrieval、Vector Database

**总时长：** 55 分钟

### 今日目标

- 理解 RAG 解决的「模型的训练数据里没有你的私有资料」这个问题。
- 画出 RAG 的三步路径。
- 知道向量数据库在其中的角色，以及它不能替代什么。

### 学习（25 分钟）

先看模型的一个硬伤：**它的训练数据里没有你的私有资料。**

```text
你问：我那份报修单说了什么？
模型的训练数据里 → 没有「你那份报修单」
它只能编一个听起来合理的回答   ← 这就是「幻觉」的来源
```

**RAG（检索增强生成，Retrieval-Augmented Generation）** 的做法是：不要指望模型记住，
**在回答之前，先把相关资料找出来递到它面前。**

```text
① 检索资料（Retrieval）
     从你的文档库里，找出和问题最相关的几段
              ↓
② 放入上下文（Context）
     把这几段文字塞进这次提问里，一起交给模型
              ↓
③ 生成回答（Generation）
     模型看着「问题 + 找来的资料」写答案
```

换句话说：

```text
不用 RAG：把问题直接抛给模型  → 它可能编
用了 RAG：先找资料再问模型    → 它有据可依
```

那「找出最相关的几段」是怎么做到的？靠 **向量数据库（Vector Database）**。

它做的事情是：把文字变成一串数字（向量），意思相近的文字，数字也相近。于是「找出最相关」
就变成了「找出数字最接近的几段」。它不负责理解、不负责回答，**只负责找。**

这里要点破一个误区：**RAG 不等于「模型变聪明了」。** 它只是每次都临时给模型递小抄。
资料找错了，答案还是会错 —— 检索的质量决定 RAG 的上限。

- 默写 RAG 的三步路径。
- 回答：向量数据库在 RAG 里负责什么？它不负责什么？

### 测试（13 分钟，不给答案）

## Day 4：MCP 与权限边界

**新概念：** MCP、Permission Boundary、NAS + AI Agent

**总时长：** 55 分钟

### 今日目标

- 理解 MCP 这类协议的设计意图：让工具和上下文以统一的方式被接入。
- 理解权限边界（只读 vs 可写），并说明为什么不该给 Agent 写权限。
- 设计一个只读访问 NAS 文档的 Agent，并指出隐私与误操作风险。

### 学习（25 分钟）

昨天你知道了模型靠「工具」做事。但每接一个新工具，都要单独对接一次，很麻烦。

**MCP（模型上下文协议，Model Context Protocol）** 想解决的就是这件事：
用一套统一的方式，把「数据源」和「可用的工具」描述出来，让不同的模型/应用都能接。

它的设计意图可以概括成两句：

```text
让「提供工具和数据的一方」与「使用模型的另一方」解耦
你只要按统一方式描述一次，谁都能接
```

**注意：MCP 本身不授予任何权限。** 它只是描述「有哪些工具可用」。
真正决定「能不能做」的，是你在后端给的**权限边界（Permission Boundary）**。

这是本周最重要的一课。回想 Day 1 的结论：**执行动作的是外面的程序。**
那么，你把什么权限交给那个程序，就等于把什么权力交给了 Agent。

```text
只读（Read-only）  →  Agent 能看，不能改
可写（Read-write） →  Agent 能改，也能删
```

**为什么默认只给读权限？** 因为 Agent 会犯错，而且它犯的错会直接作用在真实数据上：

```text
模型理解偏了   →  调用了错误的工具
工具参数写错   →  动了不该动的文件
循环没停下来   →  同一个操作反复执行
```

读错了，你顶多得到一段错答案；写错了，**数据可能就回不来了。**

所以设计一个「只读访问 NAS 文档」的 Agent，边界应该这样画：

```text
✓  允许：读取指定目录（如 /volume1/docs/）
✓  允许：列出文件名
✗  禁止：写入、修改、删除
✗  禁止：访问目录外的任何路径
✗  禁止：访问包含密钥、凭据的目录
```

**最小权限原则（Least Privilege）：** 只给完成这件事所必需的那一份权限，不多给一分。
不是「反正只读，整个 NAS 都开放也没事」—— 能读到的东西越少越好。

隐私的风险也一样真实：把整个 NAS 开放给 Agent，等于把家庭照片、私人文档、财务记录
都变成了「模型可能读到、也可能被回传的内容」。**可读范围就是隐私边界。**

### 复述（12 分钟）

- 用一句话说明 MCP 想解决什么。
- 回答：为什么默认不给 Agent 写权限？

### 测试（13 分钟，不给答案）

2. 判断：MCP 会自动帮 Agent 管好权限。
